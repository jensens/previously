## A switchover costs no request

The feedback measured that `serve` survives a switchover of the primary, and that the first request after it fails: the pool hands out a connection the old primary ended.
The server now checks a pooled connection before it uses it, SQLAlchemy's `pool_pre_ping`, and replaces one that's dead.
The check costs one round trip per request that takes a connection from the pool.

**It stands when** a switchover done on purpose, as for the feedback, is followed by `GET /healthz` at 200 on the first try, with no traceback in the log of `previously-mcp`, and `whoami` answers right after.
That's the measurement the feedback offered; repeat it if the moment suits, and report it either way.

## Answers in one call, on the clients

`write_approve` and `write_reject` now answer a proposal in one call each, without `confirm` and without a handle.
The client's question to the person is the confirmation; a second step only asked the same person a second time.
`write_assertion` keeps its two calls, and `PREVIOUSLY_MCP_CONFIRM_KEY` stays where it is, in `previously-mcp` only.

Both answering tools carry `_meta` `"anthropic/requiresUserInteraction": true` in their tool list, a mark meant to make Claude Code ask before every call.
Whether it does without an ask rule isn't measured yet, so the requirement on the clients stands as the earlier handoff states it: neither tool may be allowed always.

That's on the maintainer's machine, not in kup6s.
One consequence reaches the clients: the input schema of the two tools changed, so a client that keeps the tool list across sessions has to fetch it again after the deployment.
