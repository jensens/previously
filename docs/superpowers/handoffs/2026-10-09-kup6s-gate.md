# Handoff to kup6s: the gate, two API keys and a model server

**Date:** 2026-10-09
**From:** the Previously repository, `jensens/previously`
**To:** the agent that works in the kup6s environment
**Source:** the specification `docs/superpowers/specs/2026-10-09-pilot-gate-und-policy.md`, §6 (German, frozen), and what running the commands against a real Ollama measured since

This file adds to the handoffs of 2026-10-05, `docs/superpowers/handoffs/2026-10-05-kup6s-delivery.md`, and of 2026-10-06, `docs/superpowers/handoffs/2026-10-06-kup6s-ingest.md`, and assumes everything those two ask for: the database, the bucket, the secrets split by who needs them, the migration job, the tools pod and the CronJobs.
Like them, it says **what** Previously needs, **why**, and **how to recognize that it stands**, and never how to build it in cdk8s.
Nothing in this repository deploys anything into kup6s.

What it adds is the gate: the one place from which a language model reads content of the log, under a policy that stands in the log itself.
It's a command for the tools pod, `previously gate try`, and no job runs it: the maintainer starts it by hand.
It has two parts.
The first, the keys and the network, is needed to call Anthropic and Mistral.
The second, a model server inside the cluster, is its own piece of work and can come later; until it stands, the gate refuses wherever the policy allows only a local model.

## The image

The first release that has `gate` is the first after `0.1.0a2`; `0.1.0a2` carries `ingest imap` and not the gate.
Pin its exact version, as the first handoff says for every release until `1.0.0`.

The release brings **no migration**: the policy and the audit are events in the chain, in the tables that exist, and there's no new table.
Run the migration job of the release before anything else, as for every release, and expect it to report `up to date:` with `0005_watermark`.

**It stands when** the tools pod runs the new image and `previously gate --help` lists the subcommands `explain` and `try`.

## Two secrets

`gate try` reads two API keys from the environment, and they belong in a secret of their own that **only the tools pod mounts**:

| Variable | Value |
|---|---|
| `ANTHROPIC_API_KEY` | The API key of the Anthropic account the maintainer uses for Previously. |
| `MISTRAL_API_KEY` | The API key of the Mistral account. |

The maintainer gives you both.
Neither belongs in a CronJob: no scheduled job calls a model in this release.

A missing key isn't an error by itself.
Only the call that the policy gives to that provider fails, with `Error: anthropic: the provider is not configured — set ANTHROPIC_API_KEY`, and the failure is recorded in the log as a call of its own.
So you can set one key first and the other later.

No message of `previously` and no event prints a key, also not when a provider refuses it.
`previously` reads them from the environment and has no argument for them, so they appear in no command line.

`docs/reference/configuration.md` is the authoritative description of each.

**One variable not to set:** the Anthropic client reads `ANTHROPIC_BASE_URL` on its own, and a pod that sets it sends the content of the calls wherever that points.
Don't set it in any pod that holds the key, unless the maintainer asks you to for a proxy he runs.

## Network out

The tools pod, and only it, needs these:

- `api.anthropic.com`, port 443;
- `api.mistral.ai`, port 443;
- DNS, to resolve both.

Nothing inbound.
The calls verify the certificates against the trust store of the image, and no setting turns that off.

**Why only the tools pod:** the content of the log leaves the cluster there and nowhere else in this release.
A rule that opens these two hosts for another pod opens a second way out, and the page `docs/explanation/trust-boundaries.md` counts the ways out.

**It stands when**, from inside the tools pod, a TLS handshake with both hosts succeeds, such as `curl -sS -o /dev/null -w '%{http_code}\n' https://api.anthropic.com` printing a status code, whatever it is, and the same for `https://api.mistral.ai`.

## The price file

Optional.
The image carries a price file that the maintainer read from the two providers on 2026-10-09, and `gate try` estimates the cost of each call with it.
To use another, mount a TOML file as a ConfigMap and set `PREVIOUSLY_PRICES` to its path in the tools pod; the format is in `docs/reference/configuration.md`.
Every call records the SHA-256 of the file it used, so a changed file is visible in the log.

The estimate is an estimate; the bill of the provider is what counts.
A stale price makes only the estimate wrong, so nothing depends on updating the file on a schedule.

## No CronJob

Nothing in this release runs the gate on a schedule.
The maintainer sets the first policy himself, from the tools pod:

```shell
previously policy provider anthropic …
previously policy circle …
previously gate explain EVENT
```

`docs/how-to/set-a-policy-and-try-a-call.md` walks through it.
`gate explain` calls nothing and costs nothing.
A CronJob that reports `previously policy gaps`, the list of circles whose calls fell back to the local model, is a later idea and isn't asked for here.

## An erasure doesn't reach the copy of a provider

When the gate sends a mail to a provider, the provider keeps its own copy: Anthropic for 30 days, Mistral for a time not yet looked up.
No erasure in `previously` reaches those copies, and `previously redact` does not pretend to.
Whoever promises the erasure of a mail promises it with that limit named, beside the retention of the database, the bucket and the mail server's backups the earlier handoffs ask for.
Tell the maintainer if you learn of any retention in the path that he doesn't know.

## The model server

**Do this after the part above, as a piece of work of its own.**
The gate calls a local model for content that no rule allows to leave: with no rule, the policy lets only a local model see a mail.
Until a model server stands in the cluster, the gate in kup6s doesn't process those calls: it denies them with the reason `no local provider is declared` while no local provider is declared, and once one is, it records them with the outcome `error` and a sentence that names `PREVIOUSLY_LOCAL_MODEL_URL` while that is unset, or the server while it doesn't answer.
That is a safe failure and not a defect.

What `previously` needs:

- An **OpenAI-compatible server**, Ollama or `llama.cpp` with its server, reachable from the tools pod at one address.
  The maintainer tested against Ollama 0.13.2 and nothing else, so Ollama is the sure choice.
- The address in `PREVIOUSLY_LOCAL_MODEL_URL` in the tools pod, ending in `/v1`, such as `http://<service>:11434/v1`.
  Without the variable no local provider is reachable.
- **Only from inside the cluster.** No Ingress, no `LoadBalancer`, and a network policy that lets only the tools pod reach it.
  The server has no authentication, and everything the gate sends it is a mail.
- The model `qwen3:4b`, which is about 2.5 GB on disk.
  It runs on CPU; on the maintainer's laptop (an `i7-11370H`, under another load) one mail took between 7 and 15 seconds.
  `previously` sets `reasoning_effort` to `none` on every call to it, and that's needed: measured on 2026-10-09, without it a call didn't finish in 600 seconds.
- Memory and CPU: **not measured.**
  Start with enough memory for the model file plus its context, and tell the maintainer what you set and what the server used.
- The model's weights have to come from somewhere once: the registry of Ollama, or a volume that you fill.
  If the server pulls them itself, it needs outbound access to do that, once; after that the server needs none, and a policy can take it away.

The result of the local model is weaker than the hosted ones.
That's why `previously` marks every call that fell back to it, and why `previously policy gaps` lists the circles where that happened.

**It stands when**, from the tools pod, `curl "$PREVIOUSLY_LOCAL_MODEL_URL/models"` lists `qwen3:4b`, and `previously gate try EVENT` over a mail of a circle with no rule prints one JSON line with `language`, `topic` and `participants`, then `model_call: event <id>`, with `processed locally:` on standard error.

## A host without a cluster

For anybody who runs Previously with a `docker-compose` file, the part above is three environment variables, optionally a file for the prices, and a service `ollama` beside the database.
There's no table, no migration and no timer.
This file considers it and builds nothing for it.

## How to recognize that everything stands

1. The tools pod runs the new image and the migration job reported `up to date:` with `0005_watermark`.
2. The secret of the keys exists and only the tools pod mounts it; no CronJob does.
3. The tools pod reaches the two hosts on port 443, and no other pod has the rule.
4. `ANTHROPIC_BASE_URL` is set nowhere.
5. Optional, later: the model server answers at `PREVIOUSLY_LOCAL_MODEL_URL` and only the tools pod reaches it.
6. The maintainer knows what the model server was given in memory and CPU.
