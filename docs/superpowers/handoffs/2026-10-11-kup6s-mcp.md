## The image

The release is `v0.1.0a3`, the first with the gate and the MCP server.
Pin its exact version, as the first handoff says for every release until `1.0.0`.

The release brings **no migration**: clients, the policy and the record of every call are events in the chain, in the tables that exist.
Run the migration job of the release before anything else, as for every release, and expect it to report `up to date:` with `0005_watermark`.

**It stands when** the tools pod runs the new image, and `previously --help` there lists the subcommands `client`, `access`, `mcp` and `serve` beside `gate`.

## The deployment `previously-mcp`

One Deployment, named `previously-mcp`, running the image with the command `previously serve`, one replica, and one Service in front of it.

| Variable | Value |
|---|---|
| `PREVIOUSLY_DSN` | The connection string of a role that may write: every call of a client appends an event that records it. |
| `PREVIOUSLY_MCP_HOST` | `0.0.0.0`, so that the Service reaches the process; unset, the server listens on `127.0.0.1` inside the pod only. |
| `PREVIOUSLY_MCP_PORT` | Unset, which means `8765`, or a port of your choice. |
| `PREVIOUSLY_MCP_ALLOWED_HOSTS` | Unset for stage A; for stage A2, the host name under which the clients reach the server, as below. |

`docs/reference/configuration.md` is the authoritative description of each.

The pod needs nothing else from the secrets: no blob settings, because the server shows the names of attachments and never fetches one; no API key, because the server calls no model; no IMAP settings.
It needs the database, and outbound nothing else.
On start, `previously serve` prints one line to standard error, `serving MCP over HTTP on http://0.0.0.0:8765/mcp` with the values above, and then runs until it's stopped.

**Why one replica:** the server keeps no state between calls, so a second one should work, but two workers behind a load balancer were never measured.
Start with one; the map of open points holds the second.

**Memory and CPU: not measured.**
The server holds no cache and reads the log at every call; a call of the chronicle reads the log in batches of 200 rows until a page of 60,000 characters is full.
Tell the maintainer what you set and what the pod used.

## Readiness through `GET /healthz`

`GET /healthz` is the readiness probe, and it's the one request that needs no token.
It runs one trivial query against the database and answers with the status 200 and the body `ok`, or with 503 when the database doesn't answer.
It reaches no MCP, returns no data and writes no record into the log.
An HTTP `GET` probe on the server's port and the path `/healthz` is all the check needs: no secret, no exec, no Python started every period.
Only `GET` on exactly that path passes without a token; every other request without one gets 401.
The probe is answered before the check of the `Host` header, so the address the kubelet names needs no entry in `PREVIOUSLY_MCP_ALLOWED_HOSTS`.
For liveness alone, a TCP check on the port is enough.

This replaces what the specification of the unit planned, a `server/discover` request with the token of a client of its own.
Such a client can call every tool and read whatever its processor may see, so the pod would have held a reading credential to learn "up or down"; and the request needs two `MCP-…` headers and answers 200 with an error without them, which a check of the status alone can't tell from success.

`server/discover` stays the check of the whole path, run by hand by the maintainer with the token of one of his clients rather than a credential of its own.
Measured on 2026-10-11, against the app of `previously serve` with a stand-in for the token lookup, the request needs these headers and this body, and gets the HTTP status 200 with a JSON object that holds `result`:

```text
POST /mcp
Authorization: Bearer TOKEN
Accept: application/json, text/event-stream
Content-Type: application/json
MCP-Protocol-Version: 2026-07-28
Mcp-Method: server/discover

{"jsonrpc": "2.0", "id": 1, "method": "server/discover", "params": {"_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28", "io.modelcontextprotocol/clientCapabilities": {}}}}
```

Check the body and not only the status: without the two `MCP-…` headers the same request also gets 200, with an `error` of `Method not found` instead of a `result`.
`server/discover` writes no record into the log either: only calls of tools, resources and prompts do.

## Access in stages

**Stage A, `kubectl port-forward`.**
The maintainer forwards the Service to his machine, such as `kubectl port-forward svc/previously-mcp 8765:8765`, and points the clients at `http://127.0.0.1:8765/mcp`.
That's the trust model of the tools pod: whoever holds the kubeconfig can reach it, and the token says which client asks.
The server accepts requests whose `Host` names `127.0.0.1`, `localhost` or `[::1]`, with any port, so stage A needs no setting.

**Stage A2, the tailnet.**
The maintainer's Tailscale network, coordinated by Headscale, already exists, and you know how to put a service into it; that's yours to work out.
What Previously needs from it:

- The host name under which the clients reach the server goes into `PREVIOUSLY_MCP_ALLOWED_HOSTS`, separated by commas or blanks if there are several.
  A request whose `Host` names anything else gets 421, and one whose `Origin` names anything else gets 403.
- The token travels in a header of every request, so nobody outside the tailnet may be able to read that path.
- The token stays required inside the tailnet: the network says that somebody from inside asks, the token says which client, and the record of every call needs that.

**Stage B, an Ingress with TLS,** isn't asked for and may never be.
It's a hosting question, not decided here.

## The clients and their tokens

The maintainer creates each client in the tools pod with `previously client add`, which prints its token once.
No token belongs in this handoff, in a manifest, a secret of the cluster, or a repository: the readiness probe needs none, and a client's token stays with the client.
`previously client revoke` locks a client out from its next request, and `previously access` shows what each client saw.
`docs/how-to/connect-claude-code-and-vibe.md` walks the maintainer through it.

## The gate and its model server

The handoff of the gate asks for two API keys in the tools pod, outbound access to two providers from the tools pod alone, and, as its own piece of work, a model server inside the cluster.
None of that changes with the MCP server, and the `previously-mcp` pod needs none of it: it reads and decides, and never calls a model.
Do the gate's part first if you do them one after the other, because the release is the same and the tools pod is where the maintainer then sets the policy that the MCP server decides with.

One sentence of the gate's handoff no longer holds for this release.
It says that nothing comes inbound, and that the content of the log leaves the cluster through the tools pod and nowhere else.
The Service of `previously-mcp` is a second way out: inbound, through the Service, to a client and the provider behind it, each event only as far as the policy lets that client's chain see it.
The egress rule of the tools pod stays as the gate's handoff asks, and `previously-mcp` needs no egress beyond the database.

## A host without a cluster

For anybody who runs Previously with a `docker-compose` file, the server is one more service, `mcp`, running `previously serve` beside the database, with `PREVIOUSLY_MCP_HOST=0.0.0.0` inside the container and its port published on `127.0.0.1` only.
The tokens come from `docker compose run --rm mcp previously client add …`, once per client, and a health check of the service can ask `GET /healthz`.
One token per client, no table, no migration, no timer.
This file considers it and builds nothing for it.

## How to recognize that everything stands

1. The tools pod runs `v0.1.0a3`, and the migration job reported `up to date:` with `0005_watermark`.
2. The handoff of the gate stands as its own list says, the model server possibly later.
3. `previously-mcp` runs with one replica, and its pod mounts the database connection and nothing else.
4. The readiness probe gets 200 and `ok` from `GET /healthz`, and the maintainer's `server/discover` by hand gets a `result`.
5. From the maintainer's machine, through `kubectl port-forward`, a client with its token gets an answer from the tool `whoami`, and `previously access` in the tools pod lists the call.
6. Later, stage A2: the tailnet name is in `PREVIOUSLY_MCP_ALLOWED_HOSTS`, and the same check passes through the tailnet.
7. The maintainer knows what the pod was given in memory and CPU.
