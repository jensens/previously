# MCP authorization as of 2026-10-09

Scope of these notes: how an MCP server authorizes clients under the current specification revision, which client-registration mechanism is recommended, what is forbidden, which authorization servers work, what Claude Code and Mistral Vibe actually implement, what a single-user deployment can do today, and how a server records who called a tool.

Retrieval note: every page below was retrieved on 2026-10-09 (system clock of the research session; the assignment date is 2026-10-09). Where a page carries its own date, that date is given. Material older than mid-2025 is marked as possibly outdated, because the authorization chapter changed in the 2025-03-26, 2025-06-18, 2025-11-25 and 2026-07-28 revisions.

Vocabulary used throughout: **spec MUST/SHOULD/MAY** quotes the normative text; **client reality** reports what a shipping client does; **IdP reality** reports what an authorization server does.

## Which revision is current, and what is the authorization model?

### Takeaway
The current protocol revision is `2026-07-28`; the MCP server is an OAuth 2.1 resource server that MUST publish RFC 9728 Protected Resource Metadata and MUST validate that every bearer token was issued for it (RFC 8707 audience), while the client MUST discover the authorization server through that metadata, MUST use PKCE (S256) and MUST send the `resource` parameter. Authorization as a whole is OPTIONAL, and the 2026-07-28 revision also removed protocol sessions, so authentication is strictly per request.

### Cited Findings
- "The **current** protocol version is **2026-07-28**." Revisions are Draft, Current or Final; a `draft` revision exists alongside. — [Versioning](https://modelcontextprotocol.io/specification/versioning)
- 2026-07-28 is stateless: "Every request declares the protocol version it is using via the `io.modelcontextprotocol/protocolVersion` key in its `_meta` field, and the server accepts or rejects each request independently"; `server/discover` is "a mandatory RPC that returns the server's supported protocol versions, capabilities, and identity"; handshake-based revisions (`2025-11-25` and earlier) are covered by a backward-compatibility section. — [Versioning](https://modelcontextprotocol.io/specification/versioning)
- The 2026-07-28 release post (dated 2026-07-28) lists the authorization-related SEPs merged: SEP-2468 (RFC 9207 issuer validation), SEP-837 (`application_type` for DCR), SEP-2352 (client credentials bound to the issuing AS), SEP-2575/SEP-2567 (removal of session-based state, `initialize`/`initialized` and `Mcp-Session-Id` retired), DCR "formally deprecated in favor of CIMD" with twelve months of backward compatibility, and enterprise-managed authorization moved into the extensions framework. — [The 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- "Authorization is **OPTIONAL** for MCP implementations. When supported: Implementations using an HTTP-based transport **SHOULD** conform to this specification. Implementations using an STDIO transport **SHOULD NOT** follow this specification, and instead retrieve credentials from the environment. Implementations using alternative transports **MUST** follow established security best practices for their protocol." — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Roles: "A protected *MCP server* acts as an OAuth 2.1 resource server"; "An *MCP client* acts as an OAuth 2.1 client"; the authorization server "may be hosted with the resource server or a separate entity." — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Overview requirements, verbatim: (1) "Authorization servers **MUST** implement OAuth 2.1"; (2) "Authorization servers and MCP clients **SHOULD** support OAuth Client ID Metadata Documents"; (3) "Authorization servers and MCP clients **MAY** support the OAuth 2.0 Dynamic Client Registration Protocol … Dynamic Client Registration is deprecated and retained for backwards compatibility"; (4) "MCP servers **MUST** implement OAuth 2.0 Protected Resource Metadata (RFC9728). MCP clients **MUST** use OAuth 2.0 Protected Resource Metadata for authorization server discovery"; (5) "MCP authorization servers **MUST** provide at least one of" RFC 8414 metadata or OpenID Connect Discovery, and "MCP clients **MUST** support both". — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Standards the chapter draws on: OAuth 2.1 draft-13, RFC 6750, RFC 8414, RFC 7591, RFC 8707, RFC 9728, RFC 9207, draft-ietf-oauth-client-id-metadata-document-00, OIDC Discovery 1.0, OIDC Dynamic Client Registration 1.0. — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Protected Resource Metadata: the document "**MUST** include the `authorization_servers` field containing at least one authorization server"; the server "**MUST** implement one of" (a) `WWW-Authenticate: Bearer resource_metadata="…"` on 401, or (b) a well-known URI, either path-aware (`https://example.com/.well-known/oauth-protected-resource/public/mcp`) or at the root; clients "**MUST** support both discovery mechanisms" and fall back from header to path-aware to root. — [Authorization Server Discovery 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)
- AS metadata discovery order for an issuer with a path (`https://auth.example.com/tenant1`): RFC 8414 path insertion, then OIDC path insertion, then OIDC path appending; for a path-less issuer: RFC 8414 then OIDC. After retrieval "the `issuer` value in the document **MUST** be identical to the issuer identifier used to construct the well-known URL", otherwise the client "**MUST NOT** use the metadata". — [Authorization Server Discovery 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)
- Multiple authorization servers: "Clients **MUST** maintain separate registration state (client credentials, tokens) per authorization server". — [Authorization Server Discovery 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)
- Resource indicators: "MCP clients **MUST** implement Resource Indicators for OAuth 2.0 as defined in RFC 8707"; the `resource` parameter "**MUST** be included in both authorization requests and token requests", "**MUST** identify the MCP server", "**MUST** use the canonical URI" (valid: `https://mcp.example.com/mcp`, `https://mcp.example.com:8443`; invalid: `mcp.example.com`, `https://mcp.example.com#fragment`), and "MCP clients **MUST** send this parameter regardless of whether authorization servers support it." Trailing slash: implementations "**SHOULD** consistently use the form without the trailing slash". — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Token handling on the server: "MCP servers … **MUST** validate access tokens as described in OAuth 2.1 Section 5.2. MCP servers **MUST** validate that access tokens were issued specifically for them as the intended audience, according to RFC 8707 Section 2 … Invalid or expired tokens **MUST** receive a HTTP 401 response." "MCP clients **MUST NOT** send tokens to the MCP server other than ones issued by the MCP server's authorization server." "MCP servers **MUST** only accept tokens that are valid for use with their own resources. MCP servers **MUST NOT** accept or transit any other tokens." — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Token transport: `Authorization: Bearer <access-token>`; "authorization **MUST** be included in every HTTP request from client to server"; "Access tokens **MUST NOT** be included in the URI query string". — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- PKCE: "MCP clients **MUST** implement PKCE … and **MUST** verify PKCE support before proceeding"; "**MUST** use the `S256` code challenge method when technically capable"; if `code_challenge_methods_supported` is absent from RFC 8414 metadata **or** from OIDC provider metadata, "MCP clients **MUST** refuse to proceed"; "Authorization servers providing OpenID Connect Discovery 1.0 **MUST** include `code_challenge_methods_supported`". — [Security Considerations 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)
- RFC 9207 issuer validation: clients "**MUST** record the `issuer` value" before redirecting; "MCP authorization servers **SHOULD** include the `iss` parameter in authorization responses"; servers that do "**MUST** advertise this by setting `authorization_response_iss_parameter_supported` to `true`"; the client-side table rejects a response that lacks `iss` only when the AS advertised support, compares a present `iss` by simple string comparison regardless of advertisement, and "A future revision of this specification is expected to upgrade authorization server inclusion of `iss` from **SHOULD** to **MUST**." — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization). The release post's summary describes this as "Authorization servers must return the `iss` parameter" — [The 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/); the normative text says SHOULD for the AS and MUST for client validation.
- Scopes: "MCP servers **SHOULD** include a `scope` parameter in the `WWW-Authenticate` header"; clients "**MUST** treat the scopes provided in the challenge as authoritative"; initial selection priority: the challenge's `scope`, else all of `scopes_supported`, else omit `scope`; `scopes_supported` "is intended to represent the minimal set of scopes necessary for basic functionality". — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Error codes: 401 "Authorization required or token invalid", 403 "Invalid scopes or insufficient permissions", 400 "Malformed authorization request". — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Step-up: on insufficient scope the server "**SHOULD** respond with" 403 plus `WWW-Authenticate: Bearer error="insufficient_scope", scope="…", resource_metadata="…"`; "servers **SHOULD** include all scopes required for the current operation in a single challenge"; the client computes "the union of the client's previously requested scope set and the scopes from the current challenge", re-authorizes, and retries "no more than a few times"; "Servers **MUST** account for scope hierarchies". — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Refresh tokens: clients "**MUST** keep refresh tokens confidential", "**MUST NOT** assume refresh tokens will be issued"; resource servers "**SHOULD NOT** include `offline_access` in `WWW-Authenticate` scope or … `scopes_supported`". — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Token theft: "Authorization servers **SHOULD** issue short-lived access tokens"; "For public clients, authorization servers **MUST** rotate refresh tokens". Communication security: "All authorization server endpoints **MUST** be served over HTTPS. All redirect URIs **MUST** be either `localhost` or use HTTPS." — [Security Considerations 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)
- Extensions are "Optional", "Additive", "Composable", "Versioned independently"; the list lives in the `ext-auth` repository. — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- `ext-auth` today: Stable — Enterprise-Managed Authorization; Draft — Client Credentials. — [modelcontextprotocol/ext-auth](https://github.com/modelcontextprotocol/ext-auth)
- Enterprise-Managed Authorization implements the Identity Assertion JWT Authorization Grant (draft-ietf-oauth-identity-assertion-authz-grant, built on RFC 8693 token exchange and RFC 7523): the client authenticates to an enterprise IdP, exchanges its identity assertion for an ID-JAG, presents it to the MCP server's AS, and "The issued access token **MUST** be audience-restricted to the MCP Server identified by the `resource` claim in the ID-JAG." Identifier given in the document: `urn:ietf:params:oauth:grant-profile:id-jag`. — [enterprise-managed-authorization.mdx](https://raw.githubusercontent.com/modelcontextprotocol/ext-auth/main/specification/stable/enterprise-managed-authorization.mdx); the release post names it as the `io.modelcontextprotocol/enterprise-managed-authorization` extension — [The 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Client Credentials extension (draft): machine-to-machine without a user; "Clients use JWT Authentication as defined in RFC 7523 Section 2.2" (recommended) or a client secret; the client still discovers the AS via PRM on a 401 and sends `resource` in the token request; the draft does not say how the server attributes the caller. — [oauth-client-credentials.mdx](https://raw.githubusercontent.com/modelcontextprotocol/ext-auth/main/specification/draft/oauth-client-credentials.mdx)
- The official tutorial says authorization is optional but "strongly recommended when: Your server accesses user-specific data (emails, documents, databases); You need to audit who performed which actions; …". — [Understanding Authorization in MCP](https://modelcontextprotocol.io/docs/tutorials/security/authorization)

### Inferences
- For "Previously" the spec's own triggers for using authorization (user-specific data such as emails; auditing who did what) both apply, so an HTTP deployment is in the "SHOULD conform" case, not the "optional, skip it" case.
- Because sessions are gone in 2026-07-28, there is nothing a server could lawfully tie identity to except the token on each request; an access log keyed on the per-request principal is the only design the current revision supports.
- The audience check is the one server-side MUST that a self-hosted IdP most often fails to satisfy out of the box (see the IdP section); whoever picks an AS has to verify that `aud` can be made to equal the MCP server's canonical URI.

### Gaps
- The draft revision page for authorization was fetched and read identically to 2026-07-28 for every section quoted; I did not diff the two pages line by line, so a small draft-only change could exist.
- I did not find a page that states which protocol revision Claude Code or Mistral Vibe negotiate (2025-11-25 handshake vs 2026-07-28 stateless); the backward-compatibility section implies servers must handle both.

## Client registration: DCR, CIMD, pre-registration

### Takeaway
Since 2026-07-28 the recommended mechanism is Client ID Metadata Documents (SHOULD), pre-registration is the first choice when credentials exist, and Dynamic Client Registration is formally deprecated (MAY, "retained for backwards compatibility", eligible for removal in the first revision on or after 2027-07-28). Claude Code implements all three; Mistral Vibe shows evidence of DCR only.

### Cited Findings
- Three mechanisms and the client's priority order: "1. Use pre-registered client information for the server if the client has it available 2. Use Client ID Metadata Documents if the Authorization Server indicates that it supports them (via `client_id_metadata_document_supported` …) 3. Use Dynamic Client Registration as a fallback if the Authorization Server supports it (via `registration_endpoint` …) 4. Prompt the user to enter the client information if no other option is available". — [Client Registration 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)
- CIMD: "MCP clients and authorization servers **SHOULD** support OAuth Client ID Metadata Documents"; "The `client_id` URL **MUST** use the "https" scheme and contain a path component, e.g. `https://example.com/client.json`"; the document "**MUST** include at least … `client_id`, `client_name`, `redirect_uris`"; the AS "**SHOULD** fetch metadata documents when encountering URL-formatted client_ids", "**MUST** validate that the fetched document's `client_id` matches the URL exactly", "**MUST** validate redirect URIs presented in an authorization request against those in the metadata document", "**SHOULD** cache metadata respecting HTTP cache headers". The AS advertises support with `"client_id_metadata_document_supported": true`. — [Client Registration 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)
- Example CIMD document uses `redirect_uris` of `http://127.0.0.1:3000/callback` and `http://localhost:3000/callback`, `grant_types: ["authorization_code"]`, `token_endpoint_auth_method: "none"`. — [Client Registration 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)
- Pre-registration: "MCP clients **SHOULD** support an option for static client credentials", either hard-coded or entered through a UI "after registering an OAuth client themselves". — [Client Registration 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)
- DCR: a `Warning` box reads "Dynamic Client Registration is deprecated. New implementations should use Client ID Metadata Documents instead. This option remains available for backwards compatibility". Clients "**MUST** specify an appropriate `application_type`" (native for "desktop applications, mobile apps, CLI tools, and locally-hosted web applications accessed via `localhost`"), because "Omitting it defaults to "web" under OIDC, which can conflict with native-style redirect URIs". — [Client Registration 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)
- Credentials are bound to the issuer: clients "**MUST** associate those credentials with the specific authorization server that issued them, keyed by the authorization server's `issuer` identifier" and "**MUST NOT** reuse client credentials from a different authorization server"; CIMD identifiers "are portable across authorization servers". — [Client Registration 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)
- Deprecation registry: "Dynamic Client Registration — PR #2858 — Deprecated in `2026-07-28` — Migration path: Client ID Metadata Documents — Earliest removal: First revision released on or after 2027-07-28". Also listed: HTTP+SSE transport, deprecated since 2025-03-26. — [Deprecated Features 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)
- SEP-991 "OAuth Client ID Metadata Documents for Model Context Protocol" (Paul Carleton, Aaron Parecki): created 2025-07-07, merged via PR #1296 on 2025-11-14, status Final; motivation: DCR "requires servers to maintain registration databases", CIMD lets the AS fetch metadata on demand; discussion raised localhost redirect impersonation, SSRF against the AS, and trust-policy complexity; the IETF draft was adopted by the OAuth working group in October 2025; Bluesky uses CIMD. — [SEP-991](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/991)
- CIMD security on the AS side: "**SHOULD** consider Server-Side Request Forgery (SSRF) risks"; "Client ID Metadata Documents cannot prevent `localhost` URL impersonation by themselves"; the AS "**SHOULD** display additional warnings for `localhost`-only redirect URIs", "**MAY** require additional attestation mechanisms", "**MUST** clearly display the redirect URI hostname during authorization"; "Authorization servers **MAY** implement domain-based trust policies". — [Security Considerations 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)
- The localhost impersonation attack spelled out: an attacker "Providing the legitimate client's metadata URL as their `client_id`", "Binding to any `localhost` port", and receiving the code; "The server will see the legitimate client's metadata document and the user will see the legitimate client's name". — [Security Best Practices (draft)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Client reality, Claude Code: "By default, Claude Code uses **Dynamic Client Registration** (RFC 6749)" [sic — DCR is RFC 7591]; pre-configured credentials via `claude mcp add --transport http --client-id … --client-secret --callback-port 8080 …` (secret prompted or via `MCP_CLIENT_SECRET`); `.mcp.json` `oauth` keys `clientId`, `callbackPort`, `authServerMetadataUrl`, `scopes`; "Claude Code automatically discovers and supports servers that use a **Client ID Metadata Document** instead of Dynamic Client Registration." — [Claude Code: Connect to tools via MCP](https://code.claude.com/docs/en/mcp)
- CIMD landed in Claude Code v2.1.81 (2026-03-20): "Updated MCP OAuth to support Client ID Metadata Document (CIMD / SEP-991) for servers without Dynamic Client Registration"; the docs gap was reported 2026-03-20 and closed 2026-03-28. — [anthropics/claude-code#36861](https://github.com/anthropics/claude-code/issues/36861)
- Claude Code's CIMD identifier, as observed against Keycloak: `client_id = https://claude.ai/oauth/claude-code-client-metadata`, with localhost redirect URIs, so the AS trust list must include `claude.ai`, `localhost`, `127.0.0.1` and Keycloak's "Restrict same domain" must be off (post dated 2026-09-14; third-party). — [Skycloak: Keycloak CIMD for MCP](https://skycloak.io/blog/keycloak-cimd-mcp-authorization/)
- Client reality, Mistral Vibe: the changelog records "MCP OAuth login no longer fails after the browser callback on servers that issue a client secret (e.g. Supabase)" (2.25.5) — i.e. registration returns a secret, which is DCR behaviour; no changelog or README entry mentions CIMD or a pre-registered client id. — [mistral-vibe CHANGELOG](https://raw.githubusercontent.com/mistralai/mistral-vibe/main/CHANGELOG.md); [mistral-vibe README](https://github.com/mistralai/mistral-vibe)

### Inferences
- For a self-hosted AS that both clients must reach, the AS needs either (a) CIMD plus a trust policy that admits `claude.ai` and localhost for Claude Code, **and** anonymous DCR for Vibe, or (b) anonymous DCR for both. Until Vibe ships CIMD or a pre-registered-client option, DCR cannot be switched off on the AS without losing Vibe.
- Claude Code's `--client-id` path makes pre-registration viable for a single-maintainer AS where creating one client per MCP client by hand is no burden; Vibe has no equivalent found.
- The CIMD localhost caveat is a reason to keep the AS's consent screen on (so the redirect host is visible) rather than auto-approving a trusted client.

### Gaps
- No primary source confirms whether Mistral Vibe sends `application_type: "native"` on DCR, supports CIMD, or allows a pre-registered `client_id`; a web search for "mistral-vibe" with CIMD terms returned nothing relevant.
- Claude Code's docs misquote the DCR RFC (6749 instead of 7591); whether the implementation sends `application_type` is not documented.

## What is forbidden: token passthrough, session-based authentication, confused deputy

### Takeaway
Three hard rules: the server MUST NOT accept or forward tokens not issued for it (token passthrough), MUST NOT treat a session or state handle as authentication and MUST verify every inbound request, and an MCP proxy using a static upstream client id MUST obtain per-client consent before forwarding to a third-party AS (confused deputy).

### Cited Findings
- Token passthrough: an "anti-pattern where an MCP server accepts tokens from an MCP client without validating that the tokens were properly issued *to the MCP server* and passes them through to the downstream API"; "Token passthrough is explicitly forbidden in the authorization specification"; mitigation: "MCP servers **MUST NOT** accept any tokens that were not explicitly issued for the MCP server." Risks named include "Accountability and Audit Trail Issues: The MCP Server will be unable to identify or distinguish between MCP Clients when clients are calling with an upstream-issued access token which may be opaque to the MCP Server." — [Security Best Practices (draft)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices); same text in the [2025-11-25 copy](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)
- Upstream calls: "If the MCP server makes requests to upstream APIs, it may act as an OAuth client to them. The access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server **MUST NOT** pass through the token it received from the MCP client." — [Security Considerations 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)
- Session-based auth, 2025-11-25 wording: "MCP servers that implement authorization **MUST** verify all inbound requests. MCP Servers **MUST NOT** use sessions for authentication."; "MCP servers **MUST** use secure, non-deterministic session IDs"; "MCP servers **SHOULD** bind session IDs to user-specific information … Use a key format like `<user_id>:<session_id>` … the user ID is derived from the user token and not provided by the client." — [Security Best Practices 2025-11-25](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)
- Same rule after sessions were removed (2026-07-28 / draft): "MCP is stateless and has no protocol-level sessions. Servers that need state spanning multiple requests mint an explicit handle … MCP servers that implement authorization **MUST** verify all inbound requests. MCP servers **MUST NOT** treat possession of a state handle as authentication."; "**SHOULD** bind handles server-side to the authenticated user, for example by keying stored state as `<user_id>:<handle>` where the user ID is derived from the verified token". — [Security Best Practices (draft)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Confused deputy: vulnerable when all four hold — the proxy "uses a **static client ID** with a third-party authorization server", "allows MCP clients to **dynamically register**", the third-party AS "sets a **consent cookie**", and the proxy "does not implement proper per-client consent". Mitigation: "MCP proxy servers **MUST** implement per-client consent"; "Maintain a registry of approved `client_id` values per user"; consent page "**MUST**" name the client, show scopes and the registered `redirect_uri`, use CSRF protection and `frame-ancestors`/`X-Frame-Options: DENY`; consent cookies "**MUST**" use the `__Host-` prefix, `Secure`, `HttpOnly`, `SameSite=Lax`, be signed, and bind to the `client_id`; `redirect_uri` validated by "exact string matching (not pattern matching or wildcards)"; the `state` value stored "**only after** consent has been explicitly approved", single-use, short expiry "(e.g., 10 minutes)". — [Security Best Practices (draft)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Normative one-liner: "MCP proxy servers using static client IDs **MUST** obtain user consent for each dynamically registered client before forwarding to third-party authorization servers". — [Security Considerations 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)
- Open redirection: "MCP clients **MUST** have redirect URIs registered with the authorization server. Authorization servers **MUST** validate exact redirect URIs against pre-registered values"; clients "**SHOULD** use and verify state parameters". — [Security Considerations 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)
- Mix-up attacks: RFC 9207 issuer validation "mitigates this by binding the response to the authorization server the client recorded before redirecting … PKCE alone does not prevent this attack … This mitigation depends on honest authorization servers emitting `iss`". — [Security Best Practices (draft)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- SSRF: clients fetching `resource_metadata`, `authorization_servers`, `token_endpoint` URLs "**MUST** consider SSRF risks"; "**SHOULD** require HTTPS for all OAuth-related URLs in production", "**SHOULD** block requests to private and reserved IP address ranges"; the same applies to an AS fetching CIMD documents. — [Security Best Practices (draft)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Scope minimization: common mistakes include "Publishing all possible scopes in `scopes_supported`", "Using wildcard or omnibus scopes (`*`, `all`, `full-access`)", "Treating claimed scopes in token as sufficient without server-side authorization logic"; server guidance: "Log elevation events (scope requested, granted subset) with correlation IDs". — [Security Best Practices (draft)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Tutorial pitfalls: "Don't log credentials. Never log `Authorization` headers, tokens, codes, or secrets."; "Return proper challenges. On 401, include `WWW-Authenticate` with `Bearer`, `realm`, and `resource_metadata`"; "Unauthenticated DCR means that anyone can register"; "Return generic messages to clients, but log detailed reasons with correlation IDs internally". — [Understanding Authorization in MCP](https://modelcontextprotocol.io/docs/tutorials/security/authorization)

### Inferences
- "Previously" is not an OAuth proxy to a third-party API in the sense of the confused-deputy section (its downstream is its own database and model providers called with the server's own credentials), so the consent-registry requirement does not bite unless the server ever forwards a client's token upstream — which the passthrough rule forbids anyway.
- The passthrough rule has a direct consequence for the processing policy: whatever credential the server uses towards a model provider is the server's, never the client's; the client's token identifies the human and the tool, nothing more.
- The "MUST verify all inbound requests" rule means the access log can be written in the same code path that validates the token, which removes the possibility of an unlogged authenticated request.

### Gaps
- The 2026-07-28 copy of the security best practices lives at `/docs/2026-07-28/tutorials/security/security_best_practices` (linked from the security-considerations page); I quoted the `draft` copy, whose text already speaks of "protocol version `2025-11-25` and earlier" sessions, so it post-dates 2026-07-28. I did not confirm the two are identical.

## Which authorization servers work, and what are the pitfalls?

### Takeaway
Keycloak is the best-documented self-hosted option for MCP (official MCP tutorial, Claude Code integration docs in 26.7.0, CIMD experimental since 26.6.0), but its RFC 8707 audience handling still needs an audience mapper per MCP server; Zitadel v4 has DCR (open registration must be switched on) and CIMD advertisement but ignores `resource`; Authentik only gained DCR in 2026.8; Dex has no usable (anonymous) DCR; Entra ID and Cognito lack DCR entirely; tsidp couples Tailscale identity with DCR but is experimental.

### Cited Findings
- Compatibility matrix (page dated 2026-07-28): Microsoft Entra ID — DCR no, RFC 8707 no ("Use `scope={resource}/.default`"; lacks an RFC 8414 endpoint); Amazon Cognito — DCR no; Keycloak — DCR yes, RFC 8707 no ("Cannot recognize the `resource` parameter"; use scope with audience mapper); Auth0 — DCR tenant-dependent, `resource` partial ("prioritizes `audience` when both parameters present"); Ory Hydra — DCR disabled by default, registration response carries empty `client_uri`/`logo_uri` that "may fail validation"; Zitadel — "Dynamic registration not implemented; tracking issue open since April 2025"; authentik — "Not yet shipped". — [Zuplo: MCP identity provider support](https://zuplo.com/learn/mcp/compatibility/identity-providers) (possibly stale for Zitadel and authentik, see below)
- Keycloak in the official tutorial: default `start-dev` already supports DCR, but "the default policies restrict anonymous dynamic client registration" — one must open **Clients → Client registration → Trusted Hosts**, disable "Client URIs Must Match" and add the caller's host; the audience is set with an Audience mapper on a client scope, and the tutorial warns "For production scenarios … the audience needs to be based on the resource parameter passed from the client, not a fixed value." Token validation in the example is RFC 7662 introspection with a confidential client for the MCP server. — [Understanding Authorization in MCP](https://modelcontextprotocol.io/docs/tutorials/security/authorization)
- Keycloak RFC 8707 status (post dated 2026-08-26): "Keycloak historically ignored the `resource` parameter"; the RFC 8414 well-known endpoint shipped in 26.4; "Native RFC 8707 Resource Indicators is tracked in keycloak/keycloak#14355, open since 2022 and milestoned for 26.7.0"; experimental code merged in PR #46763; workaround: one client scope per MCP server with an Audience mapper whose `included.custom.audience` equals the server identifier "byte for byte" (trailing slash or `http` vs `https` keeps the 401). — [Skycloak: Keycloak MCP server 401](https://skycloak.io/blog/keycloak-mcp-server-401-audience-rfc-8707/)
- Keycloak CIMD (post dated 2026-09-14): experimental in 26.6.0 behind `--features=cimd`; configured with a client profile using the `client-id-metadata-document` executor and a client policy with the `client-id-uri` condition; an empty trusted-domains list "means deny"; 26.6.0 also introduced experimental `resource-indicators`, which the author advises to treat "as in progress rather than available". — [Skycloak: Keycloak CIMD for MCP](https://skycloak.io/blog/keycloak-cimd-mcp-authorization/)
- Keycloak release notes: 26.5.0 "Using Keycloak as an authorization server for Model Context Protocol (MCP) servers is becoming popular"; 26.6.0 "Keycloak now includes experimental support for CIMD, allowing it to serve as an authorization server for MCP version 2025-11-25 or later"; 26.7.0 "This release adds integration documentation for Claude Code as an MCP client"; CIMD listed as Experimental. The fetched notes contained no entry on RFC 8707. — [Keycloak 26.7.0 release notes](https://www.keycloak.org/docs/26.7.0/release_notes/)
- Zitadel (docs for v4.19): DCR "is disabled by default and configured at the instance level"; the endpoint "is only served and advertised as `registration_endpoint` in the discovery document when it is enabled"; two modes — token mode (needs `project.app.register_dynamic`) and open registration with `allowUnauthenticated = true`, annotated "Required for the MCP flow"; "When open registration is enabled, protect the endpoint with the existing instance rate limiting and only allow the redirect URI schemes you trust"; "The `resource` parameter (RFC 8707) is accepted on the authorization code flow but ignored, so it does not narrow `aud`"; `private_key_jwt` is rejected; JWT tokens "carry all client IDs from the project in the `aud` claim" so servers should validate `client_id`/`azp` instead. — [Zitadel: Dynamic Client Registration](https://zitadel.com/docs/guides/integrate/dynamic-client-registration)
- Zitadel nextgen investigation (issue opened 2026-06-22, moved to Blocked 2026-08-10): PKCE works; DCR "implemented for native public clients"; CIMD "`client_id_metadata_document_supported` advertised; URL-form `client_id` accepted"; gaps: RFC 8414 metadata "returns 404; OIDC discovery fallback works for some clients but MCP spec expects RFC 8414", and audience validation "skipped (warning only)"; PR #12860 (2026-10-02) addresses SSRF for CIMD fetches. — [zitadel/nextgen#375](https://github.com/zitadel/nextgen/issues/375); Zitadel announced DCR for "Claude Desktop and other MCP clients" — [ZITADEL on X](https://x.com/zitadel/status/2090446250726285734)
- authentik 2026.8: "Applications can now use OAuth 2.0 and OpenID Connect Dynamic Client Registration (DCR) to register themselves with authentik"; "Administrators retain control through policy bindings and configurable restrictions on grant types, scope mappings, and token validity"; the release notes do not mention MCP, CIMD, RFC 8707 or RFC 9207. — [authentik Release 2026.8](https://docs.goauthentik.io/releases/2026.8/)
- Dex: PR #4988 "feat(server): add OAuth 2.0 dynamic registration (RFC 7591)" opened 2026-08-27, still open at retrieval; it will "Require an initial access token", so anonymous registration — what MCP clients do — is not possible; no mention of MCP. — [dexidp/dex#4988](https://github.com/dexidp/dex/pull/4988). Dex appears in MCP setups only as the upstream OIDC provider behind a DCR-adding proxy (HyprMCP in IBM ContextForge's tutorial). — [IBM ContextForge: DCR with HyprMCP](https://ibm.github.io/mcp-context-forge/latest/tutorials/dcr-hyprmcp/)
- tsidp: "A lightweight OIDC/OAuth server that leverages Tailscale's cryptographically guaranteed network identity"; "tsidp is an experimental project. It is under active development and might experience breaking changes"; "tsidp supports endpoints required and suggested by the MCP Authorization specification, including Dynamic Client Registration"; token exchange behind `TSIDP_ENABLE_STS=1`; identity via LocalAPI `whois`; runs on tsnet, Docker image `ghcr.io/tailscale/tsidp:latest`; page last validated 2026-03-10. — [Tailscale docs: tsidp](https://tailscale.com/docs/features/tsidp); announcement (2025-08-26, possibly outdated) lists DCR, STS token exchange and resource indicators, with Tailscale ACL grants deciding who may register clients. — [Tailscale blog: DCR for MCP](https://tailscale.com/blog/dynamic-client-registration-dcr-for-mcp-ai)
- Obot's write-up on Entra: Entra has no DCR, so MCP clients need a DCR-adding layer in front of it (secondary, undated in the search result). — [Obot: MCP DCR with Entra](https://obot.ai/blog/mcp-dynamic-client-registration-entra/)

### Inferences
- Any of Keycloak, Zitadel v4 or authentik 2026.8 can be made to work for both clients today, but each needs the operator to (a) open anonymous DCR with rate limiting and redirect-URI policy, (b) force the token audience to the MCP server's canonical URI by configuration rather than relying on `resource`, and (c) accept that the MCP-facing features are marked experimental or recent. Keycloak has the most MCP-specific documentation, including from the MCP project itself.
- Dex is not an option without a proxy, and Entra/Cognito are not options at all for a client that cannot pre-register (Vibe).
- With Zitadel the audience claim is unusable as the server-side audience check ("all client IDs from the project"), so the server would have to validate `azp`/`client_id` plus issuer instead — a weaker binding than the spec's RFC 8707 MUST.
- For a single maintainer in kup6s, each of these adds a stateful service (database, upgrades, backups); tsidp is the only one that piggybacks on an identity the maintainer may already have, at the price of experimental status and Tailscale lock-in.

### Gaps
- I could not confirm from the Keycloak 26.7.0 release notes whether native RFC 8707 shipped there; the notes fetched mention CIMD and Claude Code documentation but no resource-indicator entry. Treat "Keycloak honours `resource` natively" as unverified.
- The Zuplo matrix (2026-07-28) contradicts Zitadel's own docs on DCR; the matrix predates or ignores the Zitadel v4 feature. Zitadel's "nextgen" is a separate codebase from v4; which one a self-hoster would deploy today was not researched.
- No practitioner report was found on authentik 2026.8 with Claude Code or Vibe specifically.

## Client reality: Claude Code

### Takeaway

- Static headers: `claude mcp add --transport http <name> <url> --header "Authorization: Bearer your-token"`; in `.mcp.json` a `headers` object alongside `"type": "http"`. — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)

### Inferences
- The "headersHelper supplies Authorization → no OAuth discovery on 401" behaviour, together with the static `headers` path, means a server can run in static-token mode without publishing any OAuth metadata and Claude Code will simply retry with the helper's headers; the same entry implies that a static `Authorization` header suppresses the OAuth path, so a server cannot expect Claude Code to step up from a static token to OAuth on its own.

- No documentation page states that Claude Code sends the RFC 8707 `resource` parameter; the exact-match advice above implies it, and the Keycloak/Skycloak reports (CIMD flow succeeding with audience mappers) are consistent with it, but it is not confirmed from a primary source.

## Simple variants for one user, and how to grow into OAuth later

### Takeaway
The spec permits a server to run without OAuth (authorization is OPTIONAL) and its own security guidance endorses "require an authorization token" for HTTP servers that are not public; both clients can send a static bearer token today, Claude Code can present a client certificate, and a network boundary (Tailscale, port-forward) is outside the spec but compatible with it. The growth path to OAuth is a server-side swap of the token verifier plus publishing Protected Resource Metadata, and a client-side switch from static headers to login; the tool code and the access-log principal need not change if both are written against one `AccessToken`-shaped principal from the start.

### Cited Findings
- Spec permission: "Authorization is **OPTIONAL** for MCP implementations." and "Implementations using alternative transports **MUST** follow established security best practices for their protocol." — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Spec guidance for a non-public HTTP server: "MCP servers intending for their servers to be run locally **SHOULD** implement measures to prevent unauthorized usage … Restrict access if using an HTTP transport, such as: Require an authorization token; Use unix domain sockets or other Interprocess Communication (IPC) mechanisms with restricted access". — [Security Best Practices (draft)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Static token in Claude Code: `--header "Authorization: Bearer …"`, `headers` in `.mcp.json`, `${VAR}` expansion, `headersHelper` for rotating tokens. — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- Static token in Vibe: `auth.type = "static"` with `api_key_env`, `api_key_header`, `api_key_format`, or `headers`; CLI `--api-key-env` / `--header`. — [mistralai/mistral-vibe README](https://github.com/mistralai/mistral-vibe)
- Reference server SDK static verifier (demonstration): the Python SDK shows `KNOWN_TOKENS = {"alice-token": AccessToken(...)}` behind the same `TokenVerifier` protocol used for JWT or introspection; the SDK "automatically publishes" `/.well-known/oauth-protected-resource/mcp` and answers unauthenticated requests with 401 plus metadata pointer once `auth=` and `token_verifier=` are both passed ("Pass one without the other and `MCPServer(...)` raises a `ValueError`"). — [MCP Python SDK: Authorization](https://py.sdk.modelcontextprotocol.io/run/authorization/index.md)
- FastMCP's equivalent: `StaticTokenVerifier` ("stores tokens as plain text and should never be used in production environments"), `JWTVerifier` (JWKS, HMAC or static key), `IntrospectionTokenVerifier` (with `audience`; "a missing or malformed `aud` is rejected when `audience` is configured"), `DebugTokenVerifier` (v2.13.1, custom callable). — [FastMCP: Token verification](https://gofastmcp.com/servers/auth/token-verification)
- mTLS on the client side: Claude Code's `CLAUDE_CODE_CLIENT_CERT`/`CLAUDE_CODE_CLIENT_KEY`/`CLAUDE_CODE_CLIENT_KEY_PASSPHRASE`. — [Claude Code: Enterprise network configuration](https://code.claude.com/docs/en/network-config); a stdio-to-remote bridge "with first-class mTLS client-certificate authentication that works with Claude Code" exists as a third-party tool. — [search result: mcp-secure-remote](https://glama.ai/mcp/servers/vu7p62a927) (secondary, not evaluated)
- Network-level identity: tsidp turns Tailscale node/user identity into OIDC tokens with DCR, so the network boundary and the OAuth flow are the same thing; experimental. — [Tailscale docs: tsidp](https://tailscale.com/docs/features/tsidp)
- Client behaviour that makes the two modes coexist: Claude Code with a helper-supplied `Authorization` header does not enter OAuth discovery on a 401 but re-runs the helper (changelog), and Vibe chooses static vs OAuth by configuration, not by probing. — [Claude Code changelog](https://code.claude.com/docs/en/changelog); [mistralai/mistral-vibe README](https://github.com/mistralai/mistral-vibe)
- Spec constraint on mixing: "MCP servers **MUST** only accept tokens that are valid for use with their own resources. MCP servers **MUST NOT** accept or transit any other tokens." and clients "**MUST NOT** send tokens to the MCP server other than ones issued by the MCP server's authorization server." — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Spec requirement for the OAuth stage: PRM with `authorization_servers`, the 401 challenge with `resource_metadata` (and preferably `scope`), audience validation, 401/403 semantics. — [Authorization Server Discovery 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery); [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- The spec already foresees the single-operator case for the AS: it "may be hosted with the resource server or a separate entity." — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

### Inferences
- A static bearer token over HTTPS is spec-compatible as long as the server does not claim OAuth conformance (no PRM, no `WWW-Authenticate … resource_metadata`); the moment PRM is published, the "only tokens from our AS" MUST applies and static tokens must either disappear or be modelled as tokens minted by the server's own (co-hosted) AS.
- The cleanest growth path is therefore: (1) now — one opaque random token per client, stored hashed on the server, mapped to a principal `{subject: jens, client: claude-code | vibe, scopes: [...]}` through a `TokenVerifier`; (2) later — add an AS (Keycloak, Zitadel, authentik, or tsidp) and swap the verifier for JWT/introspection with audience = canonical server URI, publish PRM, and move clients from `headers` to `claude mcp login` / `/mcp login`. Tool handlers reading `get_access_token()` see the same object in both stages.
- mTLS adds transport-level client authentication that neither the spec nor Vibe covers; as a second factor in front of a static token it is attractive for Claude Code only, so it should not be the mechanism the access log depends on.
- A port-forward (`kubectl port-forward`) or Tailscale makes the server unreachable to strangers but gives the server no principal; it is a complement to a token, not a substitute, if the log must say *who*. tsidp is the one network-level option that also yields an OAuth identity, at the cost of an experimental component and a Tailscale dependency the compose-file host would not share.
- Because Vibe cannot add an unauthenticated remote server through its CLI (issue #1218), "no auth behind a VPN" is also the worse user experience for that client; static auth is the path of least friction for both clients.

### Gaps
- No source quantifies how many MCP deployments run static tokens versus OAuth; the recommendation against static tokens in SDK docs is about plaintext storage in the SDK's demo verifier, not about the pattern as such when tokens are stored hashed.
- No primary source confirms that Claude Code presents `CLAUDE_CODE_CLIENT_CERT` on MCP HTTP connections (see the Claude Code section).
- The spec has no text on client certificates for the HTTP transport; whether an mTLS-only server counts as "alternative transport" or as "HTTP without authorization" is not addressed anywhere I found.

## Identity in the server: recording who called a tool

### Takeaway
Under OAuth the server learns the human (`sub`), the client (`client_id`/`azp`, which under CIMD is the client's metadata URL), the scopes and the token id (`jti`) from the validated token on every request, and the SDKs expose exactly these fields to tool code via `get_access_token()`; under a static token the same fields come from the server's own token-to-principal table; under mTLS they would come from the certificate subject, which the SDKs do not surface. In all cases the spec forbids logging the token itself.

### Cited Findings
- Python SDK: `TokenVerifier.verify_token(token) -> AccessToken | None` is "the entire integration surface"; `AuthSettings` takes `issuer_url`, `resource_server_url`, `required_scopes`, `validate_token_resource`; `AccessToken` has `token`, `client_id`, `scopes`, `resource`, `expires_at`, `subject`, `claims`; inside any handler `from mcp.server.auth.middleware.auth_context import get_access_token` returns the `AccessToken` or `None` ("stdio and in-memory clients bypass authorization"). — [MCP Python SDK: Authorization](https://py.sdk.modelcontextprotocol.io/run/authorization/index.md)
- FastMCP verifiers expose `client_id`, `scopes`, `sub`, `expires_at` and the full `claims`. — [FastMCP: Token verification](https://gofastmcp.com/servers/auth/token-verification)
- The MCP tutorial's Python introspection verifier returns `subject=data.get("sub")` and `claims=data` from the RFC 7662 response; the C# variant reads `context.Principal?.Identity?.Name`. A Keycloak token in the tutorial carries `sub`, `azp`, `aud`, `jti`, `scope`, `sid`, `auth_time`. — [Understanding Authorization in MCP](https://modelcontextprotocol.io/docs/tutorials/security/authorization)
- Spec on binding state to the verified principal: key stored state as `<user_id>:<handle>` "where the user ID is derived from the verified token rather than supplied by the client". — [Security Best Practices (draft)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Spec on why passthrough destroys attribution: with upstream-issued opaque tokens "The MCP Server will be unable to identify or distinguish between MCP Clients". — [Security Best Practices (draft)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Spec on logging around scopes: "Log elevation events (scope requested, granted subset) with correlation IDs". — [Security Best Practices (draft)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Tutorial: "Never log `Authorization` headers, tokens, codes, or secrets. Scrub query strings and headers. Redact sensitive fields in structured logs." and "log detailed reasons with correlation IDs internally". — [Understanding Authorization in MCP](https://modelcontextprotocol.io/docs/tutorials/security/authorization)
- CIMD makes the client identity a URL: Claude Code presents `https://claude.ai/oauth/claude-code-client-metadata` as `client_id` (third-party observation). — [Skycloak: Keycloak CIMD for MCP](https://skycloak.io/blog/keycloak-cimd-mcp-authorization/)
- Zitadel caveat: its JWTs put every client id of the project into `aud`, so the client identity must be read from `client_id`/`azp`. — [Zitadel: Dynamic Client Registration](https://zitadel.com/docs/guides/integrate/dynamic-client-registration)
- Enterprise-managed authorization binds the token to the `resource` claim of the ID-JAG, i.e. the enterprise user identity is carried through to the MCP server's token. — [enterprise-managed-authorization.mdx](https://raw.githubusercontent.com/modelcontextprotocol/ext-auth/main/specification/stable/enterprise-managed-authorization.mdx)
- The client-credentials draft does not define caller attribution beyond the token. — [oauth-client-credentials.mdx](https://raw.githubusercontent.com/modelcontextprotocol/ext-auth/main/specification/draft/oauth-client-credentials.mdx)

### Inferences
- A log record that answers "what did Claude ever see about customer X" needs, per tool call: timestamp, `subject`, `client_id`, token identifier (`jti` or a hash of the static token id — never the token), tool name, the customer references the tool resolved, and a request correlation id; every field but the customer references is available from `get_access_token()` in both the static and the OAuth stage.
- Under a static token the server, not an AS, is the authority for `subject` and `client_id`; the table that maps token hashes to principals is therefore part of the audit trail and should be versioned like the policy.
- Under DCR with a self-hosted AS the `client_id` is an opaque string the AS invented at registration; keeping the registration record (client name, redirect URIs, registration time) is what makes a later log entry readable. CIMD avoids that by making the id self-describing.
- Because 2026-07-28 removed sessions, `sid`-style session correlation in the log is not available from the protocol; correlation has to be per request (or per task, if the Tasks extension is used).

### Gaps
- Neither SDK documents a hook for mTLS client-certificate identity; a server wanting it would read the certificate from the ASGI scope or a reverse-proxy header, which was not researched.
- No source was found that prescribes a log schema for MCP access logs; the fields above are inferred from the token claims and the spec's logging remarks.

## Options for "Previously": single user now, more later

### Takeaway
Four defensible designs exist; the one that costs least now and least to change later is a static per-client bearer token behind HTTPS with a principal abstraction that an OAuth verifier can replace, with the AS decision deferred until Vibe supports CIMD or pre-registration or until a second human user appears.

### Cited Findings
- Spec: authorization OPTIONAL; AS may be co-hosted; servers MUST validate audience once OAuth is used; DCR deprecated with twelve-month minimum support. — [Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); [Deprecated Features](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)
- Tutorial: authorization "strongly recommended" for email data and for auditing. — [Understanding Authorization in MCP](https://modelcontextprotocol.io/docs/tutorials/security/authorization)
- Client capabilities: Claude Code — static headers, helper, OAuth with DCR/CIMD/pre-registration, mTLS env vars; Vibe — static auth block or OAuth with DCR-style registration, no CIMD/pre-registration found. — [Claude Code: MCP](https://code.claude.com/docs/en/mcp); [mistralai/mistral-vibe README](https://github.com/mistralai/mistral-vibe); [mistral-vibe CHANGELOG](https://raw.githubusercontent.com/mistralai/mistral-vibe/main/CHANGELOG.md)
- IdP state: Keycloak (DCR, experimental CIMD 26.6, audience by mapper), Zitadel v4 (DCR opt-in, ignores `resource`), authentik 2026.8 (DCR new), Dex (no anonymous DCR), tsidp (experimental). — see the IdP section's sources.
- SDK: one `TokenVerifier` protocol serves static, JWT and introspection verifiers; `get_access_token()` is transport-independent for HTTP. — [MCP Python SDK: Authorization](https://py.sdk.modelcontextprotocol.io/run/authorization/index.md)

### Inferences
- **Option A — static bearer token per client, HTTPS, hashed on the server, principal table.** For: works with both clients today (`--header` / `auth.type="static"`), no new stateful service in kup6s, trivially described for a compose file, full attribution via the principal table, swap-able for OAuth without touching tools. Against: no scopes/step-up, token rotation is manual (Claude Code's `headersHelper` can fetch a rotated token; Vibe reads an environment variable at start), the server is not spec-conformant in the OAuth sense and must not publish PRM while in this mode, and a leaked long-lived token is a full credential until rotated — short lifetimes and a kill switch (delete the row) are the mitigations.
- **Option B — self-hosted AS from day one (Keycloak, Zitadel v4, authentik 2026.8).** For: spec-conformant, step-up and scopes per tool class, identity from an IdP that can later hold several users, enterprise extension path. Against: one more database-backed service to run, back up and upgrade in kup6s and in a compose file; anonymous DCR must stay open on the internet for Vibe (rate limit, redirect-URI policy); audience binding needs manual mapper configuration on Keycloak and is unavailable on Zitadel; the MCP-relevant features are marked experimental in Keycloak; for one user the consent and login flows add friction with no security gain over A.
- **Option C — Tailscale + tsidp.** For: identity for free from the tailnet, DCR supported, no public endpoint. Against: experimental and may break; ties "Previously" to Tailscale for anyone else running it with compose; identity is the tailnet user, not a project-controlled principal.
- **Option D — AS co-hosted in the MCP server.** For: spec explicitly allows it; no extra service; the server can mint its own short-lived tokens for both clients via DCR/CIMD and still be conformant, which closes the gap of option A. Against: writing an AS is the thing the spec's confused-deputy, open-redirect, PKCE and CIMD-SSRF sections are warning about; the Python SDK v2 docs describe the server as one that "never issues" tokens, so this means an additional library or a FastMCP-style provider, which was not researched here.
- Recommended sequencing from the evidence: A now, designed so that B or D is a verifier swap; revisit when (i) Vibe gains CIMD or `--client-id`, (ii) Keycloak's native RFC 8707 is confirmed shipped, or (iii) a second person needs access. The access-log schema should be fixed in A already, with `subject`, `client_id`, token id, tool, customer references and correlation id, because that schema is what both later options have to keep.
- Counter-argument to the recommendation: if the pilot customer or an auditor expects "OAuth" as a checkbox, A will read as a shortcut even though it is the spec's own advice for a non-public HTTP server; the written design should quote the OPTIONAL clause and the "require an authorization token" guidance so the choice is visibly deliberate rather than an omission.

### Gaps
- Not researched: FastMCP or other libraries that embed an AS (option D), and their security track record.
- Not researched: Kubernetes-native ways to inject a rotating static token into a workstation client (e.g. via `headersHelper` reading a secret) — a how-to question rather than a design one.
