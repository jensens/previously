# Designing the three MCP server primitives (tools, resources, prompts) — state as of 2026-10-09

Reading guide for the report writer:

- **Spec requires / recommends** = quoted RFC-2119 wording from modelcontextprotocol.io. The **current** revision is **2026-07-28** (not 2025-11-25). Where a page was only fetched in its 2025-11-25 form (completion, pagination) this is flagged.
- **Vendor documentation** (Anthropic engineering, Claude Code docs, Mistral docs, GitHub/Sentry/Notion/Amplitude/Linear) is reported with author and date.
- **Community opinion / blogs** are reported with author and date where available, and marked "undated" otherwise. Anything older than ~12 months is marked **(possibly outdated)**.
- Dates: today is 2026-10-09/10. The field moves fast; the spec took a breaking revision on 2026-07-28, and several client behaviours changed in 2026.

## Q0. Which specification is current, and what changed in 2026-07-28 that affects primitive design?

### Takeaway
The current MCP revision is **2026-07-28**; it made the protocol stateless (no sessions, no initialize handshake), replaced server-initiated elicitation with the Multi Round-Trip Request (MRTR) pattern, replaced `resources/subscribe` with `subscriptions/listen`, added mandatory cache hints on list/read results, deprecated Roots, Sampling and Logging, and asked servers to carry cross-call state as explicit handles in tool arguments. Anything designed against 2025-11-25 needs re-checking against these points.

### Cited Findings
- "The **current** protocol version is **2026-07-28**." Revisions are marked Draft, Current or Final; features can additionally be Deprecated (minimum twelve-month window) and later Removed. — [Versioning](https://modelcontextprotocol.io/specification/versioning) (2026-07-28 spec)
- Every request now carries its protocol version in `_meta` (`io.modelcontextprotocol/protocolVersion`); `server/discover` is "a mandatory RPC that returns the server's supported protocol versions, capabilities, and identity in a single request". Calling it is optional for clients. — [Versioning](https://modelcontextprotocol.io/specification/versioning)
- Major changes vs 2025-11-25: (1) "Remove protocol-level sessions and the `Mcp-Session-Id` header … Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments (SEP-2567)"; (2) "Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake" (SEP-2575); (4) "Replace the HTTP GET endpoint and `resources/subscribe`/`resources/unsubscribe` with `subscriptions/listen`"; (5) "Remove `ping`, `logging/setLevel`, and `notifications/roots/list_changed`"; (6) tasks moved to an official extension `io.modelcontextprotocol/tasks` (SEP-2663); (7) MRTR "replaces the previous approach of sending server-initiated requests, such as `roots/list`, `sampling/createMessage`, or `elicitation/create`" (SEP-2322); (8) all results carry a required `resultType` (`"complete"` or `"input_required"`). — [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Minor changes: "Servers **SHOULD** return tools from `tools/list` in a deterministic order to enable client-side caching and improve LLM prompt cache hit rates"; "Require `ttlMs` and `cacheScope` fields on results returned by `tools/list`, `prompts/list`, `resources/list`, `resources/read`, and `resources/templates/list`" (SEP-2549); "Change resource not found error code from `-32002` to `-32602`"; "Loosen `inputSchema` and `outputSchema` to allow any JSON Schema 2020-12 keywords, and `structuredContent` to allow any JSON value" (SEP-2106); removal of `notifications/elicitation/complete` and `elicitationId`; error-code allocation policy (`-32020`…`-32099` reserved for the spec). — [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Deprecated in 2026-07-28: Roots, Sampling, Logging (SEP-2577; earliest removal "First revision released on or after 2027-07-28"), Dynamic Client Registration; suggested migrations: "pass directories or files via tool parameters, resource URIs, or server configuration instead of Roots; integrate directly with LLM provider APIs instead of Sampling; log to `stderr` (stdio) or use OpenTelemetry instead of Logging." — [Deprecated features registry](https://modelcontextprotocol.io/specification/2026-07-28/deprecated); [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Claude Code note on the new revision: "v2 Runtime: Servers on MCP protocol revision 2026-07-28 cannot deliver channel messages" (channels are Claude Code's own push feature, not a spec primitive). — [Claude Code: Connect to tools via MCP](https://code.claude.com/docs/en/mcp) (fetched 2026-10-09)

### Inferences
- A server written today should target 2026-07-28 but keep the 2025-11-25 handshake path for clients that have not moved (the spec's "Backward Compatibility" section exists for exactly this); Mistral Vibe's protocol version is undocumented (see Q1 gaps).
- "No sessions" means a knowledge-store server must not keep a per-connection "current project" — the project must be an argument (or part of a resource URI) on every call.

### Gaps
- The 2026-07-28 pages for completion and pagination were not fetched; the 2025-11-25 versions are reported below and the caching page (2026-07-28) was used to fill in what changed for pagination.

## Q1. Tools vs resources vs prompts: control model, and how real clients surface each

### Takeaway
The spec is explicit: tools are **model-controlled**, resources **application-driven**, prompts **user-controlled** — "who decides when", not who authors. Claude Code surfaces all three (tools as `mcp__server__tool`, prompts as `/mcp__server__prompt` commands, resources via `@` mentions per secondary sources), while Mistral Vibe's documentation describes **tools only** (`{server}_{tool}`), with no mention of resources, prompts or elicitation.

### Cited Findings
**What the spec says**
- Tools "are designed to be **model-controlled**, meaning that the language model can discover and invoke tools automatically". Warning: "there **SHOULD** always be a human in the loop with the ability to deny tool invocations"; applications **SHOULD** show which tools are exposed, indicate invocations, and "Present confirmation prompts to the user for operations". — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Resources "are designed to be **application-driven**, with host applications determining how to incorporate context based on their needs" — e.g. tree/list pickers, search/filter, "automatic context inclusion, based on heuristics or the AI model's selection". — [Resources 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- Prompts "are designed to be **user-controlled** … This refers to who decides when the prompt is used, not who authors its content. Prompt content is defined by the server." Example given: slash commands. — [Prompts 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts)
- Official concept page table: Tools — "Functions that your LLM can actively call" (controlled by Model); Resources — "Passive data sources that provide read-only access to information for context" (Application); Prompts — "Pre-built instruction templates that tell the model to work with specific tools and resources" (User). Prompts "allow MCP server authors to provide parameterized prompts for a domain, or showcase how to best use the MCP server." UI patterns listed for prompts: slash commands, command palettes, buttons, context menus. — [Understanding MCP servers](https://modelcontextprotocol.io/docs/learn/server-concepts)
- All three list operations **MUST NOT** vary per-connection, but **MAY** vary by the authorization presented on the request ("returning only the tools the caller's granted scopes permit — since credentials are per-request input, not connection state"). Same wording for resources and prompts. — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [Resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources), [Prompts](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts)

**Claude Code (vendor docs, fetched 2026-10-09)**
- Tool naming: "`mcp__server__tool` (e.g., `mcp__database__query`)"; plugin-bundled tools `mcp__plugin_<plugin>_<server>__<tool>`. Tools can be set per connector to `ask` or `blocked` by an organisation. Tool search "Enabled by default on Claude 4.5+" defers MCP tool discovery; `ENABLE_TOOL_SEARCH=false` disables. — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- The current MCP page did not yield the "Use MCP resources"/"Use MCP prompts as commands" sections to two fetch attempts (see Gaps). Indirect official evidence that prompts become commands: "An MCP server named `anthropic-skills`: it connects and its tools work, but **its prompts don't appear as commands**. Rename the server in your MCP configuration to list them." — [Claude Code: Slash commands](https://code.claude.com/docs/en/slash-commands)
- Secondary sources (search snippets, 2025–2026) describe the surfaces: resources referenced "with @ in your prompt, such as `@github:issue://123`", with autocomplete on `@`; prompts "appear using a naming pattern like `/mcp__servername__promptname`", e.g. `/mcp__github__pr_review 456` with space-separated arguments. — [mcpbundles: Claude Code MCP commands](https://docs.mcpbundles.com/blog/claude-code-mcp-tools) (undated); [Towards AI: MCP prompts in Claude Code](https://pub.towardsai.net/mcp-prompts-in-claude-code-a-simple-guide-for-developers-2b7a8063f616) (undated; **possibly outdated**)
- Claude Code responds to elicitation: "A call waiting on an open elicitation dialog isn't backgrounded while the dialog is open; the server is blocked on your input". Claude Code handles `list_changed` notifications and refreshes tools/prompts/resources on reconnect. — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)

**Mistral Vibe (vendor docs, fetched 2026-10-09)**
- MCP servers are configured as `[[mcp_servers]]` tables in `config.toml`; transports `http`, `streamable-http`, `stdio`; tools are named "`{server_name}_{tool_name}`" and listed via the `/mcp` CLI command; per-tool permissions `"always"` / `"ask"`; `enabled_tools`/`disabled_tools` accept exact names, globs and `re:` regex; "The CLI does not yet support MCP servers that require OAuth authentication." The page "makes no mention of resources, prompts, elicitation, or slash commands from MCP servers. Only tools are referenced." — [Mistral Vibe: MCP servers](https://docs.mistral.ai/vibe/code/cli/mcp-servers)
- Configuration overview shows `disabled_tools = ["mcp_*", "grep"]` as the filter idiom. — [Mistral Vibe: Configuration](https://docs.mistral.ai/mistral-vibe/terminal/configuration)

**Community observation on adoption**
- "Audit any public MCP catalog and the pattern is consistent: dozens of tools per server, zero prompts, zero resources, no sampling support." Also: resources — "not every client does" support them; sampling — "almost no client supports". — [Archestra: underused MCP primitives](https://archestra.ai/blog/underused-mcp-primitives) (Mack Chi, undated; opinion, no data given)

### Inferences
- For a server that must serve Claude Code **and** Mistral Vibe equally, **tools are the only primitive guaranteed to reach both**. Resources and prompts are a Claude-Code-side enhancement until Vibe documents support; nothing in Vibe's docs says they are rejected, only that they are not mentioned.
- Because list results may vary by per-request authorization but not by connection, a gate that decides "what a model may see" belongs in the per-request authorization path (token scopes → filtered `tools/list`/`resources/list`/results), not in session state.

### Gaps
- Could not retrieve the current official Claude Code wording for `@server:resource` mentions and `/mcp__server__prompt` commands; the syntax above rests on secondary sources plus the slash-commands page's indirect statement.
- The former client feature-support matrix at modelcontextprotocol.io/clients now redirects to the intro page; only an *extensions* matrix exists ([Extension support matrix](https://modelcontextprotocol.io/extensions/client-matrix.md)). No authoritative table of which clients implement resources/prompts/elicitation was found.
- Mistral Vibe's docs state no MCP protocol version and nothing about resources, prompts or elicitation; whether Vibe silently ignores or errors on a server that declares `resources`/`prompts` capabilities is unknown.

## Q2. Resources: URI schemes, templates, resource links, embedded resources, subscriptions, list-changed, size, MIME types, annotations

### Takeaway
Resources are URI-identified, read-only context with optional `size`/`mimeType`, RFC 6570 templates with completion, and `audience`/`priority`/`lastModified` annotations; in 2026-07-28 per-resource subscriptions ride on `subscriptions/listen`, reads carry cache hints, and "not found" is `-32602`. The spec sets **no size limit** on resources; the only documented limits are client-side and apply to tool results.

### Cited Findings
- Resource fields: `uri`, `name`, `title` (optional, display), `description`, `icons`, `mimeType` (optional), `size` ("Optional size in bytes"). Contents are either `text` or base64 `blob`. — [Resources 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- Capabilities: `listChanged` and `subscribe` are independent and optional; `subscribe` now means "the server supports resource-specific update notifications for resources requested through subscriptions/listen using the resourceSubscriptions filter". — [Resources 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- `resources/read`: "Servers **MAY** return multiple resource contents in response to a single `resources/read` request. For example, a server could return the contents of several files when a directory resource is read." `resources/read` may also return an `InputRequiredResult` (MRTR). "if the scheme of `uri` is `https://`, clients may fetch the resource directly from the web." — [Resources 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- Templates: "Resource templates allow servers to expose parameterized resources using URI templates (RFC 6570). Arguments may be auto-completed through the completion API." `resources/templates/list` supports pagination and caching. — [Resources 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- URI schemes: `https://` — "Servers **SHOULD** use this scheme only when the client is able to fetch and load the resource directly from the web on its own … For other use cases, servers **SHOULD** prefer to use another URI scheme, or define a custom one". `file://` — "resources do not need to map to an actual physical filesystem"; may use XDG MIME types like `inode/directory`. `git://` listed. "Custom URI schemes **MUST** be in accordance with RFC3986". — [Resources 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- Annotations (on resources, templates and content blocks): `audience` (`"user"`/`"assistant"`), `priority` 0.0–1.0 ("1 means 'most important' (effectively required), while 0 means 'least important' (entirely optional)"), `lastModified` ISO 8601. Clients can "Filter resources based on their intended audience; Prioritize which resources to include in context; Display modification times or sort by recency". — [Resources 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- Errors: "If the requested resource does not exist, servers **MUST** return a JSON-RPC error with code `-32602`"; clients **SHOULD** also accept `-32002` from older servers; "Servers **MUST NOT** return an empty `contents` array for a non-existent resource." — [Resources 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- Security: "Servers **MUST** validate all resource URIs"; "Access controls **SHOULD** be implemented for sensitive resources"; "Servers **MUST** sanitize file paths to prevent directory traversal attacks when serving `file://` resources". — [Resources 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- Subscriptions (2026-07-28): `subscriptions/listen` opens a long-lived stream; filter fields `toolsListChanged`, `promptsListChanged`, `resourcesListChanged` (booleans) and `resourceSubscriptions` (`string[]` of URIs). "The server **MUST NOT** send notification types the client has not explicitly requested." Server **MUST** acknowledge first with `notifications/subscriptions/acknowledged`. "On **stdio**, if the connection is terminated and then re-established, the client **MUST** re-send `subscriptions/listen` … the server holds no subscription state across reconnections." — [Subscriptions 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions.md)
- Caching (2026-07-28): "Servers MUST include caching hints on results with `resultType: "complete"` returned by … `resources/list`, `resources/templates/list`, `resources/read`" (and tools/prompts lists, `server/discover`). `ttlMs` is "a freshness hint, not a guarantee"; `ttlMs: 0` = immediately stale; `cacheScope` `"public"`/`"private"` — "`"private"` is appropriate for `resources/read` results that depend on the authenticated user". A `list_changed` notification "invalidates the cached response". — [Caching 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching)
- Resource links in tool results: "A tool **MAY** return links to Resources … the tool will return a URI that can be subscribed to or fetched by the client"; "Resource links returned by tools are not guaranteed to appear in the results of a `resources/list` request." Embedded resources: "Servers that use embedded resources **SHOULD** implement the `resources` capability". Resource links are also allowed in **prompt** messages. — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); [Prompts 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts)
- Concept-page examples of resource templates: `travel://activities/{city}/{category}`, `weather://forecast/{city}/{date}`; direct resource `calendar://events/2024`; "Resource Templates include metadata such as title, description, and expected MIME type, making them discoverable and self-documenting." — [Understanding MCP servers](https://modelcontextprotocol.io/docs/learn/server-concepts)
- Client-side limits that bite resource-shaped data when it travels through **tools**: Claude Code warns at 10,000 tokens, truncates at 25,000 tokens by default (`MAX_MCP_OUTPUT_TOKENS`); a tool may raise its own limit with `_meta["anthropic/maxResultSizeChars"]` (ceiling 500,000 characters); HTTP/SSE responses capped at 16 MB after decompression. — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- Community argument for resources over read-tools: a `get_user_by_id` or `read_file` tool "burns a tool slot, eats schema tokens, and forces the model to decide on a read it should never have been deciding on"; "In a Postgres server, rows are resources. In a Jira server, tickets are resources." — [Archestra: underused MCP primitives](https://archestra.ai/blog/underused-mcp-primitives) (Mack Chi, undated; opinion)

### Inferences
- A custom scheme such as `previously://…` is spec-conformant (RFC 3986) and preferred over `https://` unless the client can fetch it directly without the server.
- `audience: ["user"]` on raw customer content (e-mails) and `audience: ["assistant"]` on gate-approved derived text is the only in-protocol lever for the "what a model may see" distinction — but it is a *hint* and the gate must still enforce it server-side.
- `lastModified` maps naturally onto an append-only chain (time of the last appended event); `ttlMs` can be long for immutable events and short for the chronicle head.
- Because resource links from tools need not appear in `resources/list`, a `search` tool can return `resource_link`s to events without the server having to enumerate every event in `resources/list`.

### Gaps
- No spec-level or Claude Code-documented size limit for `resources/read` was found; whether Claude Code applies the 25,000-token tool limit to `@`-mentioned resources is undocumented.
- No evidence found on whether Claude Code or Mistral Vibe honour `audience`/`priority` annotations in practice.

## Q3. Prompts: arguments, completion (`completion/complete`), when prompts are worth it, examples

### Takeaway
Prompts are named templates with flat string arguments (`name`, `description`, `required`), resolved by `prompts/get` into user/assistant messages that may embed or link resources; argument values can be auto-completed (`completion/complete`, max 100 suggestions, with `context.arguments` for dependent arguments). The spec positions them as the server author's "opinion about how to use the server"; practitioners call them cheap and underused, but only clients that expose them (Claude Code does, Vibe does not document them) benefit.

### Cited Findings
- Prompt definition: `name`, `title`, `description`, `icons`, `arguments` (list; each with `name`, `description`, `required`). `prompts/get` takes `name` and string `arguments` and returns `description` plus `messages` (`role` user/assistant; content text, image, audio, resource_link, embedded resource). "Resources can contain either text or binary (blob) data and **MUST** include: A valid resource URI, The appropriate MIME type, Either text content or base64-encoded blob data". — [Prompts 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts)
- `prompts/get` may return `InputRequiredResult` (MRTR) when it needs more input. Errors: invalid name / missing required args → `-32602`. "Servers **SHOULD** validate prompt arguments before processing". "Implementations **MUST** carefully validate all prompt inputs and outputs to prevent injection attacks". — [Prompts 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts)
- Completion (2025-11-25 page; **assumed unchanged**): capability `completions`; request `ref` is `ref/prompt` (by name) or `ref/resource` (by URI template), `argument {name, value}`, optional `context.arguments` "A mapping of already-resolved argument names to their values"; response `values` ("max 100"), optional `total`, `hasMore`. Servers **SHOULD** "Return suggestions sorted by relevance; Implement fuzzy matching where appropriate; Rate limit completion requests"; clients **SHOULD** debounce. Security: "Prevent completion-based information disclosure". — [Completion 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/utilities/completion)
- Concept page: prompts "allow MCP server authors to provide parameterized prompts for a domain, or showcase how to best use the MCP server"; "Prompts can be context-aware, referencing available resources and tools to create comprehensive workflows"; example `plan-vacation` with arguments destination/duration/budget/interests; the worked flow is: user invokes prompt → user selects resources → model uses tools. — [Understanding MCP servers](https://modelcontextprotocol.io/docs/learn/server-concepts)
- Example of a shipping server with prompts: the `mistral-mcp` community server exposes 22 tools, 2 resources (`mistral://models`, `mistral://voices`) and 6 prompts (`french_invoice_reminder`, `french_meeting_minutes`, `french_email_reply`, `french_commit_message`, `french_legal_summary`, `codestral_review`). — [glama: mistral-mcp](https://glama.ai/mcp/servers/Swih/mistral-mcp) (community server listing)
- Opinion: "A prompt is a template a user invokes on purpose. The user types /summarize_quarterly_review, the server expands it into a structured message, the model runs it. Prompts are how a server author ships an opinion about how their own data should be used." "Shipping those as MCP prompts is two hours of work and it doubles how useful the server feels." — [Archestra: underused MCP primitives](https://archestra.ai/blog/underused-mcp-primitives) (Mack Chi, undated)
- Opinion: prompts fit "when the task requires summarization, prioritization, or natural language reasoning, and when the assistant should express user intent declaratively rather than procedurally"; "prompts are passive: they return a text string when called". — [Composio: prompts, resources and tools in MCP](https://composio.dev/content/how-to-effectively-use-prompts-resources-and-tools-in-mcp) (undated; **possibly outdated**)
- Claude Code exposes server prompts as commands (indirect evidence, Q1). — [Claude Code: Slash commands](https://code.claude.com/docs/en/slash-commands)

### Inferences
- Prompt arguments are strings only; richer input belongs in elicitation (form mode) or in the prompt text. Completion on a `project` argument is the natural place to offer the list of a user's projects without the model spending a tool call.
- A prompt can pre-load a resource (embedded or linked) *and* instruct which tools to use next — this is the spec's intended way to ship a workflow ("status of project X", "triage the inbox") without adding a tool.

### Gaps
- No systematic data on prompt adoption or on how often users invoke MCP prompts in Claude Code; only opinion.
- No published examples from the "well-regarded" servers (GitHub, Linear, Sentry, Notion) of server prompts were found; GitHub's README mentions none.

## Q4. Tools: names, descriptions, input schema, `outputSchema`/`structuredContent`, annotations, `title`, icons

### Takeaway
Names SHOULD be 1–128 chars from `[A-Za-z0-9_.-]`, case-sensitive and unique per server (clients prefix for disambiguation); `structuredContent` MUST conform to `outputSchema` when one is declared and SHOULD be accompanied by serialized text; the four behaviour hints are untrusted hints, used by Codex for approval and concurrency but ignored by Claude Code's permission engine (as of Aug 2026). Anthropic's and practitioners' consensus: write descriptions "as if explaining to a new hire", use unambiguous parameter names, and keep outputs legible rather than raw API payloads.

### Cited Findings
**Spec (2026-07-28)**
- Tool fields: `name`, `title` ("Optional human-readable name of the tool for display purposes"), `description`, `icons`, `inputSchema` ("**MUST** be a valid JSON Schema object (not `null`)"; defaults to 2020-12; for no parameters `{ "type": "object", "additionalProperties": false }` is "**Recommended**"), `outputSchema`, `annotations`. Properties **MAY** carry `x-mcp-header`. — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Names: "**SHOULD** be between 1 and 128 characters", "**SHOULD** be considered case-sensitive", allowed characters "uppercase and lowercase ASCII letters (A-Z, a-z), digits (0-9), underscore (_), hyphen (-), and dot (.)", "**SHOULD NOT** contain spaces, commas", "**SHOULD** be unique within a server"; examples `getUser`, `DATA_EXPORT_v2`, `admin.tools.list`. Aggregating clients "**SHOULD** implement a disambiguation strategy such as prefixing tool names with a server identifier"; server `name` "**SHOULD NOT** be relied upon for disambiguation". — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Structured content: "can be any JSON value … that conforms to the tool's `outputSchema` if one is defined. For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block." If an output schema is provided: "Servers **MUST** provide structured results that conform to this schema. Clients **SHOULD** validate structured results against this schema." The array-output example pairs `structuredContent` (an array) with a *summarising* text block ("Found 2 users: Alice … and Bob …"), not a JSON dump. — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Annotations trust: "clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers." — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- The four hints (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) have been in the spec since 2025-03-26. — [azukiazusa: MCP tool annotations](https://azukiazusa.dev/en/blog/mcp-tool-annotations) (secondary; the fetched 2026-07-28 tools page lists `annotations` but the annotation table itself was not in the extracted text — see Gaps)
- Stateful tools (non-normative): "return an explicit handle from a creation tool and accept that handle as an argument on subsequent calls"; handles should be opaque, authorised on every call, have a stated lifetime in the creation tool's description, and "A call against an expired or unknown handle should return a tool execution error that says so". — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Security: servers **MUST** "Validate all tool inputs; Implement proper access controls; Rate limit tool invocations; Sanitize tool outputs"; clients **SHOULD** "Prompt for user confirmation on sensitive operations; Show tool inputs to the user before calling the server". — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

**Anthropic (vendor guidance)**
- Descriptions: write "as if explaining your tool to a new hire"; make implicit context explicit; use unambiguous parameter names (`user_id` not `user`); "Small refinements to tool descriptions can yield dramatic improvements" (Claude Sonnet 3.5 reached SWE-bench Verified SOTA after description refinements). Namespacing: prefixes by service (`asana_search`) or by resource (`asana_projects_search`); choice of prefix vs suffix has "non-trivial effects". Return semantic identifiers over UUIDs; omit `uuid`, `256px_image_url`, `mime_type`-style fields; offer a `response_format` enum (`detailed` vs `concise`; Slack example 206 vs 72 tokens). — [Anthropic: Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Ken Aizawa, 2025-09-11; **possibly outdated** in details, still Anthropic's reference post)
- Tool use examples (sample calls attached to tool definitions) improved accuracy "from 72% to 90% on complex parameter handling" in internal testing. — [Anthropic: Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use) (2025-11-24)
- Claude Code recognises Anthropic-specific `_meta` keys on tools: `anthropic/maxResultSizeChars` (per-tool output ceiling, up to 500,000 chars) and `anthropic/requiresUserInteraction`. — [Claude Code: MCP](https://code.claude.com/docs/en/mcp); [Claude Code issue #87452](https://claudeissues.com/issue/87452-feature-permission-engine-should-process-mcp-toolannotations-hints-readonlyhint) (2026-08-17)

**How clients use annotations**
- Claude Code: feature request (2026-08-17, closed "not planned") states "Claude Code doesn't read or act on any of these; it only recognizes its own Anthropic-specific `_meta` fields", so "a read-only lookup … and a destructive write … get identical prompting behavior". — [Claude Code issue #87452](https://claudeissues.com/issue/87452-feature-permission-engine-should-process-mcp-toolannotations-hints-readonlyhint)
- Codex CLI: `readOnlyHint: true` tools "may be auto-approved under permissive approval policies"; `destructiveHint: true` → "approval is _always_ required, regardless of other hints"; `openWorldHint` "may trigger additional scrutiny". Same author claims Claude Code uses "classifier-based risk assessment" instead. — [Daniel Vaughan: MCP tool annotations as risk vocabulary in Codex CLI](https://codex.danielvaughan.com/2026/04/12/mcp-tool-annotations-risk-vocabulary-codex-cli/) (2026-04-12, updated 2026-10-09; blog)
- Codex CLI v0.134.0 dispatches `readOnlyHint: true` tools concurrently and serialises the rest; the post repeats a third-party claim that "Claude Code uses `readOnlyHint` to determine parallelism, dispatching read-only tools at roughly double the rate", citing MCPBlog.dev (2026-03-13) — **unverified chain**. — [Daniel Vaughan: readOnlyHint concurrency](https://codex.danielvaughan.com/2026/05/27/codex-cli-mcp-readonlyhint-concurrent-tool-execution-annotations-parallelism/) (2026-05-27)
- GitHub's lead: annotations are "underused"; marking tools read-only/destructive/open-internet "lets agent harnesses intercept calls and prompt users before execution". GitHub filters tools by token scope: a read-only PAT "shows only 20 read-only tools; more privileged tokens unlock 40+". — [Arcade: lessons from GitHub's MCP server](https://www.arcade.dev/blog/enterprise-mcp-lessons-from-githubs-mcp-server-launch) (Sam Morrow, 2026-03-03)
- Sentry's contributor rules: "**REQUIRED**: Every tool must declare `readOnlyHint`, `destructiveHint`, and …" (line 102); "Format output as user-facing markdown, not raw upstream API payloads." (line 197). — [sentry-mcp docs/contributing/adding-tools.md](https://github.com/getsentry/sentry-mcp/blob/main/docs/contributing/adding-tools.md) (fetched 2026-10-09)
- Sentry on structured content: "Markdown-only tools (for example issue and trace details today) should return markdown and omit `structuredContent` until they have a real structured" payload; "Do not duplicate a large structured payload into a markdown artifact block"; follow-up `suggestedActions` whose "Arguments must be complete enough to call the tool without reparsing markdown." — [sentry-mcp docs/contributing/tool-responses.md](https://github.com/getsentry/sentry-mcp/blob/main/docs/contributing/tool-responses.md)
- Sentry: "Keep system prompts static to enable LLM provider caching. Never modify prompts based on errors." — [sentry-mcp adding-tools.md](https://github.com/getsentry/sentry-mcp/blob/main/docs/contributing/adding-tools.md) line 397
- Linear's server (23 tools) was praised for curated flat parameters (`assigneeId`, `stateId` instead of nested GraphQL filters) and explicit value mappings (priority 0–4 documented), criticised for verbose low-signal fields (`avatarUrl`, `createdAt`), stringified JSON wrapping, and no concise/detailed toggle. — [Fiberplane: The Linear team made a good MCP](https://dev.to/fiberplane/the-linear-team-made-a-good-mcp-2ip4) (Nele Lea, 2025-11-10)
- MCP client best-practices page: for programmatic tool calling "The real fix is for server authors to provide `outputSchema`." — [Client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices.md)

### Inferences
- `title` and `icons` are display-only; `name` is what the model sees in both target clients, so names should read well after prefixing (`mcp__previously__search` / `previously_search`): short, verb-first, no redundant `previously_` inside the name.
- Annotations cost nothing and are mandatory in Sentry's house rules; they matter today in Codex and in GitHub-style harness interception, not in Claude Code's permission engine (Aug 2026) and not documented for Vibe — set them for correctness, do not rely on them for safety.
- `structuredContent` + `outputSchema` pays off once a client uses programmatic/code-mode calling; the text block should be a human-readable summary, not a second copy of the JSON (spec example and Sentry's rule agree).

### Gaps
- The fetched 2026-07-28 tools page did not include the annotation table (defaults: `readOnlyHint` false, `destructiveHint` true, `idempotentHint` false, `openWorldHint` true per the 2025-03-26 schema) — these defaults are from memory and should be verified in the [schema](https://modelcontextprotocol.io/specification/2026-07-28/schema) before being cited.
- No measurement of how Claude Code's "classifier-based risk assessment" (blog claim) treats MCP tools; treat as unverified.

## Q5. Granularity and count: few broad vs many narrow tools; effect on accuracy and context; tool search / deferred loading; workflow- vs API-shaped tools

### Takeaway
Every primary source converges: tool-selection accuracy degrades with count (studies put the knee somewhere between ~20 and ~40 for 2025 models), schema tokens are the main cost, and the fix is **fewer, workflow-shaped tools** plus client-side progressive discovery (Claude Code's tool search at 10 % of context; Anthropic's Tool Search Tool at >10K tokens / 10+ tools). GitHub (108 tools behind toolsets), Sentry (≤25, target ~20), Amplitude (96 → consolidated by object with an `action` parameter) and Notion (Markdown over JSON blocks) all moved the same way.

### Cited Findings
**Studies (small-N, 2025; possibly outdated for 2026 models)**
- Breunig summarises two papers: RAG-MCP ([arXiv 2505.03275](https://arxiv.org/abs/2505.03275)) — tool descriptions overlap above ~30 tools with DeepSeek-v3, "Beyond 100 tools, the model was virtually guaranteed to fail", RAG-selection to <30 tools gave "as much as 3x better tool selection accuracy"; "Less is More" ([arXiv 2411.15399](https://arxiv.org/abs/2411.15399)) — Llama 3.1 8B "fails a benchmark when given 46 tools, but succeeds when given only 19 tools", dynamic selection improved BFCL performance by 44 %. — [Drew Breunig: How to fix your context](https://www.dbreunig.com/2025/06/26/how-to-fix-your-context.html) (2025-06-26)
- Maxim benchmark (GitHub + Notion MCP tools, 48 vs 25 tools): Claude Sonnet 4 66.67 % → 73.33 %; Claude Opus 4 66.67 % → 66.67 %; Claude 3.7 Sonnet 66.67 % → 73.33 %; GPT 4.1 46.67 % → 53.33 %; Gemini 2.5 Pro 53.33 % → 60 %. — [Maxim: Tool chaos no more](https://www.getmaxim.ai/blog/tool-chaos-no-more-how-were-measuring-model-tool-accuracy-in-the-age-of-mcp/) (Madhu Shantan, 2025-07-17)
- Speakeasy's Dog-API experiment (qwen3-1.7b): 107 tools → hallucinated tool names; 40 tools → 3/4 correct; 20 → 19/20; 10 → 4/4. — [Speakeasy: Why less is more for MCP](https://www.speakeasy.com/mcp/tool-design/less-is-more) (undated; small model)
- Archestra: "the knee sits around 40 tools" on frontier models, bands "<20 non-issue, 20–40 occasional bad picks, >40 curve bends, 70 fail reliably"; authors concede "no hard threshold" and give no data. — [Archestra: How many MCP tools is too many?](https://archestra.ai/blog/how-many-mcp-tools-too-many) (Mack Chi, undated; opinion)
- Anthropic internal evals with Tool Search Tool: Opus 4 49 % → 74 %, Opus 4.5 79.5 % → 88.1 %; 85 % context reduction for a five-server/58-tool setup; recommended when "Tool definitions consume >10K tokens", "10+ tools available", or selection accuracy problems; "less beneficial for small libraries (<10 tools)". — [Anthropic: Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use) (2025-11-24)

**Client-side deferred loading**
- Claude Code: tool search "Enabled by default on Claude 4.5+", defers MCP tool discovery; `ENABLE_TOOL_SEARCH=false` disables. — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- Claude Code issue (v2.1.7, 2026-01-15): documentation says "when MCP tool descriptions exceed 10% of the context window, they should be automatically deferred and discovered via the MCPSearch tool"; flag `tengu_mcp_tool_search` "enabled by default for all users". — [Claude Code issue #18370](https://claudeissues.com/issue/18370-bug-mcpsearch-not-activating-despite-meeting-10-threshold-40k-200k-tokens-20)
- MCP client best practices: "Implement a threshold as a percentage of the context window. For example, 1%-5%"; three-layer pattern catalog → inspect → execute; "Offer multiple detail levels"; "Group tools by server"; prompt-cache warning — "Adding or removing tool definitions mid-conversation invalidates that cache … route every call through a single stable `call_tool({name, args})` meta-tool so the array never changes." — [Client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices.md)
- Code-execution framing: tool definitions and intermediate results through context; example "reducing token usage from 150,000 tokens to 2,000 tokens"; caveat: "Running agent-generated code requires a secure execution environment". — [Anthropic: Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp) (2025-11-04)

**Practitioners**
- Anthropic: "a few thoughtful tools targeting specific high-impact workflows" rather than wrapping every endpoint; `search_contacts` over `list_contacts`; `schedule_event` (find availability + schedule) over `list_users`+`list_events`+`create_event`; `get_customer_context` over several retrieval tools. — [Anthropic: Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents) (2025-09-11)
- GitHub: launched with "over 100 tools"; "agents in early 2025 struggled with more than 20 tools in context"; answer was composable toolsets (`issues`, `repos`, `pull_requests`, `actions`, `code_security`) × read-only mode over 108 tools; "Agents will reach for tools that sound like a solution before chaining multiple tools together" — an `unfollow-users-followers` tool beat orchestrating get+unfollow; embeddings-based dynamic tool selection was prototyped and **shelved** as belonging "at the agent harness level, not the MCP server level". — [Arcade: lessons from GitHub's MCP server](https://www.arcade.dev/blog/enterprise-mcp-lessons-from-githubs-mcp-server-launch) (2026-03-03)
- GitHub README: default toolsets `context, repos, issues, pull_requests, users`; `--toolsets`, `--tools`, `--read-only` ("write tools are skipped if `--read-only` is set, even if explicitly requested"); 24 named toolsets; no `--dynamic-toolsets` documented any more. — [github/github-mcp-server README](https://github.com/github/github-mcp-server/blob/main/README.md) (fetched 2026-10-09)
- Sentry: "AI agents have a 45 tool limit (Cursor, etc.)"; "Sentry MCP must stay under 25 tools (target: ~20)"; "Consolidate functionality where possible"; "Consider parameter variants over new tools". — [sentry-mcp docs/architecture/overview.md](https://github.com/getsentry/sentry-mcp/blob/main/docs/architecture/overview.md) lines 205–208; "Target ~20 publicly visible tools. Never exceed 25." — [adding-tools.md](https://github.com/getsentry/sentry-mcp/blob/main/docs/contributing/adding-tools.md) line 20
- Amplitude: 96 tools; one customer's 200K context "57% consumed before a single tool call"; models "choose incorrectly ~12% of the time with large catalogs"; consolidation cohorts 9 → 1, charts 16 → 4, several search tools → 1; tools consolidated by object type with an `action` parameter while keeping "individual permission levels and audit events per action"; charts' three sequential calls became one; 37 skills moved long instructions out of descriptions; a single CLI-style tool wraps rare operations with "Permissions derived from HTTP method; unknown commands treated as writes"; success metric "recovery rate: successful calls within 5 minutes after failure". Retention after consolidation: 67 % / 59 % / 50 % at 1/4/8 weeks. — [Amplitude: Lessons from consolidating our MCP server](https://amplitude.com/blog/lessons-from-consolidating-our-mcp-server) (Chanaka Perera, 2026-10-06)
- Notion: 1:1 API mapping gave "high-context token consumption from working with hierarchical block data in JSON"; hosted server uses "Notion-flavored" Markdown for "efficient content density per LLM token, requiring fewer tool interactions and less cost". — [Notion: Hosted MCP server, an inside look](https://www.notion.com/blog/notions-hosted-mcp-server-an-inside-look) (Kenneth Sinder, 2025-07-15; **possibly outdated**)
- Community re-packaging of Notion's 21 tools into 10 "semantic operations" via an `action` parameter claims 73 % fewer schema tokens (~26,073 tokens for the original 21). — [lobehub: notion-slim](https://lobehub.com/mcp/mcpslim-notion-slim) (community, undated)

### Inferences
- For a knowledge store the realistic budget is **≤ ~12 tools**, each a complete workflow: both target clients will keep them all in context (Claude Code only defers above 10 % of context, which a dozen tools will not reach), so the count is the schema-token bill *every* turn.
- Amplitude's `action`-parameter consolidation and Sentry's "parameter variants over new tools" are the same move; the price is that annotations (`readOnlyHint` etc.) are per *tool*, so mixing reads and writes under one `action` tool either forces the tool to be annotated as a write or hides writes behind a read-only hint.
- GitHub's verdict that dynamic discovery belongs in the harness means a small server should **not** build its own tool-search layer; it should keep `tools/list` small, deterministic and cheap to cache.

### Gaps
- All accuracy studies predate the 2026 model generation and use ≤ 15 trials per cell (Maxim) or a 1.7B model (Speakeasy); no 2026 study with current Claude or Mistral models was found.
- Sentry's "45 tool limit (Cursor)" is a client-specific cap from 2025 and may no longer hold.

## Q6. Pagination (cursor), large results, token efficiency, truncation, handles/IDs for follow-up calls

### Takeaway
Protocol pagination exists only for the four list operations (opaque cursors, server-chosen page size, `-32602` on bad cursor, each page separately cacheable); **tool results have no protocol pagination** — the server must build it into tool arguments and default to small, filtered pages because Claude Code warns at 10K and truncates at 25K tokens. Handles returned from one call and accepted by the next are now the spec's own recommended state mechanism.

### Cited Findings
- Pagination (2025-11-25 page; mechanics unchanged in 2026-07-28 per changelog): "opaque cursor-based approach"; "Page size is determined by the server, and clients **MUST NOT** assume a fixed page size"; supported on `resources/list`, `resources/templates/list`, `prompts/list`, `tools/list`; servers **SHOULD** "Provide stable cursors; Handle invalid cursors gracefully"; clients **MUST** "treat cursors as opaque tokens … Don't persist cursors across sessions"; invalid cursor → `-32602`. — [Pagination 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/utilities/pagination)
- 2026-07-28 caching adds: "each page is an independently cacheable response"; "There is no cross-page consistency guarantee … clients may observe duplicates or gaps"; "Clients that require a consistent snapshot of the full list **SHOULD** re-fetch from the beginning"; same `cacheScope` on all pages. — [Caching 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching)
- Handles: "Servers that need to maintain state across calls … should do so by returning an explicit handle from a creation tool and accepting that handle as an argument on subsequent calls"; state the retention policy in the creation tool's description. — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Claude Code limits: warning at 10,000 tokens; default cap 25,000 tokens (`MAX_MCP_OUTPUT_TOKENS`); 50,000-character persistence threshold for text results without the `anthropic/maxResultSizeChars` annotation; per-tool ceiling 500,000 characters; 16 MB per HTTP/SSE response; calls over ~2 minutes are moved to background tasks (`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`). — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- Anthropic: "Claude Code restricts responses to 25,000 tokens by default"; implement "pagination, range selection, filtering, and/or truncation with sensible default parameter values"; concise vs detailed `response_format`; truncated responses should steer the agent toward narrower queries. — [Anthropic: Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents) (2025-09-11)
- Linear's server criticised for a ~17.3k-token baseline from stringified JSON and low-signal fields; recommended "CSV/TSV for tabular data, Markdown for nested data". — [Fiberplane on Linear](https://dev.to/fiberplane/the-linear-team-made-a-good-mcp-2ip4) (2025-11-10)
- Sentry response shape: predictable Markdown with `#` title naming the scope, `##`/`###` per resource; a `suggestedActions` structure with complete arguments for the next call. — [sentry-mcp tool-responses.md](https://github.com/getsentry/sentry-mcp/blob/main/docs/contributing/tool-responses.md)
- Programmatic tool calling keeps intermediate results out of context: 43,588 → 27,297 tokens (37 %) on complex research tasks (Anthropic internal). — [Anthropic: Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use) (2025-11-24)
- Tool results may carry `resource_link`s so the client can fetch large bodies on demand instead of embedding them. — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

### Inferences
- A `search` tool should take `limit` (small default), `cursor`/`after`, and a `response_format`-style switch, and return stable event IDs plus natural-language identifiers (subject, date, counterpart) so the next call can be `get_event(id)` rather than another search.
- For bodies beyond a few thousand tokens, return a summary plus a `resource_link` (works in Claude Code) **and** document a `get_event(id, part=…)` path (works everywhere).

### Gaps
- No documented output limit for Mistral Vibe MCP tool results.
- No data on whether Claude Code's `@`-mentioned resources are subject to the tool-result truncation.

## Q7. Error model: protocol errors vs tool execution errors (`isError`), and writing errors a model can act on

### Takeaway
The spec splits errors into JSON-RPC protocol errors (unknown tool, malformed request) and `isError: true` results for "API failures, input validation errors, business logic errors" that carry "actionable feedback"; clients SHOULD forward only the latter to the model. Practitioners add: tell the model what to do next, and never echo untrusted text into an error.

### Cited Findings
- "**Protocol Errors** indicate issues with the request structure itself that models are less likely to be able to fix: Unknown tool; Malformed requests; Server errors" (JSON-RPC `-32602` etc.). "**Tool Execution Errors** contain actionable feedback that language models can use to self-correct and retry with adjusted parameters: API failures; Input validation errors (e.g., date in wrong format, value out of range); Business logic errors" (`isError: true`). "Clients **SHOULD** provide tool execution errors to language models to enable self-correction. Clients **MAY** provide protocol errors". Example text: "Invalid departure date: must be in the future. Current date is 08/08/2025." — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Resources: not found → `-32602` (was `-32002`); prompts: invalid name / missing args → `-32602`. — [Resources 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources); [Prompts 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts)
- Error-code policy: `-32000`…`-32019` implementation-defined, `-32020`…`-32099` reserved for the spec. — [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Code-mode clients turn `isError` into exceptions: "Generated wrappers should convert this into a thrown exception … the model is responsible for reporting any partial side effects already committed." — [Client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices.md)
- Anthropic: replace opaque codes/tracebacks with "Clear instructions on corrected input format or suggest refined search parameters". — [Anthropic: Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents) (2025-09-11)
- GitHub: instead of "403 Forbidden" say "Tried to commit, but the user needs to authorize commit signing. Please ask the user to approve the SSH agent prompt." — agents "really take the steering". — [Arcade: GitHub lessons](https://www.arcade.dev/blog/enterprise-mcp-lessons-from-githubs-mcp-server-launch) (2026-03-03)
- Sentry: two-tier model — `UserInputError` (validation, user-facing message) vs system errors (logged, generic message); agent-facing format `{ error: "Input Error: {message}. You may be able to resolve this by addressing the concern and trying again." }`; "**NEVER return untrusted error messages to AI agents - this creates prompt injection vulnerabilities**" — only application-controlled messages are returned. — [sentry-mcp error-handling.md](https://github.com/getsentry/sentry-mcp/blob/main/docs/contributing/error-handling.md) lines 81–95, 163
- Amplitude tracks "recovery rate: successful calls within 5 minutes after failure" and considered "validation failures with clear messages … acceptable". — [Amplitude](https://amplitude.com/blog/lessons-from-consolidating-our-mcp-server) (2026-10-06)
- A typed error taxonomy (`rate_limited` retryable, `validation_failed` permanent, `upstream_timeout` retry with same key) is proposed for agent-called writes. — [Frihet: Make agent-callable writes idempotent](https://dev.to/frihet/make-agent-callable-writes-idempotent-or-lose-data-2n5m) (Berthelius, "August 2", year not shown; blog)

### Inferences
- For a gate that refuses content, the `isError` text should say *that* the gate refused and *what the model may do instead* (e.g. ask the user, request a summary), without quoting the refused content — Sentry's injection rule applied to customer e-mails.
- Expired or unknown handles (event IDs, cursors, confirmation tokens) belong in `isError` with a recovery hint, per the spec's stateful-tools guidance.

### Gaps
- No source on how Mistral Vibe surfaces `isError` results versus protocol errors to its model.

## Q8. Write operations: idempotency keys, confirmation, human-in-the-loop via elicitation

### Takeaway
The protocol offers no idempotency; retries are expected (MRTR retries are *new* requests with new IDs, and the spec says servers "MUST NOT assume that clients will … retry"), so dedup is the server's job. Confirmation can be done in-band via form-mode elicitation nested in an `InputRequiredResult` (flat primitive schema, accept/decline/cancel, never secrets), but only for clients that declare `elicitation` — Claude Code shows elicitation dialogs, Mistral Vibe documents nothing — and the human-in-the-loop for tool calls is primarily the client's permission prompt.

### Cited Findings
- MRTR: "Servers **MAY** respond to any supported client request [`tools/call`, `prompts/get`, `resources/read`] with an `InputRequiredResult`"; `inputRequests` values **MUST** be `ElicitRequest`, `CreateMessageRequest` or `ListRootsRequest`; "Servers **MUST NOT** send an `inputRequests` that the client has not declared support for"; "Servers **MUST NOT** assume that clients will fulfill the `inputRequests` or retry the original request"; `requestState` is opaque to clients, and "servers **MUST** treat `requestState` as an attacker-controlled input … **MUST** protect its integrity (e.g. HMAC or AEAD)"; include principal, TTL and an originating-request digest to bound replay, and "Servers for which a given `requestState` must be consumed at most once … **MUST** enforce that invariant server-side." Retry **MUST** use a different JSON-RPC `id`. — [MRTR 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)
- Elicitation (2026-07-28): delivered only inside `InputRequiredResult`; form mode schema "limited to flat objects with primitive properties only" (string with `format` email/uri/date/date-time, number/integer, boolean, single/multi-select enums with optional titles, defaults); "Servers **MUST NOT** use form mode elicitation to request sensitive information such as passwords, API keys, access tokens, or payment credentials"; actions `accept` / `decline` / `cancel`; clients **MUST** "allow users to review and modify their responses before sending" and provide decline/cancel; "Servers … **MUST** handle cases where the user declines or cancels". URL mode is for out-of-band secrets/OAuth and "**MUST NOT**" be used to authorise the MCP client itself. — [Elicitation 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)
- Results of MRTR retries "**MUST NOT** be cached". — [Caching 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching)
- Tools: clients **SHOULD** "Prompt for user confirmation on sensitive operations" and "Show tool inputs to the user before calling the server"; servers **MUST** "Implement proper access controls" and "Rate limit tool invocations". — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Claude Code keeps an elicitation dialog open rather than backgrounding the call; organisations can set per-tool `ask`/`blocked`; `dontAsk` mode denies `ask`-flagged tools instead of prompting. — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- Mistral Vibe: per-tool `"always"` / `"ask"` permission; no mention of elicitation. — [Mistral Vibe: MCP servers](https://docs.mistral.ai/vibe/code/cli/mcp-servers)
- Idempotency (blog): "the protocol says nothing about whether invoking `create_invoice` twice creates one invoice or two. That contract is entirely yours to define"; key is "a client-generated token (usually a UUID) that stays the same across retries of the same intended write"; retain "hours to a day"; replay returns "exactly what the first caller got"; fingerprint the payload so "reusing a key with different data triggers rejection rather than silent replay". — [Frihet: Make agent-callable writes idempotent](https://dev.to/frihet/make-agent-callable-writes-idempotent-or-lose-data-2n5m) (Berthelius; blog, year unclear)
- Amplitude moved "Saving" of charts "to UI buttons via MCP Apps instead" and uses MCP Apps to "Enable human review before destructive actions"; tools marked app-visibility "never appear in model listings". — [Amplitude](https://amplitude.com/blog/lessons-from-consolidating-our-mcp-server) (2026-10-06)
- Codex requires approval whenever `destructiveHint: true`. — [Daniel Vaughan on Codex CLI](https://codex.danielvaughan.com/2026/04/12/mcp-tool-annotations-risk-vocabulary-codex-cli/) (2026-04-12)
- Tasks (long-running operations) are now an official extension with polling via `tasks/get` and `tasks/update` for client input. — [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

### Inferences
- An append-only, hash-chained store has a natural idempotency key: the content hash of the submission (plus a model-supplied `client_ref` if deliberate duplicates must be distinguishable). Server-side dedup by that key, with the original result replayed, satisfies both the protocol's retry semantics and the blog's "fingerprint" rule without trusting the model to mint UUIDs.
- A two-step confirm (`submit(preview=true)` returning a short-lived HMAC'd confirmation token → `submit(confirm=token)`) is the client-agnostic fallback to elicitation; it is literally the spec's `requestState` discipline applied at tool-argument level and works in Vibe.
- Do not double-prompt: Claude Code already asks before a write tool unless allow-listed; elicitation should ask about *content* (which obligation, which deadline), not merely "are you sure".

### Gaps
- No primary source on whether Mistral Vibe declares the `elicitation` capability; a server must check the per-request `_meta` client capabilities rather than assume.
- The dev.to idempotency post's year could not be established from the page.

## Q9. Design recommendations for a knowledge store (Previously), each with its counter-argument

### Takeaway
Serve both clients with a small set of workflow-shaped **tools** as the only mandatory surface; add **resources** (custom `previously://` scheme, templates, `audience`/`priority`/`lastModified`, `resource_link`s from search) and two or three **prompts** as Claude-Code-side conveniences; make writes idempotent by content hash with a confirm step that works without elicitation; treat annotations as documentation, not as the safety mechanism.

### Cited Findings
(These recommendations draw on the findings above; the sources repeated here are the ones each recommendation leans on most.)
- Tools reach both clients; resources and prompts are undocumented in Vibe. — [Mistral Vibe: MCP servers](https://docs.mistral.ai/vibe/code/cli/mcp-servers); [Claude Code: Slash commands](https://code.claude.com/docs/en/slash-commands)
- Fewer, workflow-shaped tools; ≤ ~20–25 practitioners' ceiling; `action` consolidation with per-action permissions. — [Sentry overview.md](https://github.com/getsentry/sentry-mcp/blob/main/docs/architecture/overview.md); [Amplitude](https://amplitude.com/blog/lessons-from-consolidating-our-mcp-server); [Arcade/GitHub](https://www.arcade.dev/blog/enterprise-mcp-lessons-from-githubs-mcp-server-launch)
- Stateless handles, deterministic `tools/list`, `ttlMs`/`cacheScope`, per-request authorization filtering. — [Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); [Caching 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching)
- Elicitation only for clients declaring it; `requestState` integrity. — [MRTR 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)
- Errors: actionable, application-controlled text only. — [sentry-mcp error-handling.md](https://github.com/getsentry/sentry-mcp/blob/main/docs/contributing/error-handling.md)
- Output limits 10K warn / 25K cap in Claude Code. — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)

### Inferences
1. **Tools are the contract; resources and prompts are accelerators.** Design every capability as a tool first (`chronicle`, `search`, `get_event`, `open_obligations`, `submit`, `record_assertion`, `triage`, `approve`), then mirror the read-only ones as resources and add prompts. *Counter:* double surface = double tests and double gate logic; the archestra argument that reads "should never have been a tool decision" would say put reads only in resources — but that strands Vibe users.
2. **Keep the tool count around 8–12 and workflow-shaped.** One `chronicle(project, since?, format?)` instead of `list_events`+`get_summary`; one `search(query, project?, kind?, limit, cursor, format)` across events, units and assertions (Amplitude's single search). *Counter:* GitHub's lesson that agents reach for "tools that sound like a solution" cuts both ways — too broad a `search` with many optional parameters shifts the selection problem into parameter-filling, where Anthropic measured the biggest gains from examples and explicit descriptions; evaluate with held-out tasks before merging.
3. **Separate read tools from write tools; do not hide writes behind an `action` parameter.** Annotations are per tool; Codex auto-approves `readOnlyHint` and always prompts on `destructiveHint`, GitHub filters by scope. *Counter:* Amplitude's consolidation kept per-action permissions and audit server-side and still reduced errors — if the gate enforces per-action policy, an `assertions(action=record|retract…)` tool saves schema tokens; the loss is only in clients that read annotations, which today excludes Claude Code.
4. **Project is an argument (or a URI segment), never session state.** `previously://{customer}/{project}/chronicle`, `previously://{customer}/{project}/event/{id}`, `previously://{customer}/{project}/obligations?status=open` as resource templates with completion on `{customer}`/`{project}`. *Counter:* a resource URI that encodes customer and project leaks structure the gate might want hidden (listing templates reveals which projects exist); keep `resources/list` filtered by the per-request authorization and set `cacheScope: "private"`.
5. **Search returns handles plus names, and `resource_link`s for bodies.** Each hit: event id, hash prefix, date, kind, counterpart, one-line gist; full body via `get_event(id, part=body|headers|attachments)` and, for Claude Code, a `resource_link`. *Counter:* two paths to the same body means two gate checks and two caches; and `resource_link`s are invisible to Vibe — if Vibe is the pilot client, the link is dead weight in every result.
6. **Default pages small; `format` switch `concise|detailed`.** Aim for < 10K tokens per result (Claude Code's warning threshold), paginate with an opaque cursor derived from `(id, hash)`. *Counter:* every extra parameter costs schema tokens on every turn; Anthropic's own advice is to measure — a concise default with explicit `limit` may be enough.
7. **Writes are idempotent by content hash + optional `client_ref`; replay returns the original result.** Append-only means a duplicate submission is naturally a no-op; `idempotentHint: true`, `destructiveHint: false`. *Counter:* a knowledge store may legitimately record the same text twice (same e-mail forwarded in two projects); the key must include project and kind, and a model-supplied `client_ref` reintroduces the "models mint bad UUIDs" problem — prefer server-derived keys and an explicit `allow_duplicate` flag.
8. **Confirmation via a two-step `preview → confirm(token)` protocol, with elicitation as an upgrade.** The token is an HMAC'd `requestState`-style blob with TTL, principal and digest; when the client declares `elicitation.form`, the same step is offered as a form (`InputRequiredResult`). *Counter:* Claude Code already prompts before writes; a server-side confirm adds a second prompt and a second round-trip per write, which Anthropic's token-efficiency advice argues against — reserve the confirm step for assertions with legal weight (obligations, approvals), not for `submit`.
9. **Gate decisions live in per-request authorization, not in the tool list.** Filter *results* (and `resources/list`) by what the caller may see; keep `tools/list` identical for everyone (deterministic order, long `ttlMs`, `cacheScope: "public"`) so prompt caches hold. *Counter:* GitHub shows that hiding write tools from read-only tokens *reduces* selection errors; a per-scope tool list is spec-conformant ("MAY vary by the authorization") — the price is cache fragmentation, acceptable if scopes are few.
10. **Errors name the next step and never quote customer content.** `isError` text like "Gate refused body of event e_123 for this policy; ask the user, or request `get_event(e_123, part=summary)`." *Counter:* over-redacted errors remove exactly the information a model needs to self-correct; include stable IDs and policy names, which are application-controlled.
11. **Prompts: two or three, argument-light, with completion.** `/mcp__previously__status <project>` (embeds the chronicle head as a resource and instructs which tools to call), `/mcp__previously__triage`, `/mcp__previously__obligations <project>`. *Counter:* invisible in Vibe and untested in adoption data; each is another surface the documentation gate must cover — but the cost is low (text templates) and they encode the "how to use this server" opinion that otherwise lands in every tool description.
12. **Target 2026-07-28 semantics now (stateless, handles, `resultType`, cache hints, `-32602`) with the 2025-11-25 handshake kept for compatibility.** *Counter:* SDK and client support for 2026-07-28 may lag (Claude Code's v2 runtime already notes one restriction for 2026-07-28 servers), and Vibe's protocol version is unknown; measure against both clients before dropping the older path.

### Gaps
- No empirical comparison of "tools only" vs "tools + resources + prompts" servers in either target client; the recommendation to add resources and prompts rests on spec intent and practitioner opinion, not measurement.
- The per-client behaviour on unknown capabilities (a server advertising `resources`/`prompts`/`completions` to Vibe) is untested.
