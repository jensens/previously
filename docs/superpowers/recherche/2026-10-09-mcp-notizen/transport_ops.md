# MCP transports and operating an MCP server in production (as of 2026-10-09)

Scope note for the writer: the current MCP revision is **2026-07-28**, published 2026-07-28, and it rewrote Streamable HTTP. Several of the key questions were phrased in terms of the 2025 model (sessions, GET stream, `Last-Event-ID`). Those mechanisms are gone from the current revision but still matter operationally, because the default Claude Code runtime still speaks the 2025 era. Each finding below is tagged: **[MUST]/[SHOULD]/[MAY]** = normative spec language; **[spec-info]** = non-normative spec prose; **[vendor]** = a vendor's own documentation about its product; **[practice]** = community blog or example, lower weight. Material older than 2026-07-28 that describes Streamable HTTP is marked **[pre-2026-07-28]** — accurate for legacy clients, superseded for modern ones.

## Key question 1: Which transports does the current spec define, what is the status of HTTP+SSE, and is anything newer (WebSocket) coming?

### Takeaway
The current revision (2026-07-28) defines exactly two bindings, stdio and Streamable HTTP; HTTP+SSE (2024-11-05) is formally Deprecated under a new lifecycle policy and eligible for removal three months after SEP-2596 reaches Final; the WebSocket SEP was closed as dormant on 2026-06-26, and there is no newer standard transport.

### Cited Findings
- The transports overview for revision 2026-07-28 lists two standard bindings: "1. stdio: newline-delimited messages over the standard streams of a client-launched subprocess. 2. Streamable HTTP: each message is an HTTP POST to a single MCP endpoint; replies arrive as a JSON object or a request-scoped SSE stream." — [MCP spec 2026-07-28, Transports overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) (fetched 2026-10-09; `latest` resolves to 2026-07-28)
- A transport is "a binding: it defines how messages are framed and delivered, how request metadata is carried, and how cancellation and termination are signaled"; protocol semantics are identical on every transport. [spec-info] — [Transports overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)
- Custom transports: clients and servers **[MAY]** implement them; they **[MUST]** preserve the JSON-RPC format, message patterns and per-request metadata model; custom transports over a reliable byte stream (Unix domain sockets, TCP) **[SHOULD]** reuse the stdio framing. — [Transports overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)
- The 2026-07-28 changelog, "Deprecated" section: "Reclassify the HTTP+SSE transport (deprecated since protocol version 2025-03-26) as Deprecated under the feature lifecycle policy (SEP-2596). Migrate to Streamable HTTP." — [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Deprecated-features registry: HTTP+SSE transport, deprecated in `2025-03-26`, migration path Streamable HTTP, earliest removal "Three months after SEP-2596 reaches Final". The policy defines "a minimum twelve-month deprecation window" for features deprecated under it; no feature has been removed yet. — [Deprecated features registry](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)
- Streamable HTTP page: HTTP+SSE "has been deprecated since protocol version 2025-03-26 ... New implementations **SHOULD NOT** adopt it; existing implementations **SHOULD** migrate". — [Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- The official release post (2026-07-28, David Soria Parra and Den Delimarsky) says HTTP+SSE is "officially deprecated with a 'year-long offramp'" and does not mention WebSocket or any other new transport. — [MCP blog, The 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- WebSocket proposal SEP-1288 (created 2025-08-02, author Larry Maccherone, sponsor Kludex): closed on 2026-06-26 with the comment "Given that we have not seen any movement in this SEP and no Core Maintainer sponsorship, marking it as dormant and closing"; labels `dormant`, `draft`. — [GitHub issue #1288](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1288)
- Claude Code offers a client-specific `"type":"ws"` transport ("Persistent connection for servers that push events unprompted", header-only auth, no OAuth, configured via `claude mcp add-json` and not via `--transport`), with the advice "Use HTTP instead when server only responds to requests". [vendor] — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp) (fetched 2026-10-09)
- Cloudflare's Agents SDK lists stdio ("local MCP connections only"), Streamable HTTP ("the standard for remote connections") and an internal RPC transport; "Server-Sent Events (SSE) was previously used for remote MCP connections but has been deprecated in favor of Streamable HTTP." [vendor] — [Cloudflare Agents, MCP transport](https://developers.cloudflare.com/agents/model-context-protocol/transport/) (page dated 2026-07-27)
- Revision timeline from the spec pages: Streamable HTTP "was introduced in protocol version 2025-03-26 as a replacement for the HTTP+SSE transport from protocol version 2024-11-05"; the revisions since are 2025-06-18, 2025-11-25 and 2026-07-28. — [Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http); [Changelog 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/changelog)

### Inferences
- There is no transport decision to wait for: stdio and Streamable HTTP are the only standard bindings for at least the next revision cycle, and the WebSocket track is dead as of mid-2026.
- Claude Code's `ws` type is a custom transport in the spec's sense; building for it would tie the server to one client and buy nothing for a request/response server such as a knowledge store.
- A Unix domain socket variant of stdio framing is explicitly blessed as a custom transport; that is the spec's own suggestion for a local HTTP-free server that must not be reachable from the browser (see question 2, security).

### Gaps
- No source states when SEP-2596 reached or will reach Final, so the earliest removal date of HTTP+SSE cannot be given as a calendar date.

## Key question 2: Streamable HTTP in detail — endpoint, methods, SSE, resumability, sessions, headers, Origin/DNS rebinding

### Takeaway
In 2026-07-28 Streamable HTTP is a POST-only single endpoint where each JSON-RPC request gets either one JSON object or a request-scoped SSE stream; sessions (`Mcp-Session-Id`), the GET stream, server-initiated requests and `Last-Event-ID` resumption are all removed; three headers (`MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`) are mandatory on every POST and must match the body; `Origin` validation with 403 is a MUST.

### Cited Findings
**Endpoint and methods**
- "The server **MUST** provide a single HTTP endpoint path (hereafter referred to as the MCP endpoint) that supports POST." Revision 2026-07-28 removed "the GET stream endpoint" and "protocol-level sessions". — [Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- "Every JSON-RPC message sent from the client **MUST** be a new HTTP POST request"; the client **[MUST]** send `Accept: application/json, text/event-stream`; the body **[MUST]** be a single request or notification (clients **[MUST NOT]** send JSON-RPC responses). — same page
- Notifications: server **[MUST]** answer `202 Accepted` with no body if accepted; note: "This revision of the core protocol defines no client-to-server notifications over Streamable HTTP." — same page
- Requests: server **[MUST]** return either `Content-Type: application/json` (one object) or `text/event-stream`; the client **[MUST]** support both. — same page

**SSE streaming of responses**
- On an SSE response stream the server **[MAY]** send `notifications/progress` / `notifications/message` before the final response; these **[MUST]** relate to the originating request; the server **[MUST NOT]** send independent JSON-RPC requests on the stream (change from 2025-03-26 through 2025-11-25); the final response **[SHOULD]** terminate the stream. — same page
- Servers **[SHOULD]** include `X-Accel-Buffering: no` on SSE responses so reverse proxies such as nginx do not buffer; servers "are encouraged to periodically emit an SSE comment line (`:\r\n`) as a keep-alive" on long-lived streams. — same page
- "Resumable SSE streams via `Last-Event-ID` are not supported." Changelog: "A broken response stream loses the in-flight request; clients **MUST** re-issue it as a new request with a new request ID (SEP-2575)." — [Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http); [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Cancellation: "Closing the SSE response stream **MUST** be treated by the server as cancellation of that request"; server **[SHOULD]** stop work and **[MUST NOT]** send further messages. — [Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)

**Sessions removed; long-lived notifications**
- Changelog major change 1: "Remove protocol-level sessions and the `Mcp-Session-Id` header from the Streamable HTTP transport. List endpoints (`tools/list`, `resources/list`, `prompts/list`) no longer vary per-connection. Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments (SEP-2567)." — [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Change 4: GET endpoint and `resources/subscribe` replaced by `subscriptions/listen`, "a single long-lived POST-response stream for opted-in server-to-client change notifications". — same
- A server that supports only 2026-07-28 and receives legacy traffic **[SHOULD]**: answer GET or DELETE with `405`; ignore `Mcp-Session-Id` "and do not mint or echo session IDs"; ignore `Last-Event-ID`. — [Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)

**Headers**
- "Every POST request to the MCP endpoint **MUST** include an `MCP-Protocol-Version` header", which **[MUST]** match `_meta["io.modelcontextprotocol/protocolVersion"]`; mismatch → `400` + `HeaderMismatch` (`-32020`); unsupported version → `400` + `UnsupportedProtocolVersionError` (`-32022`) listing supported versions; unknown method → `404` + `-32601`. — same page
- Standard headers table: `Mcp-Method` (source `method`, all requests) and `Mcp-Name` (source `params.name` or `params.uri`, for `tools/call`, `resources/read`, `prompts/get`): "These headers are **REQUIRED** for compliance." Non-ASCII values use the `=?base64?...?=` sentinel. — same page
- `x-mcp-header` schema extension lets a server mirror tool parameters into `Mcp-Param-{Name}` headers; optional for servers, clients **[MUST]** support it; servers **[MUST]** reject header/body mismatches with `400` / `-32020`. — same page
- Rationale stated by the spec: headers exist "so that intermediaries (load balancers, gateways, observability tooling) can route and inspect requests without parsing the body"; validation "prevents potential security vulnerabilities when different components in the network rely on different sources of truth". — same page
- A server supporting pre-2025-06-18 clients **[MAY]** treat a request without `MCP-Protocol-Version` as `2025-03-26`; otherwise it **[MUST]** reject. — same page

**Security: Origin, DNS rebinding, binding, auth**
- "Servers **MUST** validate the `Origin` header on all incoming connections to prevent DNS rebinding attacks. If the `Origin` header is present and invalid, servers **MUST** respond with HTTP 403 Forbidden." "When running locally, servers **SHOULD** bind only to localhost (127.0.0.1) rather than all network interfaces (0.0.0.0)." "Servers **SHOULD** implement proper authentication for all connections." — [Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) (the 403 wording was added in 2025-11-25, PR #1439: [Changelog 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/changelog))
- Security best practices, local servers: servers meant to run locally **[SHOULD]** "Use the `stdio` transport to limit access to just the MCP client" or, with HTTP, "Require an authorization token" or "Use unix domain sockets or other Interprocess Communication (IPC) mechanisms with restricted access". — [Security best practices 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)
- Token passthrough: "MCP servers **MUST NOT** accept any tokens that were not explicitly issued for the MCP server." — same page
- State-handle hijacking (replaces session hijacking): servers **[MUST NOT]** treat possession of a handle as authentication; **[SHOULD]** use non-deterministic handles and bind them server-side to the authenticated user (`<user_id>:<handle>`). — same page
- Auth framework: HTTP implementations **[SHOULD]** follow the authorization spec; "implementations using STDIO transport **SHOULD NOT** follow this specification, and instead retrieve credentials from the environment." — [Base protocol overview 2026-07-28, Auth](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)

**Legacy (2025-11-25) Streamable HTTP, for clients still on that era** [pre-2026-07-28]
- Endpoint **[MUST]** support POST and GET; server **[MAY]** assign `MCP-Session-Id` on the `InitializeResult`; if assigned, clients **[MUST]** send it on every request; server **[MAY]** terminate a session and then **[MUST]** answer `404`, after which the client **[MUST]** re-initialize; client **[SHOULD]** `DELETE` to end a session. — [Transports 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)
- Resumability: servers **[MAY]** attach SSE event IDs; resumption "is always via HTTP GET with `Last-Event-ID`"; SEP-1699 lets the server close the connection without ending the stream and send `retry`, so clients poll. Disconnection "**SHOULD NOT** be interpreted as the client cancelling its request" (the opposite of 2026-07-28). — same page
- Backward-compat probing in 2026-07-28: a dual-era client tries a modern request first; on `400` it inspects the body, and only if the body is not a recognized modern JSON-RPC error does it fall back to `initialize`, and possibly further to HTTP+SSE via GET expecting an `endpoint` event. — [Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http); [Versioning 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)

### Inferences
- "Idempotency requirement": the spec does not use the word, but the rule that a client re-issues a lost in-flight request "with a new request ID" means the server cannot deduplicate at the protocol level. A tool that writes must therefore be safe to run twice, or carry its own idempotency key as a tool argument (which the state-handle guidance already points toward).
- For a server that only ever answers in one JSON object (no progress notifications, no subscriptions), SSE never appears on the wire and none of the proxy-buffering or keep-alive concerns apply. The transport leaves that choice per request to the server.
- `Origin` validation on a server reached only over an ingress with TLS and auth is cheap; it matters most for a server bound on a workstation port, which is exactly the "local HTTP" configuration the security page steers away from in favour of stdio or a Unix socket.

### Gaps
- Whether any current client (Claude Code v2 runtime, Mistral Vibe) actually sends `Mcp-Method`/`Mcp-Name` today could not be verified from documentation; the Claude Code page says the v2 runtime "supports MCP protocol revision 2026-07-28" but does not list headers.

## Key question 3: Stateless operation — replicas behind a load balancer, what state a server must keep, long-running operations

### Takeaway
Since 2026-07-28 the protocol is stateless by definition (every request carries version, capabilities and identity in `_meta`), so any replica may serve any request without affinity or a shared session store; the only state a server keeps is what it chooses to mint as explicit handles, the open `subscriptions/listen` streams (scoped to the request, not resumable), and task records if it adopts the tasks extension, which must then be durable across replicas.

### Cited Findings
- Normative statelessness section: "A server processes each request independently; no state should be inferred from previous requests, even those on the same connection or stream." Servers **[MUST NOT]** rely on prior requests for context; **[SHOULD]** handle requests from multiple conversations; **[SHOULD NOT]** require the same connection or process; "State that needs to span multiple requests ... **MUST** be referenced by an explicit identifier the client passes on each request." — [Base protocol 2026-07-28, Statelessness](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)
- Required per-request `_meta`: `io.modelcontextprotocol/protocolVersion` (required), `io.modelcontextprotocol/clientCapabilities` (required), `clientInfo` (SHOULD); a request missing a required field is rejected with `-32602` and HTTP `400`. — same page
- `server/discover`: "servers MUST implement this RPC to advertise their supported protocol versions, capabilities, and identity." `ping` was removed. — [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Official release post: session elimination lets developers "implement application-level state through explicit handles returned by tools rather than transport-level sessions, enabling load-balanced deployments without shared storage." — [MCP blog 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- `subscriptions/listen`: the server **[MUST]** send `notifications/subscriptions/acknowledged` first, and the acknowledgment "reflects the subset the server agreed to honor"; a transport drop "carries no response" and the client **[MAY]** reconnect; on stdio the client **[MUST]** re-send `subscriptions/listen` after reconnect because "the server holds no subscription state across reconnections". — [Subscriptions 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions)
- Stdio page: "Because the protocol is stateless, any in-flight requests are simply lost and the client can retry them against the fresh process." — [stdio 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)
- Tasks extension (`io.modelcontextprotocol/tasks`, official extension since 2026-07-28, SEP-2663): server returns `CreateTaskResult` with `taskId`, `ttlMs`, `pollIntervalMs`; "The task must be durably created before sending the response"; clients poll `tasks/get`; cancellation is cooperative; motivation: "Many clients and transport intermediaries impose timeouts that make this impractical beyond a few seconds." Host support "varies by client". — [Tasks extension overview](https://modelcontextprotocol.io/extensions/tasks/overview); [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Cacheable lists: `tools/list`, `prompts/list`, `resources/list`, `resources/read`, `resources/templates/list` carry required `ttlMs` and `cacheScope` (`public`/`private`); servers **[SHOULD]** return tools in deterministic order. — [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Legacy era: in 2025-11-25 a server "**MAY** assign a session ID"; sessions are optional. — [Transports 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) [pre-2026-07-28]
- Python SDK v2.0.0 (released 2026-07-28): "speaks the 2026-07-28 revision (stateless requests with no handshake, `server/discover`, `subscriptions/listen`, multi-round-trip requests) and still serves every 2025-era client from the same `MCPServer`, over Streamable HTTP and stdio, with nothing to configure"; Streamable HTTP rejects bodies over 4 MiB with HTTP 413; v1.x "is in maintenance mode and will only receive security fixes". [vendor] — [python-sdk v2.0.0 release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.0.0)
- Cloudflare: new servers use `createMcpHandler`, "stateless" with "no protocol-level session"; the older `McpAgent` (Durable-Object-backed sessions, event replay) is deprecated. [vendor] — [Cloudflare Agents, MCP transport](https://developers.cloudflare.com/agents/model-context-protocol/transport/) (2026-07-27)
- Community write-ups since July 2026 describe the same consequence: "enabling MCP servers to be placed behind any off-the-shelf round-robin load balancer, because it no longer matters which instance receives a request" and that "sticky-session rules and shared session stores can be eliminated". [practice] — [Better Stack guide, MCP goes stateless](https://betterstack.com/community/guides/ai/mcp-stateless/); [Hackernoon](https://hackernoon.com/mcp-just-went-stateless-what-the-2026-spec-actually-changes-for-your-servers) (both undated in the search result; post-2026-07-28 by content)
- Claude Code timeouts for long calls: per-request timer is the greatest of 60 s, the per-server `timeout`, or `MCP_TIMEOUT`; idle window 5 min for HTTP/SSE/WS and 30 min for stdio ("if no response/progress for idle timeout, call aborts"); calls over 2 min become background tasks (`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`); global `MCP_TOOL_TIMEOUT` default about 28 h. [vendor] — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- Claude Code v2 runtime handling of the listen stream: "Stream closes within 10 seconds: reopens up to 3 times, then stops. Stream closes after 10+ seconds (common for serverless): waits ~6 hours before next reopen." [vendor] — same page

### Inferences
- For a knowledge store on PostgreSQL the "state" question answers itself: everything durable already lives in the database, which every replica shares, so handles (if any) are rows, and the server process keeps nothing. Replica count becomes an availability choice, not a correctness one.
- Long-running operations have two layers: progress notifications on the request's SSE stream keep the client's idle timer alive (Claude Code resets on progress), and the tasks extension covers work that outlives a connection. Tasks need a shared durable store — again the database — and client support is uneven, so a server should treat tasks as optional and check the client's declared capability per request, as the extension requires.
- `subscriptions/listen` is the one long-lived connection left; a server that never changes its tool list can simply acknowledge an empty subset and close, and that removes every ingress-timeout concern.
- A dual-era server that honours a legacy client's `initialize` may still mint a session (SDK-dependent); if it does, legacy clients get affinity requirements back. Whether the Python SDK v2 serves legacy clients with or without in-memory session state is not stated in the release notes (see Gaps).

### Gaps
- Python SDK v2: the documentation nav names pages "Deploy & scale" and "Serving legacy clients" under "Running your server" ([get-started](https://py.sdk.modelcontextprotocol.io/get-started/)), but the fetched page carried only the navigation. Whether legacy sessions are stored in process memory (affinity needed) or avoided entirely could not be confirmed. This is the single most important operational detail to verify in the SDK docs before fixing a replica count above one.
- No primary source states which clients implement the tasks extension; the spec points to a client matrix that was not fetched.

## Key question 4: Deployment patterns — own deployment vs sidecar, ingress, TLS, timeouts, health checks, observability

### Takeaway
Every Kubernetes-oriented project and cloud vendor found deploys the MCP server as its own Deployment/Service behind a standard Ingress or Gateway with TLS at the edge; the "sidecar" that appears in practice is a transport proxy that wraps a stdio server into HTTP, not an application sidecar. No spec-level health endpoint exists (`ping` was removed; `server/discover` is mandatory and serves the purpose), and observability is standardized around W3C trace context in `_meta` plus OpenTelemetry semantic conventions for MCP.

### Cited Findings
**Deployment shape**
- ToolHive operator: on an `MCPServer` resource it "Creates a Deployment to run the server, Sets up a Service for exposure"; clients connect "through a standard Ingress or Gateway"; CRDs `MCPServer`, `MCPRemoteProxy` (proxies an external server via a proxy pod), `MCPServerEntry`, `VirtualMCPServer` (aggregates backends); shared configs `MCPOIDCConfig`, `MCPTelemetryConfig`, `MCPExternalAuthConfig`. [vendor] — [ToolHive Kubernetes operator intro](https://docs.stacklok.com/toolhive/guides-k8s/intro) (last updated 2026-10-06)
- ToolHive README: each server runs "in an isolated container" with ToolHive as "a proxy layer between clients and servers"; it accepts stdio, SSE and streamable-HTTP from servers, exposes unified endpoints, supports OIDC/OAuth, token exchange, per-request policy, and exports OTel traces and Prometheus metrics. [vendor] — [stacklok/toolhive](https://github.com/stacklok/toolhive)
- kmcp (kagent): "deploys your MCP server behind a dedicated Transport Adapter, acting as a control plane to provide features such as external traffic routing ... with support for multiple transport protocols"; supports stdio and Streamable HTTP; `MCPServer` CRD (`kagent.dev/v1alpha1`) with `spec.deployment` (image, port, cmd, args) and `spec.transportType`; documented access path for testing is `kubectl port-forward deploy/my-mcp-server 3000`. [vendor] — [kagent kmcp introduction](https://kagent.dev/docs/kmcp/introduction); [kmcp deploy server](https://kagent.dev/docs/kmcp/deploy/server)
- Azure Container Apps (Microsoft, page dated 2026-02-19, updated 2026-03-25): standalone container app with HTTPS ingress and automatic TLS termination; "a minimum of one replica is recommended for interactive MCP use" (scale-to-zero caveat); ingress `transport` stays `auto`/`http`: "There's no special MCP transport value"; CORS policy needed for VS Code/browser clients; optional built-in Entra ID auth. The platform-managed variant still speaks protocol `2025-03-26`. [vendor] — [Host MCP servers on Azure Container Apps](https://learn.microsoft.com/azure/container-apps/mcp-overview)
- Azure API Management can front "an existing MCP-compatible server" with policies for access and authentication; Streamable HTTP "uses the /mcp endpoint and replaces the deprecated HTTP + SSE transport". [vendor] — [Azure API Management MCP server overview](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview)
- AWS pattern (community example, no official AWS page found): Lambda + API Gateway HTTP API v2 + Lambda Web Adapter with `StreamableHTTPServerTransport`, "stateless by design — each request creates a fresh MCP server + transport instance with no session state". [practice] — [mcpcat.io, Building a serverless MCP server](https://mcpcat.io/guides/building-serverless-mcp-server)
- Cloudflare Workers: stateless `createMcpHandler`, URL pattern `.../workers.dev/mcp`. [vendor] — [Cloudflare Agents, MCP transport](https://developers.cloudflare.com/agents/model-context-protocol/transport/)

**Ingress, buffering, timeouts**
- Spec: servers **[SHOULD]** send `X-Accel-Buffering: no` on SSE responses; keep-alive comment lines are encouraged on long streams to survive "intermediaries or client idle timeouts". — [Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- nginx in front of an MCP server (blog, 2025-11-12, Jörg Thalheim): `proxy_buffering off`, `proxy_set_header X-Accel-Buffering "no"`, HTTP/1.1 upstream, `proxy_read_timeout 3600s`, `proxy_send_timeout 3600s`, because the default 60 s read timeout kills idle SSE streams. [practice, pre-2026-07-28 but transport-level and still valid for SSE] — [Configuring nginx for n8n MCP servers with Claude Code](https://blog.thalheim.io/2025/11/12/configuring-nginx-for-n8n-mcp-servers-with-claude-code/)
- Claude Code reconnects HTTP/SSE servers "with exponential backoff (up to 5 attempts) on mid-session drops"; stdio servers get "No automatic reconnection on disconnect". [vendor] — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)

**Health checks**
- `server/discover` is a **[MUST]**-implement RPC advertising supported versions, capabilities and identity; `ping` was removed in 2026-07-28. — [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog); [Versioning 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)

**Observability**
- SEP-414 (Final; created 2025-04-25, author Adrian Cole): `_meta` keys `traceparent`, `tracestate`, `baggage` follow W3C Trace Context/Baggage and are an exception to the DNS-prefix rule; reference implementations include the Python SDK (PR #1693), C# SDK, OpenInference, Envoy AI Gateway, Logfire and ToolHive. — [SEP-414](https://modelcontextprotocol.io/community/seps/414-request-meta)
- The 2026-07-28 base protocol reserves those three `_meta` keys and cites "OpenTelemetry semantic conventions for MCP". — [Base protocol 2026-07-28, `_meta`](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)
- The Logging feature is Deprecated since 2026-07-28 with migration path "Log to `stderr` for stdio transports; use OpenTelemetry for observability". — [Deprecated features registry](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)
- OTel attribute registry page for `mcp.*` lists `mcp.method.name`, `mcp.protocol.version`, `mcp.resource.uri`, `mcp.session.id`, with the notice that the conventions "Moved to the OpenTelemetry GenAI semantic conventions repository" (the entries on the old page are marked deprecated at that location; method values are "Development" stability). — [OTel semconv registry, MCP attributes](https://opentelemetry.io/docs/specs/semconv/registry/attributes/mcp/); new home: [open-telemetry/semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai)
- Python SDK v2 documentation has an "OpenTelemetry" page under "Running your server". [vendor] — [py.sdk.modelcontextprotocol.io get-started](https://py.sdk.modelcontextprotocol.io/get-started/)
- Vendor guidance on span naming (`{mcp.method.name} {target}`, e.g. `tools/call echo`) comes from Elastic's blog and FastMCP docs, not from the fetched OTel pages. [practice/vendor] — [Elastic Observability Labs, MCP tracing](https://www.elastic.co/observability-labs/blog/mcp-tracing-opentelemetry-elastic-apm); [FastMCP telemetry](https://gofastmcp.com/v3/servers/telemetry)

### Inferences
- "Own deployment vs sidecar": for a server that is itself the application's interface to PostgreSQL there is nothing to be a sidecar *of*; the sidecar pattern in ToolHive/kmcp exists to put an HTTP face on a stdio-only server, which a Streamable HTTP server does not need.
- The spec's own `X-Accel-Buffering` hint is the one ingress-specific rule; the nginx-ingress annotations that implement it (`proxy-buffering: off`, read timeout) are standard. If the server returns plain JSON for every tool call and refuses subscriptions, no stream is ever open long enough for a timeout to matter.
- A readiness probe can POST `server/discover` with the mandatory headers; a liveness probe should stay at the HTTP layer (any 2xx/4xx from the endpoint) so that a database outage does not restart the pod in a loop. No source prescribes this; it follows from `ping` being gone and `server/discover` being mandatory.
- The deprecation of the Logging feature is a signal: the server should log to stderr/stdout for the platform (Kubernetes log collection) and emit OTel traces carrying the `traceparent` the client sends, not rely on `notifications/message`.

### Gaps
- The exact MCP span/metric definitions in the new GenAI semconv repository (file paths, stability, metric names) were not retrievable; only the attribute names from the old registry page and SEP-414 are confirmed.
- No official Kubernetes guidance (from the MCP project, ToolHive or kmcp docs fetched) on liveness/readiness probes for MCP servers was found; the probe design above is an inference.
- ToolHive's transport concept page returned 404; details of its stdio-to-HTTP proxy mode come only from the README summary.

## Key question 5: Local use — stdio started by the client vs a remote HTTP server; connecting a local client to a server in a cluster

### Takeaway
Both target clients speak Streamable HTTP natively (Claude Code recommends it; Mistral Vibe supports `http`/`streamable-http`/`stdio` but no OAuth), so a remote HTTP server with a static bearer header works for both today; stdio is the spec's recommended shape for a purely local server but ties credentials to the workstation environment, and the documented ways to reach an in-cluster server from a workstation are `kubectl port-forward` or an Ingress/Gateway with authentication.

### Cited Findings
- Claude Code transports: HTTP ("Recommended for remote MCP servers", OAuth 2.0 supported, `--header "Authorization: Bearer ..."`), SSE (deprecated; "Claude Code tries HTTP first and automatically switches to SSE if needed (v2.1.265+)"), stdio (`claude mcp add ... -- <command>`, 30-minute idle timeout, no auto-reconnect), WebSocket (`"type":"ws"`). Config files `.mcp.json` (project scope, committed) and `~/.claude.json`; `${VAR}` and `${VAR:-default}` expansion in URL and headers. [vendor] — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- Claude Code dynamic auth: `headersHelper` runs a script "fresh on each connection", 10 s timeout, re-run once on `401`/`403` — intended "For Kerberos, short-lived tokens, or internal SSO". [vendor] — same page
- Claude Code protocol eras: "v1 Runtime: MCP TypeScript SDK 1.x (default in most sessions)"; "v2 Runtime: MCP TypeScript SDK 2.0 (supports MCP protocol revision 2026-07-28)", enabled with `MCP_SDK_GENERATION=v2`; `MCP_PROTOCOL_NEGOTIATION=legacy` disables negotiation. [vendor] — same page
- Mistral Vibe `config.toml` `[[mcp_servers]]`: `transport` is one of `http`, `streamable-http`, `stdio`; HTTP fields `url`, `headers`, `api_key_env`, `api_key_header`, `api_key_format` (e.g. `"Bearer {token}"`); stdio fields `command`, `args`, `env`; `startup_timeout_sec`, `tool_timeout_sec`; tools appear as `{server_name}_{tool_name}`; known limitation: "the CLI does not yet support MCP servers that require OAuth authentication"; no SSE; no protocol version stated. [vendor] — [Mistral Vibe, MCP servers](https://docs.mistral.ai/vibe/code/cli/mcp-servers)
- Spec on stdio: the client launches the server as a subprocess; the server **[MUST NOT]** write anything but MCP messages to stdout; the client **[SHOULD]** shut down by closing stdin, then SIGTERM/SIGKILL; the server **[SHOULD]** exit on EOF; "If the server process exits unexpectedly, the client **SHOULD** restart it." — [stdio 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)
- Spec on auth for stdio: STDIO implementations **[SHOULD NOT]** use the HTTP authorization framework "and instead retrieve credentials from the environment". — [Base protocol 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)
- Security best practices on local servers: clients with one-click local configuration **[MUST]** show the exact command and get consent; servers run "with the same privileges as the client"; recommended sandboxing; local servers **[SHOULD]** use stdio or, over HTTP, require a token or use Unix sockets. — [Security best practices 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)
- Claude Code stdio examples use `npx -y ...` launchers; `uvx` is the Python equivalent but is not named on the page. [vendor] — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- kmcp documents `kubectl port-forward deploy/my-mcp-server 3000` and then connecting the MCP Inspector to `http://127.0.0.1:3000/mcp` as the way to reach a deployed server. [vendor] — [kmcp deploy server](https://kagent.dev/docs/kmcp/deploy/server)
- ToolHive: clients connect "through a standard Ingress or Gateway", with OIDC via `MCPOIDCConfig`. [vendor] — [ToolHive Kubernetes operator intro](https://docs.stacklok.com/toolhive/guides-k8s/intro)
- Azure: "You must configure a CORS policy if VS Code or browser-based clients access your MCP server." [vendor] — [Azure Container Apps MCP overview](https://learn.microsoft.com/azure/container-apps/mcp-overview)
- Community docker-compose examples all follow the same shape: one `mcp-server` service on the official Python SDK (`mcp==2.0.0` in one), Streamable HTTP, reachable at `http://localhost:8000/mcp` after `docker compose up -d --build`. [practice] — [example-mcp-server-streamable-http on Glama](https://glama.ai/mcp/servers/@yigitkonur/example-mcp-server-streamable-http/blob/b2e3ae2ad02123d178fa927b7f26d8c833a2d42d/docker-compose.dev.yml); [mcp-server-http-streamable README](https://glama.ai/mcp/servers/@douglasqsantos/mcp-server-http-streamable/blob/cfa009279e9d7b7d2eeaedc5007c3bdf847187e8/README.md)

### Inferences
- Trade-off for a single user who also runs it locally: a stdio server is simplest to start (`uvx previously-mcp` or `docker run -i`), has no network surface and no Origin/TLS/auth work — but it needs a PostgreSQL connection string in the workstation environment, which for customer data moves the trust boundary from "the cluster" to "the laptop". A remote HTTP server keeps credentials in the cluster and makes the transport the trust boundary, which is what the brief asks for.
- The same package can offer both: an entry point that runs stdio (for local development against a local Postgres) and an ASGI app for Streamable HTTP (for the cluster). The spec treats these as two bindings of one protocol, and the Python SDK runs both from one `MCPServer` object.
- Today's reach-in model (`kubectl exec` into a tool pod) extends naturally to `kubectl port-forward svc/previously-mcp 8000:8000` with the server bound inside the cluster only — no Ingress, no public TLS, authentication borrowed from the kubeconfig. Port-forward has no documented support for long SSE streams and is one-user, one-session; for a JSON-only server that is acceptable.
- Mistral Vibe's missing OAuth support is decisive against OAuth as the only auth method: a static bearer token (or a `headers` entry) is the lowest common denominator across both clients. Claude Code's `headersHelper` could mint short-lived tokens, Vibe cannot.
- Claude Code defaults to the v1 (legacy) runtime, so the server must answer `initialize` — any server built on Python SDK v2 does, but a hand-rolled 2026-07-28-only server would fail for Claude Code unless the user sets `MCP_SDK_GENERATION=v2`.

### Gaps
- No documentation was found on how `kubectl port-forward` behaves with long-lived SSE streams (it is a TCP-level forward; behaviour follows from that, but no source says so).
- Tunnels (Cloudflare Tunnel, Tailscale, SSH `-L`) as a middle ground were not researched; only port-forward and Ingress appear in the MCP-specific sources.
- Mistral Vibe's protocol revision (legacy vs modern) is not documented; assume legacy (`initialize`) until measured.

## Key question 6: Gateways and proxies (MCP gateways, mcp-remote) — what they are for and whether they are advisable

### Takeaway
mcp-remote exists to give stdio-only or OAuth-less clients access to remote HTTP servers and its own README calls it a temporary bridge; MCP gateways (ToolHive, kmcp, Azure APIM, Cloudflare, Envoy AI Gateway and a crowd of commercial products) centralize auth, routing, policy and telemetry across many servers, and the 2026-07-28 headers were designed for them — for a single server with two clients they add a moving part with little to route.

### Cited Findings
- mcp-remote (geelen): "Connect an MCP Client that only supports local (stdio) servers to a Remote MCP Server"; bridges stdio to Streamable HTTP and SSE (`--transport http-first|sse-first|http-only|sse-only`); `--header`/`--header-file`; full OAuth flow with tokens in `~/.mcp-auth/mcp-remote-v1/`, device-code and client-credentials grants; `--allow-http` for private networks; the README states that modern clients increasingly support remote servers natively, "making mcp-remote a temporary bridge solution". [vendor] — [geelen/mcp-remote](https://github.com/geelen/mcp-remote)
- Spec security section on proxies: the "stdio Transport Security in Proxy Scenarios" attack applies to architectures "where a separate proxy service manages stdio connections and can spawn MCP servers as child processes", giving XSS an escalation path to RCE; proxies **[SHOULD]** sandbox spawned processes and log all stdio use. — [Security best practices 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)
- Spec: "MCP Proxy Server" (one that fronts third-party APIs as a single OAuth client) **[MUST]** implement per-client consent to avoid confused-deputy attacks. — same page
- Spec rationale for the routing headers: intermediaries "(load balancers, gateways, observability tooling) can route and inspect requests without parsing the body"; intermediaries that enforce policy on headers **[SHOULD]** verify that the protocol version requires header-body validation and reject older requests. — [Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- ToolHive positions itself as the proxy/gateway layer: "isolated container", OIDC/OAuth SSO, token exchange, "Per-request identity and access policy enforcement", OTel + Prometheus export, auto-configuration of Claude Code/Cursor/Copilot; `VirtualMCPServer` aggregates backends behind one endpoint. [vendor] — [stacklok/toolhive](https://github.com/stacklok/toolhive); [ToolHive K8s intro](https://docs.stacklok.com/toolhive/guides-k8s/intro)
- Azure API Management "expose[s] an existing MCP-compatible server ... via API Management" with policies for access control and authentication. [vendor] — [Azure APIM MCP server overview](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview)
- Commercial gateway round-ups (Zuplo, obot.ai, Maxim, NeuralTrust) argue a gateway "stops being optional" at "fifteen of them across four teams" and name Portkey, Cloudflare, Kong, Microsoft, AWS Bedrock AgentCore, Lunar.dev, IBM ContextForge, MCPJungle, MintMCP, Docker, Zuplo. These are vendor marketing pages; the scale argument is theirs. [practice/vendor] — [Zuplo, what the best MCP gateways do in 2026](https://zuplo.com/blog/what-the-best-mcp-gateways-do-in-2026); [obot.ai, 13 best MCP gateways](https://obot.ai/blog/the-13-best-mcp-gateways-for-enterprise-teams/)

### Inferences
- mcp-remote is not needed for Claude Code (native HTTP + OAuth + headers). It would be needed for Mistral Vibe only if the server demanded OAuth, because Vibe lacks OAuth; a static bearer token avoids the proxy entirely. Running mcp-remote adds a Node process per client and a token cache on the workstation.
- A gateway earns its place when there are many servers, many users, or a policy layer the servers themselves cannot provide. One server, one maintainer, two clients: the Ingress (or port-forward) is the gateway, and the server's own token check is the policy. A gateway can be added later without changing the server, because the headers that gateways route on are already mandatory in the protocol.
- The one gateway function that is hard to retrofit is audit: if every tool call must be attributable to a person, the server has to log the authenticated principal itself from day one, rather than hoping a gateway will do it later.

### Gaps
- No independent (non-vendor) assessment of gateway reliability or overhead was found; every gateway source is a vendor.

## Recommendations for the two hosting yardsticks, with counter-arguments

### Takeaway
Build one Python server on the official SDK v2 that exposes both bindings — stdio for a local developer loop and Streamable HTTP (JSON responses, dual-era, bearer-token auth, `Origin` check) for the cluster — deploy it as its own Deployment with no session affinity, reach it first by `kubectl port-forward` and only later through an Ingress with TLS and a token; the docker-compose yardstick is the same container plus Postgres, published on localhost or behind one reverse proxy.

### Cited Findings
- Everything above; the specific facts this section leans on are: statelessness and explicit handles ([Base protocol 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)); POST-only endpoint, mandatory headers, `Origin` 403, localhost binding, `X-Accel-Buffering` ([Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)); dual-era serving and Python SDK v2 release date 2026-07-28, 4 MiB body cap, v1 in maintenance ([python-sdk v2.0.0](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.0.0)); Claude Code defaults to the legacy v1 runtime and recommends HTTP with `--header` ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)); Mistral Vibe supports `streamable-http` with `api_key_*` headers but not OAuth ([Mistral Vibe MCP servers](https://docs.mistral.ai/vibe/code/cli/mcp-servers)); kmcp documents port-forward as the access path ([kmcp deploy](https://kagent.dev/docs/kmcp/deploy/server)); Azure recommends at least one replica and no special ingress transport ([Azure Container Apps MCP overview](https://learn.microsoft.com/azure/container-apps/mcp-overview)); the stdio auth rule "retrieve credentials from the environment" ([Base protocol 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)); tasks need durable storage ([Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview)).

### Inferences
**Kubernetes (kup6s: cdk8s, ArgoCD, CloudNativePG)**
1. Own Deployment `previously-mcp` with the server as an ASGI app (uvicorn), `replicas: 1` initially, ClusterIP Service, pointing at the CNPG `-rw` (or `-ro` for a read-only tool set) Service. No sidecar: there is no stdio process to wrap.
2. Stage A access: `kubectl port-forward` from the workstation; server bound in-cluster only; `Origin` validation on; a bearer token still required so that a port-forward on a shared machine is not an open door. Matches today's `kubectl exec` trust model and needs no Ingress, cert or public DNS.
3. Stage B access (when Vibe or a second machine needs it without kubeconfig): Ingress with TLS, nginx annotations `proxy-buffering: off` and raised read timeout; auth by bearer token checked in the server (works for both clients), OIDC later only if Vibe gains OAuth or Claude Code's `headersHelper` is used.
4. Keep responses JSON (no SSE) unless a tool needs progress; decline `subscriptions/listen` by acknowledging an empty filter. Then no long-lived connection exists and replicas can be raised without affinity, provided the SDK's legacy-session handling is verified (Gap above).
5. Readiness probe: POST `server/discover` with the three headers; liveness: TCP or any HTTP answer. Log to stdout for the cluster; propagate `traceparent` from `_meta` into OTel if tracing is wanted.
6. Audit: log the authenticated principal and `Mcp-Name` per call in the server; a gateway can be inserted later because the routing headers already exist.

Counter-arguments:
- Port-forward is one user, one session, and dies with the terminal; if the maintainer uses the server all day from two clients, the Ingress is less friction than it looks. Reply: Stage B is a cdk8s change, not a server change.
- A bearer token is a static secret on the workstation; OAuth with short-lived tokens is the spec's preferred model. Reply: Vibe cannot do OAuth today, and the spec's own stdio guidance accepts environment credentials; rotate the token, scope it to the server, and revisit when both clients support OAuth.
- A single replica is a single point of failure. Reply: the server holds no state, so a restart costs one failed call that the client retries; raising replicas is a knob, not a redesign.
- Running the server with the Claude Code v1 (legacy) runtime means the SDK will mint sessions for that client if its legacy path does; this is the one fact to measure before `replicas: 2`.

**One host with docker-compose**
1. Two services: `postgres` and `mcp` (same image as in the cluster), `mcp` published as `127.0.0.1:8000:8000`, connection string via environment, bearer token via environment or Docker secret.
2. Clients on the same host connect to `http://127.0.0.1:8000/mcp` with the token header; the server's `Origin` check and localhost binding cover the DNS-rebinding case the spec warns about.
3. For remote clients add one reverse proxy (Caddy or Traefik) for TLS and the same buffering/timeout settings; no gateway, no mcp-remote.
4. Alternative for a strictly single-user box: the client launches `docker run --rm -i ... previously-mcp --stdio` with the DB URL in `env`; zero network surface. Reply to the obvious objection: this puts the DB credential in the client config, which is acceptable only when the host *is* the trust boundary (same machine, same user), not for customer data on a shared host.

Counter-arguments:
- Compose has no CNPG and no operator for backups or failover; that is the point of the yardstick — the MCP server adds nothing a plain Postgres container cannot serve, so the design passes the simplicity check.
- Publishing on `127.0.0.1` makes "remote clients" a separate step; some will want `0.0.0.0` with a token. The spec's SHOULD on localhost binding is for local servers; behind a TLS proxy the token is the control, and `Origin` still applies.

**Rejected or deferred**
- WebSocket (`ws`) transport: client-specific, dormant SEP, no benefit for request/response.
- HTTP+SSE: deprecated with removal eligibility pending; Claude Code only falls back to it.
- Sidecar (ToolHive/kmcp transport adapter): solves a problem this server does not have.
- Tasks extension: defer until a tool runs longer than Claude Code's idle timer (5 min HTTP) without progress; when needed, task rows live in Postgres.
- mcp-remote and commercial gateways: not needed at this scale; revisit only for OAuth-only clients or multi-tenant audit.

### Gaps
- The verification that the Python SDK v2 serves legacy (`initialize`) clients without process-local session state is the one open measurement before any replica count above one; the SDK docs name the page ("Serving legacy clients") but it was not fetched.
- Python 3.14 compatibility of `mcp` 2.x: the README states "Python 3.10+" ([python-sdk README](https://github.com/modelcontextprotocol/python-sdk)); no source confirms testing on 3.14.
- Whether Mistral Vibe sends the 2026-07-28 headers or speaks the legacy era is undocumented; both clients should be assumed legacy until a request is captured.
