## Key question 2: Is the protocol stateless now — no `initialize`, no sessions, no `Mcp-Session-Id`, version and capabilities per request in `_meta`, `server/discover` mandatory? How exactly does it work?

### Takeaway
Yes, all of it, in the normative text of 2026-07-28 (SEP-2567 and SEP-2575, both Final). `server/discover` is a MUST for servers and optional for clients. Two required `_meta` keys per request (`protocolVersion`, `clientCapabilities`), one SHOULD (`clientInfo`). Backward compatibility with `initialize`-era clients is explicitly specified as a "dual-era" server that a modern server MAY implement.

### Cited Findings
- Changelog major change 1: "Remove protocol-level sessions and the `Mcp-Session-Id` header from the Streamable HTTP transport. List endpoints … no longer vary per-connection. Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments (SEP-2567)." — [Changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog) [spec]
- Major change 2: "Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake. Every request now carries its protocol version and client capabilities in `_meta` (`io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`). Clients SHOULD identify themselves on each request (`io.modelcontextprotocol/clientInfo`), and servers SHOULD identify themselves in each result's `_meta` (`io.modelcontextprotocol/serverInfo`). Version mismatches return `UnsupportedProtocolVersionError` (SEP-2575)." — same page [spec]
- Major change 3: "Add `server/discover`: servers MUST implement this RPC … Clients MAY call it before any other request." — same page [spec]
- `_meta` per-request table: `protocolVersion` Required **Yes**; `clientInfo` Required **No**; `clientCapabilities` Required **Yes**; `logLevel` Required No. "A request missing any required field is malformed; the server MUST reject it with JSON-RPC error code `-32602` … On HTTP, the response status MUST be `400 Bad Request`." — [Basic overview, `_meta`](https://modelcontextprotocol.io/specification/2026-07-28/basic/index) [spec]
- "A server MUST NOT rely on capabilities the client has not declared. If processing a request requires a capability the client did not include … the server MUST return a `MissingRequiredClientCapabilityError` (`-32021`)." — same page [spec]
- Statelessness section: "Servers MUST NOT rely on prior requests over the same connection to establish context … State that needs to span multiple requests (e.g., long-running tasks, application-level handles) MUST be referenced by an explicit identifier the client passes on each request." and "an open connection, such as a STDIO process, is not a conversation or session." — same page [spec]
- `server/discover`: "Servers MUST implement it." Result fields: `supportedVersions`, `capabilities`, `_meta['io.modelcontextprotocol/serverInfo']` (SHOULD), optional `instructions`; result carries `ttlMs`/`cacheScope`. "Calling `server/discover` is optional for clients." On stdio, a dual-era client "SHOULD send `server/discover` first". — [Discovery page](https://modelcontextprotocol.io/specification/2026-07-28/server/discover) [spec]
- Version negotiation: "There is no negotiation handshake. Every request carries its protocol version, and the server accepts or rejects each request independently." Unsupported version → `UnsupportedProtocolVersionError` (`-32022`) with `data.supported`. — [Versioning and Compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) [spec]
- Era model: "Modern: … revision `2026-07-28` and later. Legacy: … `2025-11-25` and earlier. Dual-era: an implementation that supports both." "A server that wishes to support both legacy clients … and modern clients … MAY implement both behaviors." "A dual-era server MAY serve both eras concurrently on the same endpoint or process." Matrix row *Legacy client / Modern server*: "Fails. … Legacy clients have no fall-forward mechanism." Row *Legacy / Dual-era*: "Works." — same page [spec]
- Streamable HTTP: single POST endpoint; GET endpoint removed; each request MUST carry `MCP-Protocol-Version`, `Mcp-Method`, and (for `tools/call`, `resources/read`, `prompts/get`) `Mcp-Name` headers; header/body mismatch → `400` + `-32020 HeaderMismatch`. A modern-only server receiving legacy traffic "SHOULD" answer GET/DELETE with `405`, ignore `Mcp-Session-Id`, ignore `Last-Event-ID`. — [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) [spec]
- stdio: "There is no header layer"; `_meta` inline; the server "MUST NOT write JSON-RPC requests to stdout"; cancellation via `notifications/cancelled`; "If the server process exits unexpectedly, the client SHOULD restart it. Because the protocol is stateless, any in-flight requests are simply lost and the client can retry them." Backward-compat probe: `server/discover` first; "The fallback MUST NOT be keyed to one specific error code." — [stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio) [spec]
- Removed alongside (major change 5): `ping`, `logging/setLevel`, `notifications/roots/list_changed`. Replaced (major change 4): HTTP GET stream and `resources/subscribe`/`unsubscribe` by `subscriptions/listen`, a long-lived POST-response stream for opted-in change notifications. — [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) [spec]
- Non-normative "Stateful Tools" guidance: "The protocol has no concept of a state handle; from the wire's perspective a handle is an ordinary string in a tool result and an ordinary argument to subsequent tool calls." Design advice: validate authorization against the handle per call; opaque; stated lifetime; explicit expiry errors. — [Tools page](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) [spec, non-normative section]

### Inferences
- §8.1 of the record is confirmed to the letter, with one precision: `server/discover` is mandatory **to implement** (server side); clients are free to skip it.
- A server for two clients of unknown era (see key question 10) should be dual-era; the spec explicitly allows serving both eras on one endpoint or process, and the Python SDK 2.x does this by default (key question 10).

### Gaps
- None for the normative content.

## Key question 3: MRTR — what is it, how does it replace server-to-client requests, status?

### Takeaway
MRTR (SEP-2322, Final) is normative in 2026-07-28 and is the **only** way left for a server to ask the client anything: the server returns `resultType: "input_required"` with `inputRequests` (a map of `elicitation/create`, `sampling/createMessage`, or `roots/list` request objects) and an opaque `requestState`; the client retries the same request with a **new** JSON-RPC id, `inputResponses`, and the echoed `requestState`. Only `tools/call`, `prompts/get`, `resources/read` may return it. `requestState` is attacker-controlled input and MUST be integrity-protected when it influences logic.

### Cited Findings
- "Servers MUST send server-to-client requests (such as `roots/list`, `sampling/createMessage`, or `elicitation/create`) using the MRTR pattern. The previous pattern of server-initiated requests is no longer supported. This is a breaking change." — [MRTR page](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr) [spec]
- Types: `InputRequests` = map, keys server-assigned, values `ElicitRequest` | `CreateMessageRequest` | `ListRootsRequest`; `InputResponses` = map with matching keys; `InputRequiredResult` = `inputRequests` (optional) + `requestState` (optional, "opaque string meaningful only to the server"). — same page [spec]
- "Servers MUST include at least one of `inputRequests` or `requestState` in every `InputRequiredResult`." "Servers MUST NOT send an `inputRequests` that the client has not declared support for in its capabilities." "Servers MUST NOT assume that clients will fulfill the `inputRequests` or retry." — same page [spec]
- "If a client request contains a `requestState` field, servers MUST treat `requestState` as an attacker-controlled input. If `requestState` influences authorization, resource access, or business logic, servers MUST protect its integrity (e.g. HMAC or AEAD) and MUST reject state that fails verification." Replay guidance: include principal, short TTL, and a digest of the originating request; single-use must be enforced server-side. — same page [spec]
- Client side: "MUST echo back the exact value" of `requestState`; "The JSON-RPC `id` MUST be different between the initial request and the retry, as they are independent requests." — same page [spec]
- Supported on `prompts/get`, `resources/read`, `tools/call`: "Servers MUST NOT send `InputRequiredResult` responses on any other client requests." — same page [spec]
- Every result carries a required `resultType`: `"complete"` or `"input_required"`; extensions may add values (Tasks adds `"task"`); "A `resultType` of any value unrecognized by the client MUST be considered invalid"; absent `resultType` from older servers MUST be treated as `"complete"`. — [Basic overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/index) [spec]
- Results produced by an MRTR retry "MUST NOT be cached" and interim `input_required` results "carry no caching hints". — [Caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching) [spec]
- Error handling: missing requested input → server "SHOULD respond with a new `InputRequiredResult` requesting the missing information again, rather than returning an error." — [MRTR page](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr) [spec]
- SEP-2322 "Multi Round-Trip Requests", Standards Track, created 2026-02-03, status **Final**. — [SEP index](https://modelcontextprotocol.io/seps)
- Python SDK 2.0.0 (2026-07-28): "At 2026-07-28 the server can no longer call the client, so tools return the question instead. A `Resolve(fn)` parameter is filled by your function invisibly to the model and can put a question to the user; one tool body serves both eras." — [python-sdk release v2.0.0](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.0.0) [SDK]

### Inferences
- §8.4 of the record describes the wire exactly (`resultType: "input_required"`, `inputRequests`, `inputResponses`, `requestState`). One wording correction: MRTR does not replace **elicitation**; it replaces the **transport pattern** of server-initiated requests. `elicitation/create` lives on as a request object inside `inputRequests`. (See key question 5.)
- A blocking question needs the client to declare the `elicitation` capability on the request; otherwise the server MUST NOT ask, and the tool has to fail with a tool execution error that names the missing parameter. That fallback belongs in the design.
- `requestState` for the triage/approval tools must be HMAC- or AEAD-protected if it carries anything the server acts on; the simplest compliant design encodes nothing but an opaque `event.id`/`job.id` that the server re-validates.

### Gaps
- Whether Claude Code and Mistral Vibe declare `elicitation` (form, url) in modern mode was not found in any primary source (see key question 10).

## Key question 4: The Tasks extension — status and semantics

### Takeaway
Tasks are an **official extension** `io.modelcontextprotocol/tasks` (SEP-2663, Final; dated extension revision `2026-07-28` exists), polled through `tasks/get`, with `tasks/update` for input and `tasks/cancel`; `tasks/result` and `tasks/list` are gone. A server MAY return a task handle without per-request opt-in, **but only to a client that declared the extension capability in that request's `_meta`**. As of 2026-10-09 the Python SDK has not implemented it (issue open), and the official client matrix lists no client with Tasks support.

### Cited Findings
- Changelog major change 6: "Move experimental tasks out of the core protocol and into an official extension (`io.modelcontextprotocol/tasks`). The redesigned extension replaces the blocking `tasks/result` method with polling via `tasks/get` and a new `tasks/update` for client-to-server input, removes `tasks/list`, and allows servers to return task handles unsolicited without per-request opt-in (SEP-2663)." — [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) [spec]
- Extension spec, dated revision 2026-07-28: methods `tasks/get`, `tasks/update`, `tasks/cancel`; discriminator `resultType: "task"`; Task fields `taskId`, `status` ("working" | "input_required" | "completed" | "cancelled" | "failed"), `statusMessage`, `createdAt`, `lastUpdatedAt`, `ttlMs` (null = unlimited), `pollIntervalMs`; `input_required` carries `inputRequests`, `completed` carries `result`, `failed` carries `error`. "A server that has negotiated this extension MAY return `CreateTaskResult` in lieu of a standard result." "A server MUST NOT return `CreateTaskResult` to a client that did not include the extension capability on its request." "A server MUST NOT return `CreateTaskResult` until the task is durably created — that is, until a `tasks/get` for the returned `taskId` would resolve." "Clients SHOULD respect the `pollIntervalMs`." — [Tasks extension spec](https://tasks.extensions.modelcontextprotocol.io/specification/draft/tasks) (the fetched document identifies itself as the 2026-07-28 dated revision; a draft also exists) [extension spec]
- Client declares `"extensions": {"io.modelcontextprotocol/tasks": {}}` inside `_meta["io.modelcontextprotocol/clientCapabilities"]` per request; server declares it in `server/discover` capabilities. — same page and [Extensions overview](https://modelcontextprotocol.io/docs/extensions/overview)
- SEP-2663 "Tasks Extension", Extensions Track, created 2026-04-27, **Final**; the earlier in-core SEP-1686 "Tasks" (2025-10-20) is also listed Final (it is the 2025-11-25 design that 2026-07-28 moved out). — [SEP index](https://modelcontextprotocol.io/seps)
- Python SDK v2.0.0 (2026-07-28): "The tasks extension (SEP-2663) is not part of this release." v2.2.0 (2026-09-07): "The tasks extension (SEP-2663), DPoP (SEP-1932) and the `jwt-bearer` grant are not implemented yet; … ROADMAP.md tracks them." — [python-sdk releases](https://github.com/modelcontextprotocol/python-sdk/releases) [SDK]
- python-sdk ROADMAP: Tasks "deferred at 2.0 because the 2026-07-28 design is wire-incompatible with the earlier in-core Tasks", tracked in #2806. — [ROADMAP.md](https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/main/ROADMAP.md) [SDK, undated, read 2026-10-09]
- Issue #2806 "Implement SEP-2663: Tasks Extension": **OPEN**, last updated 2026-10-01 (read via `gh` on 2026-10-09). — [python-sdk issue 2806](https://github.com/modelcontextprotocol/python-sdk/issues/2806) [SDK]
- The official extension support matrix has columns for MCP Apps, OAuth Client Credentials, Enterprise Auth, Skills — **no Tasks column**; Claude Code is not listed as a row at all (Claude web and Claude Desktop are, with MCP Apps only). — [Extension support matrix](https://modelcontextprotocol.io/extensions/client-matrix) [community-maintained page]
- Open SEP-2694 "Resumable Task Event Streams" (proposal, created 2026-05-06). — `gh pr list` on 2026-10-09, [PR #2694](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2694) [SEP/draft]

### Inferences
- §8.5 is correct about the spec. "Unaufgefordert" must be read as "without per-request opt-in" — the client still has to advertise the extension in every request, and a server that returns `resultType: "task"` to a client that did not is non-conformant.
- Today, with Python SDK 2.3.0 lacking the extension and no listed client supporting it, `start_import` cannot rely on Tasks. The conformant and SDK-available design is the record's own §8.1 pattern: return a `job.id` in `structuredContent` and offer a poll tool; the Tasks extension can be layered on later, additively, for clients that declare it.

### Gaps
- Whether the TypeScript SDK (which Claude Code is likely built on) implements the Tasks extension was not checked; no primary source for Claude Code's Tasks support was found.

## Key question 5: Elicitation — status, forms, URL mode

### Takeaway
Elicitation is alive and not deprecated; it is now carried inside MRTR `inputRequests`. Two modes: `form` (flat object schema of primitives; defaults; single/multi-select enums) and `url` (out-of-band; the client only consents and opens the URL). The 2025-11-25 `notifications/elicitation/complete` and `elicitationId` were removed; correlation now rides on `requestState`.

### Cited Findings
- "Servers MAY request information from a user during the processing of a client request, by sending an `InputRequiredResult` containing an `elicitation/create` request." Client capability per request: `"elicitation": {"form": {}, "url": {}}`; empty object = form only; "Servers MUST NOT send elicitation requests with modes that are not supported by the client." — [Elicitation page](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation) [spec]
- Form schema: "limited to flat objects with primitive properties only" — string (formats `email`, `uri`, `date`, `date-time`), number/integer, boolean, enums incl. `oneOf`/`anyOf` with `const`+`title`, multi-select arrays; defaults supported. "complex nested structures, arrays of objects (beyond enums), and other advanced JSON Schema features are intentionally not supported." — same page [spec]
- Actions: `accept` (with `content` in form mode, omitted in URL mode), `decline`, `cancel`. — same page [spec]
- URL mode: "introduced in the `2025-11-25` version … Its design and implementation may change in future protocol revisions." `accept` "does not mean that the interaction is complete"; on retry "the server determines from the echoed `requestState` (or its own stored state) whether the out-of-band interaction has completed". — same page [spec]
- Changelog minor change 11: "Remove the `notifications/elicitation/complete` notification and the `elicitationId` field of URL mode elicitation requests, both introduced in `2025-11-25`. … Servers needing to correlate an elicitation across retries encode their own identifier in `requestState`." — [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) [spec]
- Security: "Servers MUST NOT use form mode elicitation to request sensitive information such as passwords, API keys …"; "Servers MUST bind elicitation requests to the client and user identity." — [Elicitation page](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation) [spec]
- Elicitation is not in the deprecated registry. — [Deprecated features](https://modelcontextprotocol.io/specification/2026-07-28/deprecated) [spec]
- Open SEP-2343 "Clarify that elicitation requires authorization for remote servers" (draft, security, created 2026-03-03). — `gh pr list` 2026-10-09, [PR #2343](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2343) [SEP/draft]

### Inferences
- A blocking triage question in Previously is a form-mode elicitation inside an `InputRequiredResult` on `tools/call`; the answer shape is restricted to a flat object of primitives, so a question whose answer is an `event.id` or an enum fits, a structured assertion does not.

### Gaps
- None in the spec. Client support in modern mode is the open question (key question 10).

## Key question 6: Deprecations — sampling, roots, logging

### Takeaway
All three are **Deprecated** (not removed) as of 2026-07-28 under a new feature-lifecycle policy (SEP-2596, SEP-2577): they remain functional for at least twelve months, earliest removal is the first revision released on or after **2027-07-28**, and new implementations SHOULD NOT adopt them. Migrations are exactly as the record states. Separately, several concrete methods are already **removed**: `ping`, `logging/setLevel`, `notifications/roots/list_changed`, server-initiated `sampling/createMessage` as a request (it survives only as an MRTR `inputRequests` entry).

### Cited Findings
- Registry rows (Deprecated in `2026-07-28`, SEP-2577): Roots → "Pass directories or files via tool parameters, resource URIs, or server configuration"; Sampling → "Integrate directly with LLM provider APIs"; Logging → "Log to `stderr` for stdio transports; use OpenTelemetry for observability"; each "Earliest removal: First revision released on or after 2027-07-28". Also deprecated: Dynamic Client Registration (PR #2858) → Client ID Metadata Documents; `includeContext: "thisServer"/"allServers"` (follows Sampling); HTTP+SSE transport (since 2025-03-26; "Three months after SEP-2596 reaches Final"). "Removed: No features have been removed under this policy yet." — [Deprecated features registry](https://modelcontextprotocol.io/specification/2026-07-28/deprecated) [spec]
- Policy: deprecated features "remain in the specification for at least twelve months, or at least ninety days under the policy's expedited-removal exception"; "the actual removal is a Core Maintainer decision taken during release preparation and may happen later." — [Versioning page](https://modelcontextprotocol.io/specification/versioning) and registry [spec]
- Changelog "Deprecated" 1: "These features remain fully functional during the deprecation window but new implementations should not add support for them." — [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) [spec]
- Removed methods (major change 5): "Remove `ping`, `logging/setLevel`, and `notifications/roots/list_changed`. Log level is now set per-request via `io.modelcontextprotocol/logLevel` in `_meta`; servers MUST NOT emit `notifications/message` for requests that did not include this field." — same page [spec]
- SEP-2577 "Deprecate Roots, Sampling, and Logging", Standards Track, created 2026-04-14, **Final**. — [SEP index](https://modelcontextprotocol.io/seps)
- Python SDK deprecation page: Roots (`ctx.session.list_roots()`) → paths as tool arguments / resource URIs / `ListRootsRequest` in `InputRequiredResult`; server-initiated sampling (`ctx.session.create_message()`) → return `InputRequiredResult`; protocol logging (`ctx.log()` etc.) → `import logging` to stderr; `ping` → "removed from protocol entirely". Deprecated methods "fail with 'no back-channel' errors on modern connections". — [py.sdk deprecated features](https://py.sdk.modelcontextprotocol.io/deprecated/) [SDK]
- A C# SDK doc page states "In protocol revision 2026-07-28, the server-to-client `sampling/createMessage` request method is removed; the recommended way to ask the client to sample … is to throw InputRequiredException" — this describes the SDK's view of the wire (no server-initiated requests), consistent with the MRTR page; the *feature* Sampling is Deprecated, not Removed. — [C# SDK sampling docs](https://csharp.sdk.modelcontextprotocol.io/v2/concepts/sampling/sampling.html) [SDK]; authoritative: [registry](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)

### Inferences
- §8.2 is confirmed in substance and in the migration paths. Precision: sampling via MRTR `inputRequests` would still be technically possible until at least 2027-07-28, so "abgekündigt" is a policy fact, not a technical impossibility; the record's decision not to build it is the one the spec recommends ("new implementations should not add support").
- For logging, the stdio rule ("The server MAY write UTF-8 strings to `stderr` for any logging purposes") plus the per-request `logLevel` gate make stderr/OpenTelemetry the only design that works for every request.

### Gaps
- No official statement was found on which revision will actually remove the three features; the registry only gives eligibility.

## Key question 7: The extensions mechanism and the official extensions

### Takeaway
Extensions (SEP-2133, Final) are identified as `{vendor-prefix}/{name}`, advertised in the `extensions` map of client capabilities (per request, in `_meta`) and of server capabilities (`server/discover`), always opt-in, and evolve independently of the core. Official extensions today: MCP Apps (`io.modelcontextprotocol/ui`), Tasks (`io.modelcontextprotocol/tasks`), OAuth Client Credentials, Enterprise-Managed Authorization, Skills over MCP (`io.modelcontextprotocol/skills`), and MCP Server Cards (SEP-2127).

### Cited Findings
- "Extensions are identified using a unique extension identifier with the format: `{vendor-prefix}/{extension-name}` … Official extensions use the `io.modelcontextprotocol` vendor prefix"; third parties use reverse-DNS. — [Extensions overview](https://modelcontextprotocol.io/docs/extensions/overview) [spec docs]
- Negotiation: "Clients advertise extension support in `_meta["io.modelcontextprotocol/clientCapabilities"]` within each request"; "Servers advertise extension support in the `server/discover` response"; "Extensions are always disabled by default and require explicit opt-in from the developer." — same page
- "If one party supports an extension but the other does not, the supporting party MUST either revert to core protocol behavior or reject the request with an appropriate error. Extensions SHOULD document their expected fallback behavior." — [Versioning page, Extension Negotiation](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) [spec]
- Changelog minor change 1: "Add `extensions` field to `ClientCapabilities` and `ServerCapabilities`." — [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) [spec]
- Official repositories: `ext-auth` (OAuth Client Credentials; Enterprise-Managed Authorization), `ext-apps` (MCP Apps), `ext-skills` (Skills over MCP), plus MCP Tasks. Experimental extensions live in `experimental-ext-*` repos and must belong to a Working/Interest Group; graduation goes through an Extensions-Track SEP requiring "at least one reference implementation in an official SDK". — [Extensions overview](https://modelcontextprotocol.io/docs/extensions/overview)
- Lifecycle advice: "prefer using capability flags or versioning within the extension settings object rather than creating a new extension identifier. If a breaking change is unavoidable, use a new identifier (e.g., `io.modelcontextprotocol/my-extension-v2`)." — same page

## Key question 8: JSON Schema dialect, `$ref`/`$defs`, `ttlMs`/`cacheScope`, deterministic `tools/list` — real requirements?

### Takeaway
JSON Schema 2020-12 is the default dialect and MUST be supported; `inputSchema`/`outputSchema` accept any 2020-12 keyword including `$ref`/`$defs` (SEP-2106, SEP-1613), with network `$ref`s forbidden by default. `ttlMs` and `cacheScope` are a **MUST** on `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read` (SEP-2549). Deterministic `tools/list` ordering is a **SHOULD**, not a MUST.

### Cited Findings
- Minor change 10: "Loosen `inputSchema` and `outputSchema` to allow any JSON Schema 2020-12 keywords, and `structuredContent` to allow any JSON value. Add `$ref` resolution requirements and composition-keyword resource bounds (SEP-2106)." — [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) [spec]
- Dialect: "Default dialect: When a schema does not include a `$schema` field, it defaults to JSON Schema 2020-12"; "Implementations MUST support at least 2020-12". `$ref`: "Implementations MUST NOT automatically dereference `$ref` values that resolve to a network URI"; unresolved external `$ref` "SHOULD be rejected rather than silently treated as permissive". Composition keywords and `$defs`: implementations "SHOULD apply reasonable bounds". — [Basic overview, JSON Schema Usage](https://modelcontextprotocol.io/specification/2026-07-28/basic/index) [spec]
- Output schema: "Servers MUST provide structured results that conform to this schema. Clients SHOULD validate structured results against this schema." `structuredContent` "can be any JSON value … that conforms to the tool's `outputSchema`"; "a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block." — [Tools page](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) [spec]
- Caching: "Servers MUST include caching hints on results with `resultType: "complete"` returned by the following operations: `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read`." "Servers MUST provide a `ttlMs` value that is `>= 0`." `cacheScope` `"public"` (no user-specific data; shared caches may serve it) vs `"private"` (per authorization context). "Servers MUST apply the same `cacheScope` to all response pages." — [Caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching) [spec]
- Ordering: "Servers SHOULD return tools in a deterministic order … Deterministic ordering enables clients to reliably cache the tool list and improves LLM prompt cache hit rates when tools are included in model context." Also: the tool set "MUST NOT vary per-connection or as a side effect of other requests on the connection. The set MAY vary by the authorization presented on the request." — [Tools page](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) [spec]
- Tool names SHOULD be 1–128 chars of `[A-Za-z0-9_.-]`, case-sensitive, unique per server. — same page [spec]
- Error model: protocol errors (unknown tool, malformed request) as JSON-RPC errors; execution errors (validation, business logic) as `isError: true` results. Open SEP-2145 "Standardize `tools/call` failure reporting" (**in-review**, created 2026-01-23) would move unknown-tool and **output validation failures** into `isError: true` results too. — [Tools page](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) [spec]; [PR #2145](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2145) [SEP/in-review]
- `x-mcp-header` (SEP-2243) lets a tool parameter be mirrored into an `Mcp-Param-{Name}` HTTP header; stdio clients MAY ignore it. — [Tools page](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) [spec]
- SEP-2106 (created 2026-01-06) and SEP-1613 (2025-10-06) are Final; SEP-2549 "TTL for List Results" (2026-04-09) is Final. — [SEP index](https://modelcontextprotocol.io/seps)

### Inferences
- A shared `$defs.sources` with `minItems: 1` referenced via local `$ref` from every assertion shape is expressible and conformant; the schema must stay self-contained (no network `$ref`). Enforcement is a server-side MUST (the server must not emit non-conforming `structuredContent`); client-side validation is only a SHOULD, so the record's "schemaseitig durchsetzbar" holds for the server's own validator, not as a guarantee about what clients check.
- The record's "Pflicht" for `ttlMs`/`cacheScope` is right; the set is six operations, two of which (`server/discover`, `resources/read`) are not lists. The record's "Pflicht" for deterministic ordering overstates a SHOULD, though the reasoning it gives (prompt cache) is the spec's own.
- Customer-content lists (e.g. a resource read) are `cacheScope: "private"`; the tool list can be `"public"` only if identical for all callers.

### Gaps
- Tool annotations (`idempotentHint`, `readOnlyHint`, `destructiveHint`, `openWorldHint`) are mentioned on the tools page only as "Optional properties describing tool behavior"; their exact field list in the 2026-07-28 schema was not quoted and should be read from `schema/2026-07-28/schema.ts` before use.
