## Key question 1: The official SDK (`mcp`, modelcontextprotocol/python-sdk)

### Takeaway
`mcp` 2.3.0 (2026-10-02, MIT) implements the 2026-07-28 revision and negotiates back to every earlier one; it is a Tier 1 SDK maintained day to day by one Anthropic employee with Pydantic's Starlette/uvicorn maintainer as the second regular committer, releases a minor roughly monthly, and carries a published versioning, support and dependency policy.

### Inferences
- Bus factor: one person authored 84 of the last 100 commits, and the repository has no maintainers file. Anthropic employs that person, which is the strongest maintenance signal available, but the project should record this as a single-maintainer dependency and recheck the commit distribution at each review.
- Cadence since 2.0.0 is one minor per month with patches in between; combined with the policy that a floor raise may ship in a minor, `uv lock --upgrade` can pull a new `httpx2` or `starlette` floor at any monthly step. Renovate's weekly PR will show it.

### Gaps
- No page on the documentation site states the implemented spec revision; the statement lives in ROADMAP.md and the v2.0.0 release notes.
- I did not find a published list of named maintainers beyond the GitHub commit log and the Discord channel the release notes point to.

## Key question 3: Spec coverage of each (2026-07-28 features)

### Takeaway
Both implement the 2026-07-28 revision and serve legacy clients from the same server; the SDK's conformance baseline lists exactly three things it lacks (tasks extension, DPoP, jwt-bearer grant), while FastMCP ships the tasks extension as a separate package and a broader authorization catalogue, but has no publicly visible continuous conformance run.

### Cited Findings
- The 2026-07-28 revision: "Each request now travels on its own, carrying its protocol version, client identity, and client capabilities in `_meta`." Sessions, the `initialize`/`initialized` handshake and the `Mcp-Session-Id` header are retired (SEP-2575, SEP-2567); optional `server/discover`; MRTR replaces server-initiated elicitation, sampling and roots (`resultType: "input_required"`, `inputResponses`, SEP-2322); `Mcp-Method` and `Mcp-Name` headers required on Streamable HTTP (SEP-2243); `ttlMs`/`cacheScope` on list and read responses (SEP-2549); tasks move to the `io.modelcontextprotocol/tasks` extension (SEP-2663); change notifications on `subscriptions/listen`; RFC 9207 issuer validation required (SEP-2468); `application_type` in DCR (SEP-837); client credentials bound to the issuing AS (SEP-2352); DCR deprecated in favour of Client ID Metadata Documents; roots, sampling, logging deprecated with a minimum 12-month window (SEP-2577); HTTP+SSE transport deprecated with a one-year offramp; Tasks, MCP Apps and Enterprise Managed Authorization are formal extensions. Authors David Soria Parra and Den Delimarsky. — [MCP blog, 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

- Legacy (2025-11-25 and earlier) path in the SDK is stateful by default, with `stateless_http=True` as an opt-in that "sacrifices sampling/elicitation"; the 2026-07-28 path ignores the flag. — [Deploy & scale](https://py.sdk.modelcontextprotocol.io/run/deploy/), read 2026-10-09

### Inferences
- For a server that only exposes tools, resources and prompts, feature coverage of the two is equal at 2026-07-28; the differences are the tasks extension (FastMCP only), the authorization provider catalogue (FastMCP), and the verifiable conformance baseline (SDK).
- Elicitation "as a feature" has to be designed as MRTR on both: on the SDK via `Resolve(fn)`, on FastMCP via guard-mode `InputRequiredResult`. The old `ctx.elicit()` back-channel exists on both only for legacy clients, which is exactly what Mistral Vibe currently is (see question 7).

### Gaps
- Whether FastMCP runs the conformance harness continuously in CI could not be established from the workflow listing; #4650 shows it was run at least once before 4.0.0.
- I did not fetch the SDK's authorization page in detail; the DEPENDENCIES.md entry should not claim more about Protected Resource Metadata on the server side than the release notes above say (issuer validation on the PRM path since 2.0; `validate_token_resource` since 2.2.0).

## Key question 4: Typing quality under pyright strict

### Takeaway
The SDK ships `py.typed`, runs pyright in strict mode over its own source, and its `@mcp.tool()`/`@mcp.resource()`/`@mcp.prompt()` decorators are identity-typed (`Callable[[_CallableT], _CallableT]`), so decorated functions keep their signatures; FastMCP also ships `py.typed` and identity-typed decorator overloads (verified to return the original function at runtime), but it gates itself with Astral's `ty` with "a number of error types broadly disabled" and no pyright run, so pyright-strict cleanliness of its public surface is unmeasured.

### Cited Findings

### Inferences
- With identity-typed decorators on both, pyright strict will see the decorated function unchanged; neither erases parameter types. The `Callable[..., Any]` bound means pyright cannot check the *body* of a tool against what the framework will call it with, but that is true of any decorator with that bound and is not a strict-mode error.
- The SDK's own strict gate is the same gate this project runs. That makes the SDK the lower-risk choice for "no `# type: ignore`": a public API that passes the author's strict pyright is unlikely to need suppressions downstream. FastMCP's public API may be equally clean under pyright, but nobody measures it; its own suppression above (`# type: ignore[attr-defined]`) is internal and does not reach consumers.
- The camelCase bridge is almost certainly a `__getattr__`-style fallback; pyright strict will reject old names at the call site, which is the right outcome for this project but means the bridge offers nothing to it.

### Gaps
- No pyright-strict run over consumer code using either package was performed in this research. **Measure it in the project worktree before the decision is recorded**: a minimal `MCPServer` with one tool, one resource template, `Context[AppState]`, `Resolve(...)`, and a `Client(server)` test, under the project's `pyproject.toml` pyright settings; the same against FastMCP if it stays in contention.

## Key question 5: Stateless Streamable HTTP, ASGI mounting, horizontal scaling

### Takeaway
On 2026-07-28 connections both are stateless without configuration; for legacy clients the SDK needs `stateless_http=True` (which disables the legacy back-channel), and both require the host app's lifespan to run the session manager when mounted; the SDK additionally documents the two cross-replica concerns, `RequestStateSecurity` keys for MRTR state and a `SubscriptionBus` for notifications, of which it ships only in-memory implementations.

### Cited Findings
- SDK, protocol eras at deployment: 2026-07-28 is "completely stateless", one POST per operation, no `Mcp-Session-Id`, "any worker handles any request", "`stateless_http` flag irrelevant on this path". 2025-11-25 and earlier: "Requires sticky sessions at load balancer", "Cross-worker retries fail with `Session not found`", "Optional `stateless_http=True` disables sessions but sacrifices sampling/elicitation". — [Deploy & scale](https://py.sdk.modelcontextprotocol.io/run/deploy/), read 2026-10-09
- SDK, transport security default rejects non-localhost: `TransportSecuritySettings(allowed_hosts=["mcp.example.com", "mcp.example.com:*"], allowed_origins=["https://app.example.com"])`, otherwise `421 Misdirected Request` with "Invalid Host header" logged server-side only. — [Deploy & scale](https://py.sdk.modelcontextprotocol.io/run/deploy/)
- SDK, MRTR state across workers: `MCPServer("billing", request_state_security=RequestStateSecurity(keys=[key]))`; "Same server name and keys across all instances"; `keys[0]` seals, all entries unseal (rotation); the server name is the default audience claim. — [Deploy & scale](https://py.sdk.modelcontextprotocol.io/run/deploy/)
- SDK, subscriptions across replicas: `MCPServer("Notebook", subscriptions=bus)`; "The SDK provides only in-process `InMemorySubscriptionBus`; implement custom `SubscriptionBus.Protocol` over Redis/NATS for multi-process pub/sub." — [Deploy & scale](https://py.sdk.modelcontextprotocol.io/run/deploy/)
- SDK, process model: "No built-in multi-process support; bring your own server: `uvicorn server:app --workers 4`"; no health route, use `@mcp.custom_route("/health", methods=["GET"])`; behind TLS termination run `uvicorn server:app --proxy-headers --forwarded-allow-ips='<proxy address>'`. — [Deploy & scale](https://py.sdk.modelcontextprotocol.io/run/deploy/)
- SDK, ASGI mounting: `app = Starlette(routes=[Mount("/", app=mcp.streamable_http_app())])`; "a mounted sub-application's lifespan never runs. Whichever app sits at the top of your ASGI stack must enter `mcp.session_manager.run()` in its own lifespan", else `RuntimeError: Task group is not initialized`; default path `/mcp`, `streamable_http_path="/"` to serve at the mount prefix; several servers via `AsyncExitStack`. — [Add to existing app](https://py.sdk.modelcontextprotocol.io/run/asgi/), read 2026-10-09
- SDK, limits: Streamable HTTP servers reject bodies over 4 MiB with HTTP 413 (2.0.0); legacy sessions idle-expire after 30 minutes and cap at 10,000 (2.2.0); SSE events over 1 MiB rejected by the client unless `max_sse_event_size` is raised (2.3.0). — [v2.0.0](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.0.0), [v2.2.0](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.2.0), [v2.3.0](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.3.0)
- FastMCP: `mcp.run(transport="http", host="127.0.0.1", port=8000)` serves at `/mcp`; SSE transport is legacy, "We recommend using HTTP transport instead of SSE for all new projects"; `mcp.http_app()` returns an ASGI app. — [Running your server](https://gofastmcp.com/deployment/running-server), read 2026-10-09
- FastMCP, stateless: `app = mcp.http_app(stateless_http=True)`; "each request creates a fresh transport context, eliminating the need for session affinity entirely"; sticky sessions "don't work reliably" because "most MCP clients use `fetch()` internally and don't properly forward `Set-Cookie` headers"; an `EventStore` enables reconnection with `Last-Event-ID`; when mounting "you **must** pass the lifespan context from the FastMCP app to the resulting Starlette app"; `uvicorn app:app --host 0.0.0.0 --port 8000 --workers 4`. — [HTTP deployment](https://gofastmcp.com/deployment/http), read 2026-10-09
- FastMCP 4.0 on replicas: "modern requests are sessionless and self-contained, so any replica behind an ordinary load balancer can answer them". — [v4.0.0 release notes](https://github.com/PrefectHQ/fastmcp/releases/tag/v4.0.0)
- FastMCP 4.1.0: "HTTP sessions now expire after the MCP SDK's 30-minute idle default instead of never." — [v4.1.0 release notes](https://github.com/PrefectHQ/fastmcp/releases/tag/v4.1.0)
- The transport the brief should still check for a kup6s/compose setup: `Mcp-Method`/`Mcp-Name` headers are required on Streamable HTTP at 2026-07-28, so an ingress or gateway can route on headers. — [MCP blog, 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

### Inferences
- For this project's two hosting modes the SDK's deployment story is: one ASGI app, `uvicorn --workers N` or N replicas, no shared state unless MRTR or subscriptions are used; if MRTR is used, one secret (the `RequestStateSecurity` key) must be shared across replicas, which is one Kubernetes Secret or one compose environment variable. That satisfies the "compose file and a cron line" test.
- The legacy path for Vibe (question 7) needs `stateless_http=True` on the SDK; the cost (no legacy elicitation/sampling) is nil for a server that was not going to use the back-channel anyway.

### Gaps
- Hypercorn is not mentioned on either deployment page; both document uvicorn only. The SDK declares `uvicorn>=0.31.1` as a hard dependency.

## Key question 6: Testing without mocks

### Takeaway
Both provide an in-memory `Client(server)` that drives the real dispatcher without sockets or subprocesses; the SDK documents it with anyio fixtures and `raise_exceptions=True`, FastMCP adds `asgi_client`/`asgi_server` helpers for in-process HTTP; neither requires mocking time, the database or randomness.

### Cited Findings
- SDK: "The SDK's `Client` class, the same one that connects to a URL or launches a subprocess, also connects **in memory**: pass it your server object and it talks to it directly." Fixtures: an anyio backend fixture, an async client fixture inside `async with`; "era-neutral by default: it probes the server and picks the appropriate protocol path", pin `mode="legacy"` for legacy-specific tests; create the test client with `raise_exceptions=True` so errors surface. — [Testing](https://py.sdk.modelcontextprotocol.io/get-started/testing/), read 2026-10-09

### Inferences
- The SDK's in-memory client plus the Starlette app from `streamable_http_app()` driven through `httpx2`'s ASGI transport covers both layers the project will want to test (dispatch and HTTP) without a socket; the second half is not on the SDK's testing page and would have to be written by hand, which is a few lines.
- Nothing in either testing story conflicts with the project's rule on mocks: the real server object is under test, PostgreSQL stays real via testcontainers, and time is not stubbed by either framework.

### Gaps
- The SDK's testing page does not cover in-process HTTP (ASGI transport) testing; whether a documented helper exists elsewhere on the site was not checked.

## Key question 8: Alternatives

### Takeaway
There is no third serious framework: `fastapi-mcp` is at 0.4.0 from 2025-07-28 on `mcp>=1.12` (a zombie by this project's rule), `mcp-use` is a LangChain-based client/agent library on `mcp<2`, and writing on the protocol directly means reimplementing both eras, the header routing, the body and event limits and the host checks that the SDK already passes conformance for.

### Cited Findings
- `fastapi-mcp` 0.4.0, uploaded 2025-07-28, requires `fastapi>=0.100.0`, `mcp>=1.12.0`; repository tadata-org/fastapi_mcp. No release since. — [PyPI JSON `fastapi-mcp`](https://pypi.org/pypi/fastapi-mcp/json), measured 2026-10-09 *(the package is outdated, not the measurement)*
- `mcp-use` 1.7.1, uploaded 2026-09-10, requires `langchain>=1.0.0`, `mcp<2.0.0,>=1.24.0`. — [PyPI JSON `mcp-use`](https://pypi.org/pypi/mcp-use/json), measured 2026-10-09
- Third-party comparison pieces frame the choice as "FastMCP wraps everything in decorators, FastAPI-MCP turns an existing FastAPI app into an MCP server with one import, and the official Python SDK gives you raw spec control at the cost of more boilerplate" — [mcp.directory, "updated May 2026"](https://mcp.directory/blog/fastmcp-vs-fastapi-mcp-vs-python-sdk-2026) *(possibly outdated; pre-2.0/pre-4.0, and the "boilerplate" claim no longer describes `MCPServer`)*; another quotes a 2026 MCP keynote remark that FastMCP is "just way better than the Python SDK we ship" — [agenticwire.news](https://www.agenticwire.news/article/fastmcp-vs-mcp-python-sdk) *(secondary, undated quote, pre-v2 context; treat as colour, not evidence)*
- The SDK's low-level `Server` is the sanctioned "thin" option: constructor-registered `on_*` handlers, hand-written JSON Schema, no argument validation, `add_request_handler` for custom methods. — [Low-level Server](https://py.sdk.modelcontextprotocol.io/advanced/low-level-server/), read 2026-10-09
- What a from-scratch implementation would have to cover at 2026-07-28 alone: per-request `_meta` with protocol version, client identity and capabilities; `Mcp-Method`/`Mcp-Name` headers; MRTR `input_required` result shape; `subscriptions/listen`; `ttlMs`/`cacheScope`; and, for legacy clients, the `initialize` handshake, `Mcp-Session-Id`, and the HTTP GET notification stream. — [MCP blog, 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/); [Deploy & scale](https://py.sdk.modelcontextprotocol.io/run/deploy/)
- A public conformance harness exists against which a hand-written server could be checked: `@modelcontextprotocol/conformance` (npm), pinned at `0.2.0-alpha.11` in the SDK's CI. — [conformance.yml](https://github.com/modelcontextprotocol/python-sdk/blob/main/.github/workflows/conformance.yml), read 2026-10-09; [modelcontextprotocol/conformance](https://github.com/modelcontextprotocol/conformance)

### Inferences
- A thin protocol-level implementation would be sensible only if the dependency footprint of 28 packages were itself unacceptable, or if the SDK's abstractions fought the design (for example, a wire format the SDK validates away). Neither is the case for a tool/resource server; and because two client eras must be served at once, the from-scratch surface is roughly double what it was a year ago.
- Between the SDK's `MCPServer` and its low-level `Server`, the project can start high-level and drop one tool to low-level if an exact schema is ever needed; both run on the same dispatcher and the same ASGI app.

### Gaps
- No Python framework other than the two compared, and the two outdated packages above, surfaced in searches; a Django- or Litestar-specific integration was not looked for.

### Recommendation: the official SDK, `mcp` 2.x, high-level `MCPServer` API

### Counter-argument: FastMCP 4.x

Draft entry, should the counter-argument win:

> **fastmcp** (PrefectHQ/fastmcp) — judged 2026-10-09.
> *Release:* 4.1.0, 2026-10-08 (PyPI); 4.0.0 on 2026-08-31, eleven patch releases to 2026-10-04; 3.x still receives releases (3.4.8, 2026-10-04).
> *Repository activity:* ≥100 commits, 281 PRs closed, 151 issues closed in the 30 days to 2026-10-09; 329 open issues, 86 open PRs; last 100 commits: 49 by one external contributor, 14 by two Prefect employees. Vendor-backed by Prefect, which sells the Prefect Horizon gateway; Horizon-specific auth and CLI code ships in the package.
> *Typing:* `py.typed`; gated with Astral `ty`, "a number of error types broadly disabled" (issue #1587 open since 2025-08-22); no pyright configuration; decorators identity-typed and verified to return the original function; a camelCase compatibility bridge that pyright strict will not see through.
> *Licence:* Apache-2.0.
> *Footprint:* 68 packages on CPython 3.14 (measured 2026-10-09), including `websockets`, `watchfiles`, `pyperclip`, `keyring`, `cyclopts`, `pyyaml`; builds on `mcp>=2.0,<3`.

The case for it: FastMCP ships the tasks extension (`fastmcp-tasks`, SEP-2663) today, which the SDK defers; it has argument completion, `asgi_client` test helpers, a middleware layer that is not labelled provisional, and a catalogue of OAuth providers and an `OAuthProxy` that would save work if the server ever has to be an OAuth resource server for Claude Code while taking an API key from Vibe. Its activity is several times the SDK's, and its surface was hardened by five betas "under real gateways, agent frameworks, and production servers". If the project needs background tasks for long ingests, or OAuth in front of the server within the next stage, FastMCP has the parts and the SDK does not.

The case against it, under this project's rules: 40 more packages for features a stateless tool server does not use; a type gate that is not ours and is known to have rules switched off; a release tempo that will turn Renovate's weekly PR into a FastMCP PR nearly every week; a commercial roadmap next door; and a dependency on the SDK anyway, so every SDK risk is inherited plus FastMCP's own. The tasks extension is the one feature the SDK genuinely lacks, and the SDK roadmap tracks it (#2806); until the project has a concrete need for it, the leaner dependency is the one to record.
