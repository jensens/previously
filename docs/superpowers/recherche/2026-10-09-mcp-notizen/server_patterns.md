# How production MCP servers expose knowledge bases and records (state as of 2026-10-09)

Scope note. All pages were fetched on 2026-10-09/10. Dates in brackets are the publication or "last updated" dates the pages themselves carry. Anything from 2025 is marked **(2025, possibly outdated)** where a later source shows the server moved on. Where a source is a vendor describing its own product, that is said. "Does" means a documented behaviour; "reports works" means a claim about effect, with the number quoted when one was given.

Conventions used below: *tool names* are quoted exactly as the server advertises them; "search→fetch" means a two-step contract where a search tool returns identifiers and a second tool returns the full item.

## Key question 1: What do the widely used servers actually expose (tools, granularity, naming, pagination, IDs, large results, read/write separation, auth)?

### Takeaway
The record-and-knowledge servers that matured in production converged on a small, agent-oriented surface rather than a mirror of their REST API: a search tool with filters and a hard result cap, a fetch tool keyed by URL or ID, Markdown as the response format, read/write separation at the transport or scope level, OAuth 2.1 for hosted servers, and either toolsets or deferred discovery once the catalog passes a few dozen tools.

### Cited Findings

**Reference servers (Anthropic/MCP project)**

- The reference *memory* server stores a knowledge graph of entities (`name`, `entityType`, `observations: string[]`) and relations (`from`, `to`, `relationType`) in a JSONL file; it exposes nine tools: `create_entities`, `create_relations`, `add_observations`, `delete_entities`, `delete_observations`, `delete_relations`, `read_graph`, `search_nodes` (query matched against names, types and observation text), `open_nodes`; `create_relations` fails if an endpoint entity does not exist; the README notes no versioning or timestamps — [modelcontextprotocol/servers src/memory](https://github.com/modelcontextprotocol/servers/tree/main/src/memory) (fetched 2026-10-09).
- The reference *filesystem* server has 13 tools; `read_text_file` takes `head`/`tail` line limits for large files, `edit_file` has `dryRun`, `directory_tree` takes exclusion patterns; allowed directories come from CLI args or, preferred, the MCP Roots protocol, which "completely replace[s] any server-side Allowed directories when provided" — [src/filesystem](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem) (fetched 2026-10-09).
- The reference *fetch* server exposes one tool with `url`, `max_length` ("default: 5000" characters), `start_index` ("default: 0") and `raw`; the README says that with `start_index` the model can read successive sections of a long page "until they find the information they need"; it respects robots.txt for model-initiated requests and uses two user agents ("Autonomous" vs "User-Specified"); it carries the warning that it "can access local/internal IP addresses and may represent a security risk" — [src/fetch](https://github.com/modelcontextprotocol/servers/tree/main/src/fetch) (fetched 2026-10-09).

**MCP specification primitives these servers build on (2025-06-18 revision)**

- Tool results may contain `resource_link` blocks (`uri`, `name`, `description`, `mimeType`, `annotations`) and embedded `resource` blocks (`uri`, `mimeType`, `text`/`blob`); "Resource links returned by tools are not guaranteed to appear in the results of a `resources/list` request"; tools may declare `outputSchema` and return `structuredContent`, and "For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block" — [MCP spec, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools).
- Tool `annotations` exist but "clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers"; errors split into protocol errors (JSON-RPC) and execution errors (`isError: true` in the result); `tools/list` paginates with `cursor`/`nextCursor` — [MCP spec, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools).
- Resources are "application-driven" (the host decides how to include them), identified by URI, support templates (RFC 6570), `subscribe`/`listChanged`, and annotations `audience` (`user`/`assistant`), `priority` (0..1) and `lastModified`; the `https://` scheme is to be used "only when the client is able to fetch and load the resource directly from the web on its own", otherwise "servers **SHOULD** prefer to use another URI scheme, or define a custom one" — [MCP spec, Resources](https://modelcontextprotocol.io/specification/2025-06-18/server/resources).
- Elicitation lets a server request structured user input mid-call via `elicitation/create` with a flat-object schema and a three-action reply (`accept`/`decline`/`cancel`); "Servers **MUST NOT** request sensitive information through elicitation"; the page marks it as newly introduced and liable to change — [MCP spec, Elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation).

**GitHub MCP server (github/github-mcp-server, remote at `https://api.githubcopilot.com/mcp/`)**

- Toolsets: `context`, `actions`, `code_quality`, `code_security`, `copilot`, `copilot_issue_intents`, `dependabot`, `discussions`, `gists`, `git`, `governance`, `issues`, `labels`, `notifications`, `orgs`, `projects`, `pull_requests`, `repos`, `secret_protection`, `security_advisories`, `stargazers`, `users`; default when unspecified: `context`, `repos`, `issues`, `pull_requests`, `users`; stated reason: "Enabling only the toolsets that you need can help the LLM with tool choice and reduce the context size"; `--tools` selects individual tools; "write tools are skipped if `--read-only` is set, even if explicitly requested via `--tools`"; invalid tool names fail startup — [README](https://github.com/github/github-mcp-server) (fetched 2026-10-09).
- Pagination is `page` (min 1) and `perPage` (min 1, max 100) on most list tools, with `after`/`before` cursors on discussions, dependabot alerts and notifications — [README](https://github.com/github/github-mcp-server) (fetched 2026-10-09).
- Remote selection: URL path `/x/{toolset}` for one toolset, `/x/all`, header `X-MCP-Toolsets` ("Comma-separated list of toolsets to enable"), `X-MCP-Readonly`, and `X-MCP-Lockdown`: "Enables lockdown mode, hiding public issue details created by users without push access. Lockdown mode is a best-effort content filter, not a security boundary." and "Server-side lockdown configuration is an upper bound: if the operator has already enabled lockdown mode, this header cannot disable it for a request." — [docs/remote-server.md](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md) (fetched 2026-10-09).
- Auth: OAuth by default on github.com ("token kept in memory only") or a PAT via `Authorization: Bearer`; GHES via `GITHUB_HOST` — [README](https://github.com/github/github-mcp-server).
- OAuth scope filtering (2026-01-28): "When using a classic Personal Access Token (`ghp_` prefix), the server automatically detects your token's OAuth scopes and hides tools you don't have permission to use." — [GitHub changelog 2026-01-28](https://github.blog/changelog/2026-01-28-github-mcp-server-new-projects-tools-oauth-scope-filtering-and-new-features/).

**Atlassian Rovo MCP server (v2, `https://mcp.atlassian.com/v2/mcp`)**

- "150+" tools across 11 product areas, grouped into permission groups per product and intent: `read_jira`, `write_jira`, `search_jira`, `delete_jira` (disabled by default), `manage_jira` (disabled by default), `read_confluence`, `write_confluence`, `search_confluence`, and so on; tool names are camelCase verbs on nouns: `getJiraIssue`, `listJiraIssueComments` ("Paginated comments for a Jira work item"), `searchJiraIssuesUsingJql`, `createJiraIssue`, `editJiraIssue`, `transitionJiraIssue`, `getConfluenceContent`, `searchConfluence` ("Search Confluence content with CQL"), `getConfluenceContentPermissions`; each group maps to an OAuth scope like `read:jira:agent-interface` — [Atlassian supported tools (support site)](https://support.atlassian.com/atlassian-rovo-mcp-server/docs/supported-tools/) (fetched 2026-10-09).
- Cross-product: `search` (beta, "Semantic search across Jira, Confluence, and connected apps", scope `search:rovo:agent-interface`), `getTeamworkGraphObject` ("Fetch data via ARIs/URLs"), `getTeamworkGraphContext`; Teamwork Graph calls "consume 1-10 Rovo credits" — [Atlassian supported tools](https://support.atlassian.com/atlassian-rovo-mcp-server/docs/supported-tools/).

- Generic Rovo search and fetch: search uses "natural language to look up issues, pages, and other content across Jira and Confluence" and fetch retrieves content "using a simple prompt" given "enough information for Rovo to identify the item (such as the issue key or page title)"; no response shape is documented — [Atlassian, Rovo search and fetch](https://support.atlassian.com/atlassian-rovo-mcp-server/docs/using-rovo-search-and-fetch-in-the-atlassian-remote-mcp-server).

### Inferences
- Across GitHub, Atlassian, Linear, Slack, HubSpot and Notion, read/write separation is enforced *outside* the model — endpoint path, header, OAuth scope, or disabled-by-default group — not by tool descriptions; the model-facing hint (`readOnlyHint`) is explicitly untrusted in the spec. For a server whose content is customer data, this is the layer where "what the model may see" belongs.
- Naming splits into two camps: GitHub and Notion use `noun_verb`/`noun-verb` with a `method` or `mode` enum inside (`issue_read`, `notion-query-data-sources`); Atlassian uses `verbNounQualifier` (`searchJiraIssuesUsingJql`). Both work; what they share is that the name encodes object + intent and the query language is explicit in the name or parameter.
- Hard caps on page size (GitHub 100, Notion 50, HubSpot 200/100) are universal; nobody returns an unbounded list, and the servers that handle documents (fetch, filesystem, Anthropic memory tool) all offer offset/line-range paging rather than relying on the client to truncate.

### Gaps
- No official Google-authored Gmail/Drive MCP server surfaced in search; only community wrappers around Google's `gws` CLI. I could not verify any Google-published design for exposing mailbox data via MCP.
- Linear's current tool list and count are not published on its docs page; the "25+" figure is third-party.
- Sentry's current tool enumeration is not on its docs landing page; the `/llms.txt` was not fetched.
- The Notion tool table I fetched is the one live on 2026-10-09; the July 2025 launch set was smaller, but I found no changelog enumerating what was added when.

## Key question 2: Which documented redesigns happened after launch (consolidation, toolsets, dynamic discovery, code mode), and what reasons were given?

### Takeaway
Every major vendor moved in the same direction within roughly a year of launch: fewer, broader tools with a `method` enum; toolsets or scope-based hiding; and on-demand discovery of the rest — and Anthropic and Cloudflare both published numbers showing that loading fewer definitions up front raises accuracy as well as cutting tokens.

### Cited Findings

**GitHub: consolidation, server instructions, scope filtering, dynamic toolsets**

- 2025-10-29: `get_issue`, `get_issue_comments`, `list_labels`, `list_sub_issues` merged into `issue_read` with `method` ∈ {`get`, `get_comments`, `get_labels`, `get_sub_issues`}; `create_issue`+`update_issue` → `issue_write`; four PR-review tools → `pull_request_review_write`; three sub-issue tools → `sub_issue_write`; stated reason: make the server "simpler and more performant by merging more related tools into unified, multifunctional ones", with "configurations leaner, AI reasoning clearer, and performance faster" — [GitHub changelog 2025-10-29](https://github.blog/changelog/2025-10-29-github-mcp-server-now-comes-with-server-instructions-better-tools-and-more/).
- Same release added server instructions: "a feature of the Model Context Protocol specification which acts like a system prompt that guides the model in effectively using an MCP server", used for sequencing ("always use tool A before tool B") and multi-tool workflows — [GitHub changelog 2025-10-29](https://github.blog/changelog/2025-10-29-github-mcp-server-now-comes-with-server-instructions-better-tools-and-more/).
- 2026-01-28: the Projects toolset was consolidated into `projects_list`, `projects_get`, `projects_write`, "reducing token usage by approximately 23,000 tokens (50%)"; OAuth scope filtering hides tools the token cannot use — [GitHub changelog 2026-01-28](https://github.blog/changelog/2026-01-28-github-mcp-server-new-projects-tools-oauth-scope-filtering-and-new-features/).
- 2025-12-10: tool-specific configuration (`--tools`) — [GitHub changelog 2025-12-10](https://github.blog/changelog/2025-12-10-the-github-mcp-server-adds-support-for-tool-specific-configuration-and-more/) (title only verified via search; body not fetched).
- Dynamic toolsets (`--dynamic-toolsets` / `GITHUB_DYNAMIC_TOOLSETS=1`): the server starts with three management tools, `list_available_toolsets`, `get_toolset_tools`, `enable_toolset`, and "allow[s] the MCP host to list and enable toolsets in response to a user prompt" — [instagit summary of github-mcp-server](https://instagit.com/github/github-mcp-server/dynamic-toolsets-on-demand-discovery-mcp-server) (secondary; my fetches of the README and of `pkg/github/dynamic_tools.go` did not return the section, so the verbatim tool descriptions are unverified).

**Atlassian: v2 with deferred tools**

- The v2 server advertises a small set of primary tools and defers the rest behind `discover` + `executeRead`/`executeWrite`/`executeDestructive`, "depending on the operation's risk tier", with the stated reason that this "preserves context window and lets Atlassian add tools without requiring you to reconnect" — [Atlassian developer docs](https://developer.atlassian.com/cloud/rovo-mcp/guides/supported-tools/) (last updated 2026-09-30).

**Notion: rewrite from API mirror to agent-oriented tools**

- Blog 2025-07-15 (Kenneth Sinder): the first open-source server was an API wrapper; feedback showed "the technical barrier was too high for widespread adoption" and "the 1:1 API mapping created suboptimal experiences for AI agents"; the hosted server exposes "a tailored suite of tools optimized for AI agents—not HTTP calls to the API"; Notion-flavored Markdown replaces JSON because it "provides efficient content density per LLM token, requiring fewer tool interactions and less cost"; `create-pages` and `update-page` are rewrites with interfaces "that make more sense for an AI agent conversation than a traditional, rigid web API"; "Notion's URLs and IDs work seamlessly across tool calls" — [Notion blog](https://www.notion.com/blog/notions-hosted-mcp-server-an-inside-look) **(2025; the tool list has since grown to 36)**. No token or call-count numbers are given.
- A third-party server claims "~6–7× fewer response tokens vs the official Notion MCP" — [Grey-Iris/easy-notion-mcp](https://github.com/Grey-Iris/easy-notion-mcp) (vendor claim, unverified).

**Cloudflare: many servers → one API server, and Code Mode**

- Eight product servers are deprecated in favour of one "Cloudflare API MCP Server (recommended)" — [cloudflare/mcp-server-cloudflare](https://github.com/cloudflare/mcp-server-cloudflare) (fetched 2026-10-09). No written rationale on the page.
- Code Mode (2025-09-26, Kenton Varda and Sunil Pai): "LLMs have seen a lot of code. They have not seen a lot of 'tool calls.'"; "The output of each tool call must feed into the LLM's neural network, just to be copied over to the inputs of the next call, wasting time, energy, and tokens."; the agent gets one execute-code tool and a generated TypeScript API; "agents are able to handle many more tools, and more complex tools, when those tools are presented as a TypeScript API rather than directly"; sandbox: V8 isolates, "Network access disabled by default", MCP reached only through bindings, "API keys never exposed to sandboxed code" — [Cloudflare blog](https://blog.cloudflare.com/code-mode/). No benchmark numbers are given.

**Anthropic: tool design, code execution, tool search**

- "Writing effective tools for agents" (2025-09-11, Ken Aizawa et al.): consolidate ("Tools can consolidate functionality, handling potentially multiple discrete operations (or API calls) under the hood" — e.g. `get_customer_context` instead of `get_customer_by_id` + `list_transactions` + `list_notes`); namespace ("asana_search, jira_search" — prefix vs suffix "produced non-trivial performance differences"); name parameters semantically ("Instead of a parameter named user, try a parameter named user_id"); "Implement some combination of pagination, range selection, filtering, and/or truncation with sensible default parameter values"; Claude Code caps tool responses at 25,000 tokens by default; a `response_format` enum: the detailed Slack example is 206 tokens and the concise one 72 (~⅓), the detailed one keeping `thread_ts`, `channel_id`, `user_id` "for chaining tool calls"; "return only high signal information ... eschew low-level technical identifiers (for example: uuid, 256px_image_url, mime_type)"; error messages should "clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks"; reported effect: SWE-bench Verified state of the art for Sonnet 3.5 after description refinement — [Anthropic engineering](https://www.anthropic.com/engineering/writing-tools-for-agents).
- "Code execution with MCP" (2025-11-04): tool definitions presented as a filesystem of TypeScript files; progressive disclosure via directory listing or a `search_tools` function; an example drops "from 150,000 tokens to 2,000 tokens—a time and cost saving of 98.7%"; intermediate results stay in the sandbox ("filter and transform results in code before returning them"); "the MCP client can tokenize PII automatically"; caveat: "Running agent-generated code requires a secure execution environment with appropriate sandboxing, resource limits, and monitoring." — [Anthropic engineering](https://www.anthropic.com/engineering/code-execution-with-mcp).
- "Advanced tool use" (2025-11-24): Tool Search Tool with `defer_loading: true` reports "85% reduction" in tokens, accuracy "Opus 4 improved from 49% to 74%; Opus 4.5 improved from 79.5% to 88.1%"; programmatic tool calling "37% reduction on complex research tasks (43,588 to 27,297 tokens)" with knowledge-retrieval accuracy 25.6%→28.5%; tool-use examples 72%→90% "on complex parameter handling"; defer when "Tool definitions exceed 10K tokens", "10+ available tools", or selection accuracy drops; keep "3-5" critical tools loaded — [Anthropic engineering](https://www.anthropic.com/engineering/advanced-tool-use).
- "Effective context engineering" (2025-09-29): "lightweight identifiers (file paths, stored queries, web links, etc.)" loaded at runtime; Claude Code uses `head`/`tail` and targeted queries "without ever loading the full data objects into context"; a hybrid of some up-front context plus exploration; sub-agents return "a condensed, distilled summary of its work (often 1,000-2,000 tokens)" — [Anthropic engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).

**Sentry: production lessons**

- Talk summary: 60M requests/month from 30M, "5,000+ organizations", "45,000 tool call errors monthly (~0.075% error rate)", three-person team; "when a tool is invoked within the MCP server, they can incorporate an AI agent to process and filter information before returning it"; descriptions carry concrete examples, chaining hints ("you can get more details about a specific issue by using the tool get_issue_details"), FAQ-style guidance and timing expectations; "standardized on Markdown for all tool responses and descriptions"; "context pollution" defined as "the measurable distance between original intent and current direction", mitigated by concise descriptions, in-tool AI filtering and re-anchoring; they shipped "with no observability" and learned of outages from Twitter; a stdio break affecting "10% of queries" went undetected; "When something doesn't work, users don't typically come back the next day—they abandon it for months." — [ZenML summary](https://www.zenml.io/llmops-database/scaling-an-mcp-server-for-error-monitoring-to-60-million-monthly-requests) (secondary summary of a 2025 talk; numbers are the speaker's).

### Inferences
- The consolidation rationale is reported the same way by GitHub ("AI reasoning clearer"), Notion ("suboptimal experiences for AI agents"), Anthropic ("help the LLM with tool choice") and Cloudflare ("handle many more tools") — fewer, wider tools. The one measured counter-signal is Anthropic's own eval that `response_format` and detailed IDs matter for chaining; consolidation does not mean hiding identifiers.
- Two different mechanisms now exist for "not loading everything": host-side (Anthropic's Tool Search Tool, `defer_loading`) and server-side (GitHub dynamic toolsets, Atlassian `discover`). A server that cannot assume its client supports deferred loading needs the server-side variant or a small catalog; for Previously with Claude Code and Mistral Vibe as clients, the catalog should be small enough that neither mechanism is needed.
- Atlassian's `executeRead/Write/Destructive` split shows a vendor deciding that the *risk tier* of an operation should be a first-class routing dimension, not an annotation — consistent with the spec saying annotations are untrusted.

### Gaps
- No vendor published before/after accuracy numbers for its own consolidation; only token figures (GitHub's 23,000 tokens / 50% for Projects). The accuracy evidence is Anthropic's and concerns tool *search*, not tool *merging*.
- Cloudflare gives no written reason for deprecating the product servers in favour of one API server.

## Key question 3: How do servers let the model cite the exact source, and how do clients display it?

### Takeaway
Citation in practice rides on a stable URL or ID returned by search and accepted by fetch; the only client-side citation contract I found that is explicit is OpenAI's ("citation metadata only when url is a non-empty string"), while MCP's own `resource_link` blocks and `lastModified` annotations exist but none of the surveyed record servers document using them.

### Cited Findings
- OpenAI/ChatGPT: `search` results must carry `id`, `title`, `url`; `fetch` returns `id`, `title`, `text`, `url`, `metadata`; "ChatGPT creates citation metadata only when url is a non-empty string." Results lacking a URL "remain as ordinary tool output without citations" — [OpenAI developers, MCP](https://developers.openai.com/api/docs/mcp).
- MCP spec: a tool "MAY return links to Resources" as `resource_link` with `uri`, `name`, `description`, `mimeType`, `annotations` (`audience`, `priority`, `lastModified`); embedded `resource` blocks carry the content plus the same annotations; the `https://` scheme is reserved for things the client can fetch itself, otherwise a custom scheme — [MCP spec, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) and [Resources](https://modelcontextprotocol.io/specification/2025-06-18/server/resources).
- Notion: fetch "by its URL or ID"; "Notion's URLs and IDs work seamlessly across tool calls" — [Notion supported tools](https://developers.notion.com/guides/mcp/mcp-supported-tools), [Notion blog 2025-07-15](https://www.notion.com/blog/notions-hosted-mcp-server-an-inside-look).
- Microsoft Learn: `microsoft_docs_fetch` takes a `url` — the search result's URL is the citation and the fetch key — [MicrosoftDocs/mcp](https://github.com/MicrosoftDocs/mcp).
- Atlassian: fetch by "issue key or page title"; Teamwork Graph objects by "ARIs/URLs" — [Atlassian Rovo search and fetch](https://support.atlassian.com/atlassian-rovo-mcp-server/docs/using-rovo-search-and-fetch-in-the-atlassian-remote-mcp-server), [supported tools](https://support.atlassian.com/atlassian-rovo-mcp-server/docs/supported-tools/).
- Graphiti: `get_episode_entities` exists to "Trace provenance of entities/facts from specific episodes"; edges are retrievable by UUID via `get_entity_edge` — [getzep/graphiti mcp_server](https://github.com/getzep/graphiti/tree/main/mcp_server).
- Anthropic's guidance keeps technical IDs out of the concise format but in the detailed one, because `thread_ts`, `channel_id`, `user_id` are needed "for chaining tool calls" — [Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents).
- Sentry's descriptions chain tools by name ("you can get more details about a specific issue by using the tool get_issue_details") — [ZenML summary](https://www.zenml.io/llmops-database/scaling-an-mcp-server-for-error-monitoring-to-60-million-monthly-requests) (secondary).

### Inferences
- None of the ticket/document servers surveyed returns `resource_link` blocks or sets `lastModified`; they put URLs inside Markdown text. A server that wants a client to *render* a citation has to assume the client reads the text, which is why OpenAI made the URL field mandatory in a structured result. For Previously, returning both a Markdown body (for Claude Code and Mistral Vibe today) and `structuredContent` with `id`/`url` (for any client that honours it) costs little and covers both.
- The "URL as identifier" convention works because the URL is also what a human can open. Previously's units of text have no public URL; a custom scheme (`previously://…`) plus a human-openable anchor (event id, source message-id, offset) would be the equivalent.

### Gaps
- I found no documentation from Claude Code, Claude Desktop or Mistral Vibe on how (or whether) they render `resource_link` blocks or citation metadata from MCP tool results. Whether a client turns a URI in a tool result into a clickable citation is unverified.

## Key question 4: How do search tools look (hybrid search, filters, snippets vs full documents, follow-up fetch)?

### Takeaway
The dominant shape is search→fetch: a search tool with a natural-language query, a few structured filters and a hard cap returns identifiers plus a short rendering; a separate fetch tool returns one item in full, with range or offset paging for long content. Hybrid search is implemented inside the server (Graphiti: embeddings + BM25 + graph) and not exposed as a model-facing choice.

### Cited Findings
- OpenAI's deep-research contract is search→fetch by design, with fetch returning "The full text of the document or item" — [OpenAI developers, MCP](https://developers.openai.com/api/docs/mcp).
- Microsoft Learn: semantic `microsoft_docs_search` then `microsoft_docs_fetch` by URL returning the page "into markdown format" — [MicrosoftDocs/mcp](https://github.com/MicrosoftDocs/mcp).
- Context7: resolve-then-query with a `language` ranking hint — [upstash/context7](https://github.com/upstash/context7).
- Notion: `notion-search` with `filters` (location, creator, date, title, status), `sort`, `limit` (max 50), `query_type`; the search "supports semantic search via questions, surfacing pages across your Notion workspace plus over ten third-party connected apps"; `notion-fetch` by URL/ID; `notion-query-data-sources` adds SQL/rows/saved-view modes with limit 100 — [Notion supported tools](https://developers.notion.com/guides/mcp/mcp-supported-tools), [Notion blog](https://www.notion.com/blog/notions-hosted-mcp-server-an-inside-look).
- Atlassian exposes both an explicit query language (`searchJiraIssuesUsingJql`, `searchConfluence` with CQL) and a natural-language `search` (beta, semantic, cross-product) — [Atlassian supported tools](https://support.atlassian.com/atlassian-rovo-mcp-server/docs/supported-tools/).
- Sentry translates natural language to its query syntax inside the tool using an embedded LLM (`search_issues`, `search_events`, `search_errors` "require an LLM provider") — [getsentry/toolkit](https://github.com/getsentry/sentry-mcp).
- HubSpot: `search_crm_objects` with text query, "up to five filter groups with up to six filters each", sorting, 200/page; `query_crm_data` SQL without joins — [HubSpot developer docs](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/integrate-with-the-remote-hubspot-mcp-server).
- Slack search: "filter by date, user, and content type. Retrieve metadata and content." — [Slack developer docs](https://docs.slack.dev/ai/slack-mcp-server/).
- GitHub: `search_issues` takes a natural-language `query` with `page`/`perPage` — [README](https://github.com/github/github-mcp-server).
- Graphiti: "Combines semantic embeddings, keyword (BM25), and graph traversal for low-latency, high-precision queries without reliance on LLM summarization", "Typically sub-second latency" versus GraphRAG's "Sequential LLM summarization" at "Seconds to tens of seconds"; separate `search_nodes` and `search_memory_facts`, with `valid_at`/`invalid_at` filters — [getzep/graphiti README](https://github.com/getzep/graphiti), [mcp_server](https://github.com/getzep/graphiti/tree/main/mcp_server).
- Qdrant: single `qdrant-find` over one collection; descriptions tunable per deployment — [qdrant/mcp-server-qdrant](https://github.com/qdrant/mcp-server-qdrant).
- Long-content paging: fetch server `start_index`/`max_length` (default 5000 chars); filesystem `head`/`tail`; Anthropic memory tool `view_range` and 16,000-character truncation; Claude Code's 25,000-token result cap — [src/fetch](https://github.com/modelcontextprotocol/servers/tree/main/src/fetch), [src/filesystem](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem), [memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool), [Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents).
- Anthropic's example for log search: replace `read_logs` with `search_logs` returning "only relevant lines plus context", and when truncating tell the agent to "make many small and targeted searches instead of a single, broad search" — [Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents).

### Inferences
- Where a precise query language exists (JQL, CQL, SQL), the mature servers expose it *and* a natural-language search, rather than choosing. The embedded-LLM translation (Sentry) is the expensive alternative and brings its own provider dependency; the cheap alternative is to document the query syntax in the tool description and let the client model write it.
- Nobody exposes "hybrid vs vector vs keyword" as a parameter. Previously's full-text-now, vector-later plan is compatible with a single `search` tool whose backend changes without a tool-surface change.

### Gaps
- Result-shape details for Atlassian's generic `search`/`fetch` and Microsoft's `microsoft_docs_search` (chunk count, chunk size) are not in the fetched pages.

## Key question 5: What goes wrong with memory servers (stale memories, contradictions, unbounded growth), and how do append-only / event-sourced designs fare?

### Takeaway
The two documented answers to contradictions are consolidation (mem0: an LLM decides ADD/UPDATE/DELETE/NONE against similar memories) and bi-temporal invalidation (Zep/Graphiti: the old fact gets a `t_invalid`, nothing is deleted, point-in-time queries stay possible); the reference memory server has neither timestamps nor supersession, and vendors converge on expiry, decay and background consolidation to keep growth in check.

### Cited Findings
- Reference memory server: observations are plain strings on entities; the README notes "No explicit versioning or timestamp tracking" — [src/memory](https://github.com/modelcontextprotocol/servers/tree/main/src/memory).
- Zep paper (2025-01-20, Rasmussen, Paliychuk, Beauvais, Ryan, Chalef): "timeline T represents the chronological ordering of events, and timeline T′ represents the transactional order of Zep's data ingestion"; edges carry `t'_created` and `t'_expired` (T′) and `t_valid`, `t_invalid` (T); "When the system identifies temporally overlapping contradictions, it invalidates the affected edges by setting their t_invalid to the t_valid of the invalidating edge."; this "enables the dynamic addition of data to Graphiti as conversations evolve, while maintaining both current relationship states and historical records of relationship evolution over time"; reported results DMR "94.8% vs 93.4%" against MemGPT and LongMemEval "accuracy improvements of up to 18.5% while simultaneously reducing response latency by 90%" — [arXiv 2501.13956](https://arxiv.org/abs/2501.13956), [HTML v1](https://arxiv.org/html/2501.13956v1) (vendor-authored paper).
- Graphiti README: "Facts have validity windows: when it became true, and when (if ever) it was superseded." and "When information changes, old facts are invalidated — not deleted. Query what's true now, or what was true at any point in time."; "Automatic fact invalidation with temporal history preserved" — [getzep/graphiti](https://github.com/getzep/graphiti).
- mem0 paper (2025-04-28, Chhikara et al.): memories are extracted, consolidated and retrieved; reported "26% relative improvements in the LLM-as-a-Judge metric over OpenAI", "91% lower p95 latency" and "saves more than 90% token cost" versus full context; the graph variant "around 2% higher" — [arXiv 2504.19413](https://arxiv.org/abs/2504.19413) (vendor-authored).
- mem0 docs on the update step: the LLM "returns a strictly formatted JSON list specifying actions, with each entry containing an event field with values ADD, UPDATE, DELETE, or NONE"; DELETE removes "memories that conflict with the new memory"; `update` "lets you fix or enrich an existing memory without deleting it" — [docs.mem0.ai update page (via search)](https://docs.mem0.ai/core-concepts/memory-operations/update).
- mem0 docs on `add` (fetched 2026-10-09) now describe an "additive pipeline": "New memories are added without overwriting or deleting existing memories."; "When you switch to `infer=False`, Mem0 stores your payload exactly as provided, so duplicates can land. Mixing both modes for the same fact can save it twice."; `expiration_date` hides expired memories unless `show_expired` — [docs.mem0.ai add page](https://docs.mem0.ai/core-concepts/memory-operations/add), [memory operations](https://docs.mem0.ai/core-concepts/memory-operations). **Conflict:** the 2025 paper and the update page describe LLM-decided UPDATE/DELETE; the current add page says additive-only. I cannot tell from the pages whether the pipeline changed or the documentation simplified; treat mem0's consolidation behaviour as undetermined.
- Letta: background "Dreaming" subagents "consolidate useful lessons, and update memory"; `/doctor` audits "duplication, and system-prompt token usage" — [Letta docs](https://docs.letta.com/configuration/memory).
- Anthropic memory tool guidance: "Track memory file sizes and cap how large a file can grow"; "Periodically delete memory files that haven't been accessed in a long time"; strip sensitive data before writing; reject paths outside `/memories` — [memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool).
- A vendor comparison (2026-05-27, Brandon Waselnuk, getunblocked.com — promotes its own product) reports agentmemory ships "53 tools, 6 resources, 3 prompts, and 4 skills" and warns "Adding 53 more tool definitions can push your context tax past the point where your agent starts making mistakes"; Stash runs "contradiction detection, confidence decay"; it also states that benchmark "Scores across them aren't apples-to-apples" — [getunblocked.com](https://getunblocked.com/blog/memory-mcp-servers-compared/).
- Community articles describe the failure mode in prose ("A memory system that never revalidates what it's holding will hand back stale conclusions dressed up as current facts") — [dev.to](https://dev.to/shweta_mishra_b3c97874de9/mcp-connected-your-tools-it-didnt-fix-your-agents-memory-ph6), [datamcp.app](https://datamcp.app/blog/multi-agent-memory) (opinion pieces, no data).
- Sentry's "context pollution" and its mitigation by filtering inside the tool — [ZenML summary](https://www.zenml.io/llmops-database/scaling-an-mcp-server-for-error-monitoring-to-60-million-monthly-requests) (secondary).

### Inferences
- The Zep/Graphiti design is the closest published analogue to Previously's append-only store: ingestion time and validity time are separate axes, supersession is a new fact plus an `invalid_at` on the old one, and provenance to the source episode is a first-class tool. It is the only surveyed memory design where "what was true on date X" is answerable, which is exactly what a chronicle of obligations needs.
- Consolidation-at-write (mem0) trades auditability for compactness: a DELETE on contradiction removes the evidence that the contradiction existed. For customer histories, where the contradiction itself may be the fact of interest, that is the wrong trade, and mem0's own docs drifting toward "additive" suggests the vendor felt the cost.
- Growth is handled everywhere by something *outside* the write path: expiry dates, decay, background consolidation. An append-only store should expect to need an equivalent — in Previously's case the policy layer and erasure, plus search ranking by recency/validity rather than deletion.

### Gaps
- No independent (non-vendor) measurement of stale-memory or contradiction rates in any MCP memory server was found.
- Whether Graphiti's invalidation is reliable in practice (false invalidations, missed contradictions) is not reported; the paper reports benchmark accuracy, not invalidation precision.

## Key question 6: What is specific to exposing email/CRM data via MCP (privacy controls, redaction, injection)?

### Takeaway
The servers that hold mail and CRM data put the policy on the server side (HubSpot blocks email/call/meeting activity entirely when "Sensitive Data" is on; permissions mirror the human user's), separate write tools with user confirmation, and treat every retrieved message as a prompt-injection vector — with published exploits for Gmail-connected agents.

### Cited Findings
- HubSpot: with Sensitive Data on, "activity (e.g., calls, emails, meetings, notes, and tasks) and conversation data will be blocked from access through the MCP server"; `manage_crm_objects` writes require "user confirmation"; inbox visibility restrictions carry over — [HubSpot developer docs](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/integrate-with-the-remote-hubspot-mcp-server).
- Slack: least-privilege scopes per tool and admin approval of clients; "Using these clients means giving them access to your Slack data" — [Slack developer docs](https://docs.slack.dev/ai/slack-mcp-server/).
- GitHub lockdown mode hides content "created by users without push access" and is "a best-effort content filter, not a security boundary"; operator setting is an upper bound the request cannot lower — [docs/remote-server.md](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md).
- Gmail-style attacks: a LangChain GmailToolkit indirect prompt injection with email exfiltration is tracked as CVE-2025-46059 — [Netzilo threat library](https://www.netzilo.com/threats/atr-langchain-gmailtoolkit-indirect-prompt-injection-email-exfil) (secondary); StackOne lists hidden-HTML instructions in email bodies ("zero-opacity divs or display:none blocks") that cause an agent to forward sensitive mail — [StackOne blog](https://www.stackone.com/blog/prompt-injection-mcp-10-examples/) (vendor blog); a calendar-invite-triggered exfiltration was reported 2025-09-15 — [Dataconomy](https://dataconomy.com/2025/09/15/gmail-ai-prompt-injection-attack/) (press, secondary).
- Google Cloud's guidance for its managed MCP servers names the vector ("share with a victim directly (e.g., in an email or calendar) or indirectly (e.g., by including them in Cloud Storage or BigQuery) and wait for the agent to act") and mitigations: constrained environments without internet access, Principal Access Boundaries, VPC Service Controls, and "Enable Model Armor to detect and block potential prompt injection attacks from data accessed through Google's managed MCP servers." — [Google Cloud docs](https://docs.cloud.google.com/data-agent-kit/prompt-injection-risk).
- MCP spec security: servers "MUST ... Sanitize tool outputs"; clients "SHOULD ... Show tool inputs to the user before calling the server, to avoid malicious or accidental data exfiltration" and "Validate tool results before passing to LLM"; "there **SHOULD** always be a human in the loop with the ability to deny tool invocations" — [MCP spec, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools).
- Anthropic's code-execution pattern: "Intermediate results stay in the execution environment by default" and "the MCP client can tokenize PII automatically", so sensitive values can flow between tools without entering the model's context — [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp).
- Anthropic memory tool: "Claude usually refuses to write sensitive information to memory files. For stronger guarantees, add validation that strips sensitive data before your handler writes the file." — [memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool).
- Elicitation must not be used for sensitive information — [MCP spec, Elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation).

### Inferences
- No surveyed server documents field-level redaction of message bodies; the published controls are coarse (block a category, mirror user permissions, hide a class of authors). Previously's "policy decides what the model may see" is finer than anything in the field, and there is no precedent to copy for its tool-facing shape — which argues for keeping the policy evaluation inside the server, before rendering, with the tool surface unaware of it.
- Every email body returned by a tool is untrusted input to the client model. A server cannot fix that, but it can label quoted content as data (fenced, with provenance) and keep its own tool descriptions free of anything that could be mistaken for instructions.

### Gaps
- No official Google/Microsoft mail MCP server documentation with privacy controls was found; the Gmail evidence is attacks on third-party toolkits.
- No server documents how it handles erasure requests (right to be forgotten) through MCP; `delete_all_memories` (mem0) and `delete_episode` (Graphiti) are wholesale, not per-subject.

## Patterns to adopt and patterns to avoid for Previously's server

### Takeaway
Adopt search→fetch with stable identifiers, Markdown plus structured results, a small catalog with `method` enums, server-side read/write and policy gating, and Graphiti-style validity windows; avoid API mirroring, unbounded lists, consolidate-on-write memory semantics, and embedded LLMs in the read path.

### Cited Findings (patterns, each with its counter-argument)

**Adopt**

- **search→fetch with `id`/`url` on every hit.** Precedent: OpenAI contract, Microsoft Learn, Notion, Atlassian, Context7 — [OpenAI](https://developers.openai.com/api/docs/mcp), [Notion](https://developers.notion.com/guides/mcp/mcp-supported-tools). *Counter:* two calls per fact doubles round-trips; Anthropic's consolidation advice (`get_customer_context`) argues for a fetch that bundles the chronicle entry with its sources in one call — [Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents). Resolution candidate: search returns ids + snippet, fetch returns the unit *and* its citation block in one result.
- **Markdown body + `structuredContent` with ids.** Precedent: Notion's Markdown and Sentry's standardisation; spec's dual return — [Notion blog](https://www.notion.com/blog/notions-hosted-mcp-server-an-inside-look), [MCP spec Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools). *Counter:* dual output doubles payload tokens for clients that read both; the spec's "SHOULD also return the serialized JSON" is for backward compatibility, not a recommendation to ship twice. Keep the text block as the Markdown rendering, not a JSON copy.
- **Small catalog, `method` enums, read/write split by endpoint or scope.** Precedent: GitHub `issue_read`/`issue_write`, Linear `/readonly` + `read` scope, HubSpot write confirmation — [GitHub changelog 2025-10-29](https://github.blog/changelog/2025-10-29-github-mcp-server-now-comes-with-server-instructions-better-tools-and-more/), [Linear docs](https://linear.app/docs/mcp). *Counter:* Anthropic measured that parameter ambiguity hurts (72%→90% only after adding examples); a `method` enum moves ambiguity from the tool list into a parameter — [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use). Mitigation: tool-use examples in the description, as Sentry does.
- **Validity windows and supersession instead of deletion; provenance tool.** Precedent: Zep's `t_valid`/`t_invalid`, Graphiti's `get_episode_entities` — [arXiv 2501.13956](https://arxiv.org/html/2501.13956v1), [Graphiti mcp_server](https://github.com/getzep/graphiti/tree/main/mcp_server). *Counter:* every retrieval then has to filter on validity, and a model asked "what is the obligation" can be handed both the superseded and the current assertion; Graphiti answers that with `valid_at`/`invalid_at` filters defaulting to "now", which the tool must do too.
- **Hard caps and paging on everything; truncation messages that tell the model what to do next.** Precedent: Notion 50, GitHub 100, fetch `start_index`, Claude Code 25,000 tokens — [Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents). *Counter:* caps hide completeness; a chronicle query that silently stops at 50 events misleads worse than a long result. Return the total count and a continuation cursor with every page.
- **Server instructions for workflow (search before asserting, cite before answering).** Precedent: GitHub server instructions; Anthropic's memory protocol injected by the API — [GitHub changelog 2025-10-29](https://github.blog/changelog/2025-10-29-github-mcp-server-now-comes-with-server-instructions-better-tools-and-more/), [memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool). *Counter:* clients differ in whether they surface server instructions at all (unverified for Mistral Vibe); do not rely on them for anything a tool result can enforce.
- **Policy and permission evaluation inside the server, before rendering.** Precedent: HubSpot sensitive-data block, GitHub scope filtering and lockdown as an operator upper bound — [HubSpot](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/integrate-with-the-remote-hubspot-mcp-server), [GitHub remote-server.md](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md). *Counter:* hidden tools and silently filtered results make the model's failures look like missing data; GitHub chose hiding, HubSpot chose an explicit block. Prefer an explicit "withheld by policy" marker over silence.

**Avoid**

- **Mirroring the REST/ORM surface 1:1.** Notion's stated reason for the rewrite — [Notion blog](https://www.notion.com/blog/notions-hosted-mcp-server-an-inside-look). *Counter:* a thin mirror is cheapest to build and Cloudflare's Code Mode argues the model copes with large APIs if they are presented as code — [Cloudflare](https://blog.cloudflare.com/code-mode/); but that presumes a sandboxed execution client, which neither Claude Code's MCP path nor Mistral Vibe guarantees.
- **Consolidate-on-write (LLM decides UPDATE/DELETE of prior facts).** mem0's design; its own docs now hedge toward additive — [arXiv 2504.19413](https://arxiv.org/abs/2504.19413), [mem0 add docs](https://docs.mem0.ai/core-concepts/memory-operations/add). *Counter:* an append-only store without consolidation grows and retrieval noise rises; the vendor comparison's "context tax" warning applies to results as much as to tool lists — [getunblocked.com](https://getunblocked.com/blog/memory-mcp-servers-compared/). Answer with ranking and validity filters, not with rewriting history.
- **An embedded LLM in the read path.** Sentry's natural-language search needs an `EMBEDDED_AGENT_PROVIDER` — [getsentry/toolkit](https://github.com/getsentry/sentry-mcp). *Counter:* Sentry reports it as the main lever against context pollution ("incorporate an AI agent to process and filter information") — [ZenML summary](https://www.zenml.io/llmops-database/scaling-an-mcp-server-for-error-monitoring-to-60-million-monthly-requests). For customer data it adds a second model that sees the content, which the policy layer would have to cover too.
- **Dozens of fine-grained tools or dynamic discovery for a single-domain server.** agentmemory's 53 tools; Anthropic's "10+ tools" threshold for deferral — [getunblocked.com](https://getunblocked.com/blog/memory-mcp-servers-compared/), [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use). *Counter:* Atlassian's deferral works at 150+ tools and lets them add tools without reconnection — [Atlassian](https://developer.atlassian.com/cloud/rovo-mcp/guides/supported-tools/); it is the right tool at that scale, and the wrong complexity at ten.
- **Relying on tool annotations or descriptions as the safety boundary.** Spec: annotations untrusted; GitHub: lockdown "not a security boundary" — [MCP spec Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools), [GitHub remote-server.md](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md). *Counter:* annotations still help a well-behaved client prompt for confirmation; set them, just do not depend on them.
- **Shipping without per-tool telemetry.** Sentry learned of outages "from Twitter" and missed a 10% stdio failure — [ZenML summary](https://www.zenml.io/llmops-database/scaling-an-mcp-server-for-error-monitoring-to-60-million-monthly-requests) (secondary). *Counter:* telemetry on a customer-data server is itself sensitive; log tool name, latency, error class and result size, not content.

### Inferences
- The field's convergence is strong enough on search→fetch, caps, Markdown and read/write separation that departing from it needs a measured reason; the open design choices for Previously are the ones nobody has a precedent for — field-level policy, erasure through an append-only log, and citations to units of text without public URLs.

### Gaps
- No surveyed server targets Mistral Vibe; all client-side behaviour claims (citation rendering, server instructions, annotations) are unverified for that client and should be measured against it before any of the "adopt" items that depend on client behaviour is fixed in a specification.
